# Frontend: Settings page

The Settings page: Update now, the time zone, and the Scheduling, Job Sheets, Clients, Appearance, Notifications, Backup, Tidy up and Stats cards.

## Update now and the time zone

- The Settings page holds the Update now button (the manual full run, `generateWeeklySchedule`) beside Save settings; Update now is disabled while a run is in progress; runs use the saved settings, so it first saves the form when the days, gap, schedule order, day window or lunch fields differ from the saved values (and stops if that fails). On success it reports how many tasks were placed, the last day used (`lastScheduledDate`), the window (`scheduleDays`) how many could not be placed and how many are waiting on materials; on failure it shows the engine's error text. Saving shows a warning when the response lacks `scheduleDays`, `gapMinutes`, `scheduleOrder`, `day` or `lunch` (a backend that predates a setting). Its result line (`#scheduleStatus`, also used by Reschedule) sits under the form on the same page. Every date and time on the page uses one configured zone: `loadSettings` reads `getSettings` after sign-in and `applySettings` switches the formatters (default Pacific/Auckland until the settings arrive or if they fail to load), redraws the list, and sets the page title to the location name.

## Settings cards

- Every card on the Settings page is a collapsible `<details class="card settings-card">` whose summary is its title with a turning chevron, all collapsed on every load (the open state is not remembered). The Settings page's first card is titled "Scheduling" and edits, with short labels, the days to schedule (a number field, 1 to 28) and the gap between tasks (a number field, 0 to 60 minutes; empty counts as 0) side by side, a Warn when a timer has run for field (whole hours, 1 to 48; empty leaves the saved value alone; `timerWarnHours`), a Schedule tasks by select (Urgency, the default, or Task number; `scheduleOrder`), the daily window (a start and an end time field, default 9:00 and 17:00), a lunch break (a checkbox, a start time and a length in minutes, 5 to 180; the time and length are disabled while the box is unticked), the location (place search against the Open-Meteo geocoding API called from the browser with plain `fetch`, never `apiFetch`, so no Firebase token goes to a third party; picking a result sets name, latitude, longitude and time zone together; the search box is `makePlaceSearch`, which is also the Clients form's search while no Places key is set), the automatic schedule (enabled, plus one Repeat every select: every 15/30/60/120/240 minutes during 8:00-20:00, or "Daily at 8pm" (last in the list), whatever the daily window; the page always saves `time` as 20:00, and `scheduleChoice`/`scheduleFromChoice` map the select to `frequency`, `time` and `intervalMinutes`) and shows the last automatic run; Save posts the whole form to `updateSettings` and shows the server's error text when it rejects a field. Below that card, a "Job Sheets" card holds a multi-line Contractor information field (up to 1000 characters), an Hourly rate number field (empty for none; no GST; the default, which a client's own rate overrides) and a Travel rate per km number field (empty for none; no GST) with one Save button (`saveJobSheetSettings`, `jobSheetPayload(text, rate, travelRate)`), which sends only `jobSheet` so unsaved Scheduling edits are untouched; `applySettings` replaces each field only while it has no unsaved edits (`savedContractorInfo`, `savedHourlyRate`, `savedTravelRate`). A "Clients" card follows (`loadClients` after sign-in through `getClients`, `allClients`). Above the list is the Projects section's field: a text input (`#newClientName`, 100 characters, "Search clients or projects, or type a new client name") and an Add button (`#addClientBtn`). Typing redraws the list (`renderClients`), narrowed by `filterClients(clients, projects, query)`: every word of the query must be in `clientSearchText(client, projects)` (name, location name, phone, email and the names of its projects), case ignored, a blank query keeps all; "No clients match the search." shows when none do, "No clients yet." for an empty list. Add (Enter or the button; `addClient`) saves nothing: it opens the client form (below) for a new client, its Name filled from the trimmed text and the Location box focused (`fillClientForm(null, { name })`); an empty field does nothing and a name an existing client already has is reported in `#clientsStatus` and opens nothing. Save client then creates it (`updateClient` CREATE through `saveClientRequest`, the whole form as typed; a taken name shows the server's error and keeps the form open) and on success closes the form and empties the search field, so the whole list shows again; Cancel drops the draft. The list (`#clientList`, the Queue Projects filter's `.project-list` look, hidden until the clients load) shows each client as a `.project-item` row holding its name only, the row being edited marked; tapping a row (or Enter or Space on it) opens its form. Add, or a row, opens one form, hidden until then (`#clientEdit`, shown by `fillClientForm(client)` for an edit and `fillClientForm(null, draft)` for a new client, hidden again by `fillClientForm(null)`; its Save client and Cancel buttons never change text; Save client sends UPDATE while `editingClientId` is set, else CREATE; below them a Delete client button (`#deleteClientBtn`, shown only while an existing client is edited, `clientDeleteShown`) asks `deleteClientPrompt`, which says the projects stay with no client, then closes the form), the Clients form block: `clientFormHtml(prefix, options)` is its only markup, every id starting with the prefix (`Name`, `Location`, `LocationNote`, `PlaceSearchBtn`, `ClearCoordsBtn`, `PlaceResults`, `CoordsNote`, `Phone`, `UseWhatsApp`, `Email`, `Url`, `HourlyRate`; the card's prefix is `client`, so `clientName` and so on; the add card, the edit modal and the Projects section hold one each for a new project's client, prefixes `manualClient`, `editClient` and `projectClient`), put in a container and wired by `mountClientForm(prefix, containerId, options)` (the card's is `#clientFormMount`; the add card's and the edit modal's blocks pass `{ nameRow: false }`, which hides the Name row because the Client field's picker fills the Name box), each block keeping its own map position and autocomplete in `clientFormState(prefix)`, and filled and read by `fillClientFormBlock(prefix, client)` and `readClientForm(prefix)` (`clientFormFill` and `clientFormValues` are the pure halves, `clientFormBody` makes the `updateClient` object); the Save and Cancel buttons and the status line are the card's own. The form (name, a Location text field (up to 200 characters, the client's address, printed on job sheets and used for navigation; it is also the search box) with, while a position is held, a Clear position button. With `CONFIG.placesApiKey` set the field is a type-ahead (`makePlacesAutocomplete`, Address autocomplete in infrastructure.md): picking a suggestion sets the text to the address without its country and the block's position (`clientFillFromPlace`), the Find on map button hidden. Without a key a Find on map button searches the typed text through `makePlaceSearch` (`placeQueries`: the text as it stands, then its town-like parts, at most 4 searches, the list saying which one found places), and picking a result keeps the text as typed and sets the block's position; a note under the field says "Map position set: Orewa, Auckland, New Zealand" for a place found now, "Map position saved (lat, lon)" for a stored one or "No map position yet."; emptying the text drops the position when saved; phone, a "Use WhatsApp for calls and texts" checkbox, email, a Link box (`#clientUrl`, up to 500 characters; sent as `url`, empty for none, and an edit replaces it), Hourly rate (0 to 10000); a bad email, link or rate is a warning alert and nothing is sent (`clientFormWarning`: `INVALID_EMAIL`, `INVALID_URL` or `INVALID_RATE`, from `parseEmailText`, `parseUrlText` and `parseCostText`, the same check for every place that holds the block); `fillClientForm` fills the card's form; the rate box is empty for the global rate, shown as a placeholder) that adds a client, or saves the edited one with Cancel to leave editing, through `updateClient` (the server's error text shown on a taken name or a bad email). Appearance, Notifications and Backup follow.

## Notifications, Backup and Tidy up cards

- A Notifications card follows (`pushState`, `renderPush`): its text says whether this device is unsupported, blocked, off or on, and it shows only the buttons that fit: Turn on notifications (`enablePush`: asks the browser for permission first, inside the tap, then gets the token and registers it), Send a test (`sendPushTest`: posts to `sendTestNotification` and reports how many devices got it, `pushTestText`) and Turn off (`disablePush`: unregisters the token and deletes it from Firebase); after sign-in `refreshPushToken` swaps in a new token when Firebase has issued one. Under those buttons, "Tell me when" holds three checkboxes (run fails, rain moves a task, a task is about to start) and a select for how long before (30 minutes, 1 or 2 hours; disabled while start reminders are off), saved as soon as one changes (`saveNotifySettings`, `notifyPayload`: only `notify` is sent; a failure restores the saved choices, `renderNotifySettings`, `notifyFormValues`). A Backup card below that has a Download all data button (`downloadExport`): it calls `exportData` through `apiFetch` (a plain link would not carry the sign-in token) and saves the response as `taskhub-export-YYYY-MM-DD.json` (`exportFilename`, the date in the configured zone), the status line saying what the file holds (`exportSummary`). Under it the card holds a Completed work spreadsheet: From and To date fields (either may be empty) and a Download button (`downloadCsv`: posts `csvRequestBody` to `exportCompletedCsv` through `apiFetch` and saves the response as `completed-work-<from>-to-<to>.csv` (`csvFilename`), the status line giving the number of tasks). A Tidy up card below that has a Delete duplicate tasks button (`removeDuplicateTasks`): it asks `removeDuplicateTasks` for a dry run, lists the copies in a confirm dialog and only then deletes them; `addOrUpdateTask` logs a warning when one request adds more than 3 tasks, to help trace how a queue gets duplicated. The last card is Stats (`#statsDetails`, collapsed by default and, like the others, its open state left alone when it reloads, hidden while there are no completions or the load failed): every visit to the Settings tab calls `fetchStats`, which reads `getCompletedTasks` with `limit=1` (the summary does not depend on the limit) and fills `#statsSummary` with `renderSummary`; without a connection it keeps what an earlier visit showed, else says "Stats need a connection.". The summary holds the total completed and tracked time (`totalMinutes`), a streak line ("Current streak: 3 days · Longest: 9 days", a "+" after a number whose run reaches the window's first day, `streakText`), a per-week bar list, priority, tag and project chips, the project chips being "📁 Garden 2 · 45m" with the tasks of deleted projects together as "Deleted project" (`statProjectName`), and a "Most completed jobs" list of the first 10 `byJob` entries, a title with "6 in 8 wks · 24 total · avg 45m · est. 40m" under it (`jobStatsText`).
