# Frontend: tasks

Task cards and gestures, the edit modals, the timer, adding tasks, completing, deleting, Undo and Snooze. Offline behaviour of these is in offline.md and offline-edits.md.

## Task cards and gestures

- Each task row starts with a task-number chip ("#3", `numberChipText`) before its priority badge: the task's place in the queue, 1..n over the whole list (`queueNumbers`: stored `order` ranks in order, ties in list order, worked out on the page at every redraw so removing tasks never leaves a gap), never part of the title; the edit modal's Task number field (with a Top button that types 1, on one line with the Tags field) sends `queueNumber` only when changed (`queueNumberChange`, clamped to the list length). A queued task's card is tinted by its due date (`dueClass`): pale red when overdue, amber when due within `DUE_SOON_DAYS` (2) days, today included, plain with no due date or a later one (`--card-soon-bg`, `--card-overdue-bg`; the tint holds while the card is swiped; the Active task box keeps its timer tint). Each task row also shows an Overdue chip when overdue, a project chip ("📁 Kitchen reno · 2", the name alone when unordered, nothing for an unknown project), a Repeats chip ("Weekly", "Every 2 weeks") when `recurrence` is set, a Snoozed chip ("Snoozed until Sun 25 Oct") while `snoozedUntil` is after today, its schedule (`scheduledStart`/`scheduledEnd`, formatted in the configured time zone) and a Locked chip when `locked`, and a timer chip once the timer has ever been started on it (▶️ while running, ⏸️ while paused, `timerChipIcon`); all are read-only. A task card has no buttons, so its title and chips use the full width; it takes gestures instead (one set of handlers on `#taskList` and `#activeTaskBox`, so the active task answers anywhere inside its bordered box, its label and padding included): a long press (`LONG_PRESS_MS` 500, a queued card then flashes for `FLASH_MS` 600 (`flashElapsed`; `applyFlash` re-applies it after the redraw the timer call causes; the active task never flashes, its box colour shows the change), cancelled when the finger drifts `PRESS_MOVE_PX` 10, `pressMoved`; a short vibration where supported; the long-press menu and text selection are suppressed) toggles the timer, and a tap opens the edit modal at once (there is no double-tap gesture, so completing by gesture is only possible on the active task). Every card, the active task's included (swipeable anywhere in its box), also swipes: it follows the finger (`swipeOffset`) over a coloured backdrop (`swipeRowHtml`: `--swipe-del`, `--swipe-snooze`, `--swipe-complete` and `--swipe-abort`), and once the drag is clearly sideways (`isHorizontalDrag`, `SWIPE_START_PX` 12, the row then has `touch-action: pan-y`) and released at least `SWIPE_COMMIT_PX` 90 across (`swipeAction`, which takes whether the card is the active task's), a queued card's left swipe asks `deletePrompt` and deletes on OK and its right swipe opens the snooze dialog, while the active task's left swipe asks `abortPrompt` and aborts on OK (`abortTask`: the timer stops, its tracked time, first-started time and active mark are erased and the task is a never-timed queued task again, with no undo) and its right swipe completes after the usual confirmation; a shorter drag snaps back, and the click that ends a swipe does nothing. Snooze is also reached from the edit modal.

## Edit modal

- A read-only job number line ("Job number 123", `jobNumberText`) sits under the title in this modal and in the completed task form, hidden for a task with none. The edit modal's due date field has a Clear button that empties it; saving then stores an empty `dueDate`. Its Repeats control (frequency, plus an interval when it repeats) is saved with the other fields as `recurrence`, null for "Does not repeat". Its Project select and Order number field (disabled and emptied without a project; empty means unordered) are saved with the other fields as `projectId` and `projectOrder`, but only once `getProjects` has answered, so a failed load never strips a task's project; a project the page does not know stays selectable as "Unknown project". Once `getProjects` has answered, the select's last choice is "＋ New project…" (`NEW_PROJECT`), which shows a name field (`#editNewProject`) and keeps the Order number field enabled; Save then sends the name as `newProject` (an empty name is a warning alert, nothing is sent) and the server creates the project in the same commit as the edit (a 400 for an unusable or taken name saves nothing), the response's `projects` replacing the page's list. Beside its Snooze button (which saves the edits, then opens the snooze dialog) sits one timer button, "▶️ Start" or "⏸️ Pause", with the task's tracked time next to it (`formatElapsed`, "7:05" or "1:02:09", ticking every second while the timer runs and the modal is open). The edit modal scrolls inside itself (`max-height: 90vh`, `overscroll-behavior: contain`) and locks the page behind it (`body.modal-open`) while open. In both edit modals (queued and completed) Materials, Travel (km) (`#editTravel`, `#ceTravel`: a number box, empty for none; `parseTravelText`, `travelBoxText`, sent as `travelKm`, null clearing it), Phone and Email (`#editPhone`, `#editEmail`, `#cePhone`, `#ceEmail`, one line each; `parseEmailText`, a bad email is a warning alert; sent as `phone` and `email`, an empty box removing it, and an empty box inherits its client's: the placeholder then reads "From client: 021 555 1234", `effectiveContact`, `contactPlaceholder`) and Description sit in an "Extra fields" collapsible (`#editExtraFields`, `#ceExtraFields`; closed each time a modal opens); above it, under the Project field, both modals show a row of Call, Text and Email buttons (`#editContactActions`, `#ceContactActions`, `refreshContact`, `contactLinks`: links `tel:`, `sms:` and `mailto:` with the task's title and job number as the subject, `phoneHref`, `smsHref`, `emailHref`) for the task's effective phone and email (its own when typed, else those of its project's client, each decided on its own; a button shows only when there is a detail for it, the row is hidden when there is none, and it follows the typed boxes and the chosen project); when the project's client has `useWhatsApp`, one "💬 WhatsApp" button (a `https://wa.me/<number>` link opening in a new window, `whatsappHref`, `whatsappNumber`: digits only, a leading + or 00 taken as written, a leading 0 replaced by `WHATSAPP_COUNTRY_CODE` 64) replaces Call and Text, whichever of the task and the client the number came from (`effectiveContact`'s `whatsApp`); the add card's manual fields have the same Travel (km) box (`#manualTravel`, between Materials and Description, cleared after each add and filled from a copied completed task) and Phone and Email boxes (`#manualPhone`, `#manualEmail`, after it, handled the same way). The queued edit modal has a Materials checklist (a checkbox, an editable text, an optional Cost box (an amount with at most two decimals, `parseCostText`; empty for none) and a remove button per row, plus an add field with its own cost box; the add card's list works the same way), saved with the other fields as `materials` (null when empty; a cost that is not an amount is an alert, `invalidMaterialCost`, and nothing is sent); a task row shows a chip while it has a list ("Waiting on materials (2 of 5 ready)" in orange while any is unchecked, "Materials ready" once all are). The edit modal's Description textarea (`#editDescription`, up to 2000 characters, below the Materials) is saved with the other fields as `description` (empty removes it), and a task row shows its description in muted text below its chips (`.task-description`), cut to three lines; the card also shows the latest comment (`.task-comment`, `commentLineHtml` from `commentLineView`: a chat icon, its time and "+N earlier" when there are more, then its text, cut to two lines); the model never sees it.

The edit modal also has a Comments group (`#editComments`, `#editCommentText`, `#editCommentAdd`; code under "Comments panel" in the page, shared with the History form by prefix `edit` or `ce` through `COMMENT_PANELS`): the timeline oldest first (`commentTimeline`: time on the owner's clock, the text, a delete control each) above a box and an Add button. Like photos, a comment is added at once through `addComment`, not on Save, and the task list it returns replaces the page's (`setTasks`); delete asks first (`deleteCommentPrompt`) and calls `deleteComment`. The id is made by `newRequestId` and kept for the same text (`commentIdFor`, `pendingComment`), so a retry after a lost reply cannot add twice. Text still in the box when Save, Snooze or Complete is pressed is added first (`postComment`; if that fails the action stops and the modal stays open). With no connection, or behind changes already waiting, an added or deleted comment is held and shown at once, an added one marked "Waiting to send" (offline-edits.md). Saving the form or choosing a Snooze date with no connection holds the change for later (offline-edits.md); materials, the project, its order number and the task number need a connection.

## Timer and rescheduling

- The edit modal button and the long press both call `toggleTimer`, which posts START or PAUSE (`abortTask` posts ABORT, through the same `sendTimerAction`) to `toggleTimer` and redraws from the response, leaving the form's unsaved edits alone; the page only displays the server's `trackedSeconds` and `timerStartedAt` (`elapsedSecondsOf`). `rescheduleTask` is called only after a snooze (`snoozeTask`), reporting in the schedule status line (an error is also shown in an alert, since that line is on the Settings page, out of sight from the list).

## Adding tasks

- The add card has an "Enter the details myself" checkbox that reveals every field of the edit modal in the same order (priority, estimated minutes, tags, due date, Repeats, Project with Order number, Materials, Description); with it ticked the Add button posts `{manual: {...}}` (the text field is the title) instead of `{input}`, so the model is not asked to parse anything (only to suggest tags when none were entered, see `addOrUpdateTask`), and the tags, due date, Repeats, Project, Materials and Description fields are cleared afterwards (priority and estimate stay) and the checkbox unticks itself, hiding the fields again. The Project select's last choice, \"＋ New project…\" (`NEW_PROJECT`), shows a name field (`#manualNewProject`) and keeps the Order number field enabled; Add then posts the name as `manual.newProject` (an empty name is an alert, nothing is sent), and the server creates the project in the same commit as the task (`withNewProject`), so a failed add leaves no project behind; it answers 400 for an unusable or taken name (nothing is added) and returns `project` and `projects`, which replace the page's project list. A \"Start immediately\" checkbox beside it adds `startNow: true` to the post (either mode) and is unticked again after each add. A free-text add posts `allowProposal: true` (`freeTextBody`); when the server answers `needsChoice`, nothing has been added and a dialog (`#proposalModal`, `openProposalModal`) shows the suggested project name and its steps (`proposalStepText`, \"Strip walls · 1h 30m · Indoor\") with Add as a project (posts `{acceptProposal}`, `proposalAcceptBody`; the response's `projects` replace the project list), Add as one task (posts `{apply: {changes: singleChanges}}`, `proposalDeclineBody`) and Close without adding. The text stays in the add field until a choice succeeds, `startNow` goes with whichever choice is made, and a failed call is an alert with the dialog left open (`answerProposal`, `finishAdd`). While the text field holds two or more characters, a live search of completed tasks lists up to 6 matches below those checkboxes (`#templateResults`, \"HIGH · 45 min · Outdoor\" under each title): `loadTemplates` fetches `getCompletedTemplates` on the first keystroke and keeps the list (dropped after a completion or undo), `templateMatches` filters it with the Queue search's `matchesSearch` and lists the most often completed first (`completedCount` descending, equal counts newest first). Tapping a match (`useTemplate`, `templateFormValues`) ticks \"Enter the details myself\" and fills the title and every field from the old entry: priority, estimate, tags, Repeats, Project with Order number (only for a project that still exists and once `getProjects` has answered), Materials (all unchecked, costs kept) and Description, but not the due date; the estimate is the job's rolling average (see `recentSeconds`), and the Add button then posts it as a manual entry carrying the template's history (`historyOf`), only while the title still matches the copied one (`historyForTitle`). Its Project select follows the project list and, like the modal's, is not sent until `getProjects` has answered.

## Removing, completing, Undo and Snooze

- After a delete or completion an Undo footnote (`#undoNote`, a `footer` after the pages styled as a sticky bar pinned to the bottom of the screen on every tab, with the Multi-Select bar lifted above it while it shows; text from `removalMessage`) offers `undoRemove`; it is one slot (`openUndoNote` with the handler the Undo button runs, `undoNoteKey` naming what it is about), also used for check-offs on the Materials page (frontend-materials.md) and for a Reorder move: it stays until the next removal, check-off or move replaces it, an Undo or a failed save clears it, or `UNDO_NOTE_MS` (the server's 10-minute window less 10 seconds) passes, and does not survive a reload; a task is deleted from the edit modal's Delete button or by a left swipe on its card (the cards have no buttons). Deleting and completing are optimistic (`removeTask`): the task leaves the page and the Undo footnote shows at once, the server call follows (one removal at a time, in order, so Undo waits for `removalChain`), and the server's list then replaces the page's (a repeating task's next occurrence appears then); `pendingRemovals` keeps the task out of any list that arrives meanwhile (`setTasks`, `withoutTasks`), and a failed call puts it back at its old place (`insertTaskAt`) with an alert. Completing a task, by a right swipe on the active task or from the edit modal, first asks "Mark \"title\" as complete?" (`completePrompt`; for a repeating task it adds that the next occurrence will be added); cancelling does nothing and leaves the edit modal open. Snooze opens a dialog (`#snoozeModal`) with Until tomorrow, Until next Monday (a week ahead on a Monday) and a date field (a day after today), plus Unsnooze while snoozed; a choice saves `snoozedUntil` through `updateTaskDirect` and, when the task has a calendar event, is not pinned and is not waiting on materials (`snoozeNeedsReschedule`), then calls `rescheduleTask` so the event moves at once, after a "Delete this task?" confirmation (cancelling leaves the modal open), and the footnote follows.
