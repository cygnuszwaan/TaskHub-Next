# Endpoints: tasks

The functions that read and change the active task list: add, update, batch, timer, Undo and complete. Every endpoint needs the owner's sign-in (see PROJECT.md).

| Function | Purpose | AI |
|---|---|---|
| `getTasks` | Read the active list; the response also holds `serverTime` (the server's clock in milliseconds), which `toggleTimer`, `completeTask`, `reopenCompletedTask`, `undoRemove` and `updateTaskDirect` also return | No |
| `addOrUpdateTask` | Free text in; Gemini returns only new or changed tasks (title, priority, dueDate, estimatedMinutes, tags, recurrence, rank), merged server-side; the rank counts only on a new task (inserted at that place in the queue, lowest rank first, clamped; the end when none) and is ignored on a change to an existing task, so the model can never reorder existing tasks; the prompt shows it the queue as 1..n. With a `manual` body `{title, priority?, dueDate?, estimatedMinutes?, tags?, recurrence?, projectId?, projectOrder?, materials?, description?, travelKm?, phone?, email?, url?, location?, history?, queueNumber?}` instead of `input` the model parses nothing: the task is added at the place `queueNumber` asks for (a whole number from 1, clamped to the end; `manualTaskChange` passes it on as the change's `order`, which only a new task honours); with no usable `queueNumber` the model picks the place (`buildPlacePrompt` and `placeSchema`: the queue as 1..n with titles, priorities, due dates and estimates, never descriptions or materials, and the task as entered; its integer `order` counts only from 1 up and is clamped like any other; a failure only logs and the task goes last), with the fields validated like the model's (an unusable one takes the new-task default; 400 without a title); `recurrence` is validated like the model's, `projectId` counts only for a project stored at commit time (with `projectOrder` through `applyProjectFields`) and `materials` goes through `normalizeMaterials`, `description` through `normalizeDescription`, `travelKm` through `normalizeTravelKm` and `location` through `normalizeLocation`, a new task only, as does `history` (`normalizeHistory`, the job history of a copied completed task). A manual entry with no usable tag gets tags from the model (title and the tags already on the list only, 1 to 3, cleaned by `cleanTags`; a failure only logs and the task is added untagged); the tag and place questions are asked at once, and an entry with a number and tags asks neither (so a copy of a completed task with no tags gets them too). Any body with `startNow: true` starts the timer of the first task it adds (the same effect as `toggleTimer` START, in the same transaction), making it the active task. Omitting `recurrence` leaves an existing task's unchanged; frequency NONE removes it. The model's changes never carry `projectId` or `projectOrder`: `withoutProjectFields` strips them from the model's output and from an `apply` list, and the prompt and response schema leave them out, so a free-text add never puts a task in a project, moves it or reorders it (a task joins a project only through a manual entry or an accepted suggestion), and the model cannot create, rename or delete projects, and its changes never read or change `materials` or `description` (only a manual entry sets them, on a new task) or `snoozedUntil`. A free-text body with `allowProposal: true` also lets the model suggest a project (`projectProposal`, asked for only then, checked by `normalizeProposal`: a step may carry `description`, the detail the input gives for it (asked for only where there is some, 2000 characters at most, stored on its task by an accepted project; the dialog shows them cut to two lines); dropped as a whole under 3 or over 12 usable steps, when its name matches an existing project (ignoring case), or when the input names an existing project (`namesProject`)); when one survives, nothing is committed and the response is `{success, needsChoice: true, proposal: {name, steps}, singleChanges}`, `singleChanges` being the model's ordinary changes. Without `allowProposal` the model is not asked and the behaviour is as described above. The owner's choice comes back without calling the model: `{acceptProposal: {name, steps}}` re-validates the suggestion with `normalizeProposal` against the projects stored at commit time (400 with the reason when it no longer passes, e.g. the name was taken meanwhile), then in one transaction creates the project and adds its steps at the end of the list, step n with that `projectId` and `projectOrder` n (`acceptProposalInList`), and responds `{success, tasks, added, updated, skipped, project, projects}`; `{apply: {changes}}` (the declined path: `singleChanges`, a list of at most 100 change objects, else 400) is merged by `mergeTaskChanges` like any model output. `startNow: true` works with both and starts the first task added. Every new task it adds, however added, takes the next job number in the same transaction (`jobCounter` passed to `mergeTaskChanges` and `acceptProposalInList`). A body may carry `requestId` (8 to 64 letters, digits, `-` and `_`; else 400): on a manual, free-text or `apply` body it is recorded in `settings/addRequests` with the add that used it, and a body with an id already there adds nothing and takes no job number, responding `{success, tasks, added: 0, updated: 0, skipped: 0, duplicate: true}` (a repeated free-text body may still call the model, and an add that changes nothing records no id; `acceptProposal` ignores it). Cannot delete or complete tasks | Yes |
| `updateTaskDirect` | UPDATE or DELETE one task by id; DELETE also removes its photos and calendar events. A DELETE's body may carry `at` (epoch milliseconds, `resolveActionTime`, as `toggleTimer`'s): when the owner deleted it, for a delete held offline, at which a running timer is stopped (so Undo restores the time accrued by then); a missing or unusable `at` counts as now and one more than 14 days old is a 400; the undo window still runs from the commit. A DELETE of a task already gone changes nothing and leaves the last removal kept for `undoRemove` alone. Responds with `serverTime` too. An UPDATE's `recurrence` is validated (null or frequency NONE removes it, an unusable value is ignored), and so are `projectId` (null or empty leaves the project, an id that is not a stored project is ignored; checked against the projects at commit time) and `projectOrder` (null clears it; ignored for a task outside a project), and `materials` (validated by `normalizeMaterials`: items without text are dropped, ids that are missing, invalid or repeated are regenerated, null or an empty list removes it, an unusable value is ignored) and `snoozedUntil` (validated by `normalizeSnooze`: a real YYYY-MM-DD date sets it, null or an empty string removes it, an unusable value is ignored) and `description` (validated by `normalizeDescription`: text is trimmed and cut to 2000 characters, null or blank text removes it, a non-string is ignored; `comments` is never changed here) and `travelKm` (validated by `normalizeTravelKm`: a number or plain decimal text is rounded to one decimal, null, empty text or 0 removes it, an unusable value is ignored) and `phone`, `email` and `url` (validated by `normalizePhone`, `normalizeEmail` and `normalizeUrl`: null or blank text removes it, an unusable value is ignored) and `location` (validated by `normalizeLocation`: null, blank text or an empty object removes it, an unusable value is ignored) and `queueNumber` (a whole number: moves the task to that place in the queue, clamped to 1..n, the others closing up and every `order` renumbered 1..n, `moveToQueueNumber`; `order` itself is never taken from an edit) | No |
| `batchUpdateTasks` | Body `{action, taskIds, ...}` (at most 500 ids; ids matching no task are ignored, 404 when none match) changes the named queued tasks in one transaction (`applyBatch`): `MOVE_TO_TOP` (they go to the top, keeping their relative queue order, every `order` renumbered 1..n), `SET_PROJECT` (`projectId` of a stored project, or null to take the tasks out of their project and drop their `projectOrder`; a task already in the project keeps its `projectOrder`, any other loses it), `SET_DUE` (`dueDate`, a real YYYY-MM-DD date; null or empty clears it to "") or `SNOOZE` (`snoozedUntil` as `updateTaskDirect` takes it; null or empty unsnoozes). After a `SNOOZE`, one `runScheduleEngine({taskIds})` moves the events of the tasks that have one, are not locked and are not waiting on materials (`needsReschedule`); a failure there keeps the snooze and sets `rescheduleError`. 400 with the reason for an unusable action, id list or value. Responds `{success, tasks, count, rescheduled, rescheduleError?}`. Completing and deleting several tasks are not here: the page calls `completeTask` and `updateTaskDirect` once per task | No |
| `toggleTimer` | Body `{taskId, action, capSeconds?}`, `action` being START, PAUSE or ABORT (400 for anything else, 404 for an unknown task); `capSeconds` (a whole number >= 0, else 400; counts for PAUSE only) counts at most that much of the running stretch, so a timer left on overnight can be paused without keeping the whole night (`pauseTimer`; a cap above the stretch changes nothing). Uses the server's clock: START records `timerStartedAt` (and `firstStartedAt` when the task has none), marks the task `active` and pauses every other running timer (so one runs at a time) and clears their `active`; PAUSE adds the running stretch to `trackedSeconds` and removes `timerStartedAt`, leaving `active`; ABORT instead removes `timerStartedAt`, `trackedSeconds`, `firstStartedAt` and `active` from that task alone, wiping its timing. Starting a running timer or pausing a paused one changes nothing. Responds `{tasks, serverTime}`. The body may carry `at` (epoch milliseconds, `resolveActionTime`): the instant the change was made on the device, which the server books in place of its own clock for a held offline change, clamped to now when it is in the future and a 400 when it is more than 14 days old; a missing or unusable `at` counts as now | No |
| `undoRemove` | Body optional (`requestId`, recorded when the undo goes through, so a repeat after a lost reply answers `{success, tasks, duplicate: true}` instead of 404). Undoes the last delete or completion if it was within 10 minutes (`undoInList`): the task returns with its own id, rank and fields, minus its timer if one was running (a delete pauses it first, a completion stops it), its `active` mark and its schedule fields unless it is `locked` (its calendar event was deleted with it, so the next run books it again); a completion's archive entry (with its photos) and the next occurrence it created are removed (the job number that occurrence took is not given back). One step only, since only the last removal is kept. Responds `{tasks, kind, restored, serverTime}`; 404 when there is nothing (or nothing recent) to undo | No |
| `completeTask` | Archive to `completed_tasks` (a running timer is stopped first, so the row's `trackedSeconds` holds everything accrued), remove from the list, remove its calendar events. A recurring task also gets its next occurrence in the same transaction (`completeInList`), with the next job number: same title, priority, tags, recurrence, project and order number, the job's history and an estimate that is the rolling average of the tracked times (this completion's included; the completed task's own estimate while no instance has any tracked time), materials (all unchecked, with new ids) and description, the completed task's rank, PENDING, no schedule, snoozed until its new due date (`snoozedUntil` equals `dueDate`, so it is not scheduled before it is due) and a `dueDate` stepped forward from the old one in whole intervals until it is after today in the configured time zone (finishing early keeps the rhythm, finishing late skips missed occurrences; no due date counts from today; month ends clamp without drifting). The body may carry `at` (as `toggleTimer`'s: the timer stops, `completedAt`, the local day that steps a repeating task's due date and the next occurrence's `addedAt` all use it; the undo record's time stays the server's own), `archiveId` (8 to 64 letters, digits, `-` and `_`, `normalizeArchiveId`: the archive row is created under it, a 400 when it is already a row) and `requestId` (recorded in `settings/addRequests` in the same transaction; a repeat answers `{success, tasks, spawned: null, duplicate: true}`). The response includes `spawned` (the new task or null) and `serverTime` | No |

Every write to `tasks` is a Firestore transaction (via `updateTaskList` in `store.js`: it reads the whole collection, runs the modification, and writes only the tasks that changed or were removed). `addOrUpdateTask` calls Gemini outside the transaction and merges its changes into the list as stored at commit time: a change naming a task that no longer exists is skipped, and id, status, calendar and schedule fields, and `locked` are never taken from the model, nor are `projectId` and `projectOrder`; a manual entry's or an accepted suggestion's project fields count only for a project stored at commit time (the transaction reads `projects` too, and `clients` for a new project's client), applied through `applyProjectFields`. `completeTask` commits the archive write and the list removal together. Calendar cleanup runs after the commit.

Deleting or completing a task removes its calendar events by stored `googleCalendarEventId` and by the `taskId` private extended property on the event, so a task whose stored id was lost still gets cleaned up.
