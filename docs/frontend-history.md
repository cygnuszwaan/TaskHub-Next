# Frontend: History page

History: Stats, project hours, job sheets, the completed list, the completed entry's form and photos.

## History page, completed entries and photos

- The History page (the tab id is `history`; not to be confused with a job's `history`, the completion history a template carries) shows the recently completed tasks: it loads `getCompletedTasks` each time the tab is opened, read-only; each completed row's time chip is its tracked time (`completedTimeText`: "25m", "45s"), or its estimate marked "est." when no time was tracked on it (never timed, or archived before time tracking began); above the list a collapsible Stats card (`#statsDetails`, a `settings-card` like the Settings cards, collapsed by default, its open state left alone when the lists reload, hidden while there are no completions or the load failed) holds the summary (total completed and tracked time (`totalMinutes`), a streak line ("Current streak: 3 days · Longest: 9 days", a "+" after a number whose run reaches the window's first day, `streakText`), a per-week bar list, priority, tag and project chips, the project chips being "📁 Garden 2 · 45m" with the tasks of deleted projects together as "Deleted project", `statProjectName`, and a "Most completed jobs" list of the first 10 `byJob` entries, a title with "6 in 8 wks · 24 total · avg 45m · est. 40m" under it, `jobStatsText`). Below the Stats card (the project hours and the completed list have no card heading of their own) a "Project" section is a timesheet and the project filter of the completed list: a project field (`#historyProjectField`, a `.picker-field` button showing the project's name, or "Any project" which is where it starts; the choice is kept across reloads of the list while that project still exists, `pickHistoryProject`) that opens the picker modal (`openHistoryProjectPicker`, kind `hours`: search by project name, "Any project" as the top row while the search is blank, only projects with completed work, newest week first, the muted text at the row's right the project's total hours, no Add row; a pick calls `selectHistoryProject`, which redraws what is under the field, returns the list to page 1 and redraws it; `historyProjectChoices`). With Any project nothing is shown under the field and the completed list is unfiltered; with a project chosen the list shows only that project's tasks (`completedBrowse`'s `filters.projectId`, combined with the search; `historyProjectFilter`, which is "" while the section is not on screen, so the saved copy, which has no Project section, and an empty or failed load apply no project filter) and under the field are its total, "3h 20m (3.33 h) · 30m est. · 4 tasks" (the `est.` part comes from tasks whose timer was never started), and every Monday-to-Sunday week it has work in, newest first (`hoursText`, `projectWeekText`, `weekRangeText`, `pickHistoryProject`). It covers all time and only the current projects. A "📄 Job sheet, project to date" button under the project's total and a 📄 button on each week row download that project's job sheet, and the completed task's edit form has a 📄 Download job sheet button (the last item of its Audit trail section) for that task's (`downloadProjectSheet`, `downloadTaskSheet`, then `downloadJobSheet`, which posts to `getJobSheet` through `apiFetch` and saves the PDF from a Blob; the file is named by `jobSheetFilename`, e.g. `jobsheet-kitchen-reno-week-2026-10-19.pdf`; the button shows "…" meanwhile and a failure is an alert). A completed entry is a card with no buttons of its own: tapping it (or Enter or Space on it, `data-completed-open`) opens a form (`openCompletedEditor`) for the correctable fields (priority and time spent in minutes sharing the first line, with no estimate box since a repeating job's estimate comes from the average of its tracked times; Materials as a textarea with one item per line, a trailing `| 12.50` giving an item's cost (`parseMaterialItems`, `materialLine`, `completedMaterialLines`), the completion on the owner's clock) with a Delete button behind a confirmation and a Reopen button (`reopenCompletedEntry`: after `reopenPrompt`'s confirmation it saves any edits made in the form, then posts `{id, requestId}` to `reopenCompletedTask`, puts the returned queue on the page, drops the cached templates, closes the form and reloads the History lists; without a connection it holds the reopen, see `offline-edits.md`; Save is held the same way for the fields `ENTRY_EDIT_FIELDS` names, and a completion still waiting to be sent opens the form with only those fields enabled); the form sends only the fields that changed (`completedChanges`, `completedFormValues`, `completedMaterialTexts`, `parseMaterialLines`), and the History lists reload afterwards. The list below the project hours is the newest 1000 completed tasks (`COMPLETED_FETCH_LIMIT`, loaded with the rest of History), 50 to a page (`COMPLETED_PAGE_SIZE`), under a live search box with a Clear button (`#completedSearch`): every word typed must appear in a task's title (`matchesCompletedSearch`, which is the Queue's `matchesSearch`; tags, materials, description, comments and the project name are not searched: tags and the project have their own filters), except that a word of the form `#123` matches only the task whose job number is 123 (leading zeros ignored, a bare `#` ignored) and a word of the form `@smith` must appear in the name of the client of the task's project (`projectClientNameById`; ignoring case, part of a word is enough, every `@` word must be in that name so "Smith Ltd" is `@smith @ltd`, a task with no project or client never matches one, a bare `@` ignored; `jobNumberWords` splits the words), and the placeholder says `#job` and `@client` can be used, any change of the text returns to page 1. Under the search row a collapsible Tags section (`#completedTagsDetails`, the Queue's `.filter-section` markup, collapsed by default, hidden while no loaded task has a tag, the chosen tags in its heading `#completedTagsActive` via `tagFilterLabel`) holds an All chip and one chip per tag on the loaded completed tasks with its count, alphabetical (`tagChipItems`, `sortedTags`; `renderCompletedTagBar`): a tap toggles that tag (`setCompletedTagFilter`, `toggleTagFilter`; any of the chosen tags matches, OR), All clears, and a change returns the list to page 1. The chosen tags (`completedTagFilters`, `completedBrowse`'s `filters.tags`) combine with the search and the project, survive reloads of the list and edits (`pruneTagFilter` drops a tag no loaded task carries) and work from the saved copy offline. A count line says what is shown (`completedCountText`: a search, the project or a tag makes it "Showing 1–12 of 12 matches (312 completed tasks)", or "No completed tasks match the search and filter."; a note when older entries exist than were loaded). Page links (Previous, numbers, Next, `pagerItems`) sit above and below the list; the search text and the page survive the reload after an edit. Entries older than the newest 1000 cannot be reached. The form holds the entry's comments too (`#ceComments`, `#ceCommentText`, `#ceCommentAdd`, the same panel as the edit modal's with prefix `ce`): added and deleted at once through `addComment` and `deleteComment` with `{archiveId}`, the reply patched into `completedServer` and the saved copy (`applyCommentResult`) without reloading the lists; text left in the box is added when Save or Reopen is pressed; with no connection, or on an entry whose completion is still waiting, an added or deleted comment is held (`offline-edits.md`; `COMPLETED_FORM_CONTROLS` maps the box and Add to `comments`, enabled offline). An entry shows its latest comment under its description (`.completed-comment`, as on a card). The form also holds the entry's photo panel (`#cePhotos`, `photoPanels` by archive id, dropped when the form closes; the edit modal of a task in the queue has the same panel, `#editPhotos`, keyed by task id and posting `{taskId}` instead of `{archiveId}`, made by `showPhotos(key, field, boxId)`; its photos are saved at once, not with Save, and move to the archive row when the task is completed): `getCompletedPhotos` is called when the form opens, through `apiFetch`, never with the list, and the panel shows "1 of 3 photos" (`photoCountText`), 72 px thumbnails and an Add photo button while there are fewer than `MAX_PHOTOS`. Add photo opens one shared file input (`#photoInput`, `accept="image/*"`, so the browser offers camera and gallery); `shrinkPhoto` draws the picture on a canvas (EXIF orientation applied by the browser when it decodes it) at 1280 px on its longest side as JPEG at 0.7, retrying plainer and smaller versions (`photoAttempts`, `photoTargetSize`) until it is within `PHOTO_MAX_BYTES` (300 KB), and posts it to `addCompletedPhoto` as base64 (`base64FromDataUrl`); a failure is an alert. Tapping a thumbnail opens the viewer (`#photoModal`, above either form) with the full-size picture, Close and Delete (a confirmation, then `deleteCompletedPhoto`).
