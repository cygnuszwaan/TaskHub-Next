# Offline: held edits, Reopen and comments

How the page holds the changes made in forms and on the Materials page without a connection (or behind changes already waiting) and sends them in order, on the action queue in `offline.md`.

- Reopen (page): `reopenCompletedEntry` confirms (`reopenPrompt`), then fixes a `requestId` and tries the calls as online (the form's unsaved edits to `updateCompletedTask`, then `{id, requestId}` to `reopenCompletedTask`). On a connection failure it calls `queueReopen` with the fields not yet saved, and at once, with `behind`, while any action is PENDING or a drain runs. `queueReopen` keeps an EDIT of the changed fields `ENTRY_EDIT_FIELDS` holds (when the form changed any) and then a REOPEN (`taskId` the entry's own `id`, `archiveId` the entry's), refusing with an alert that names the other changed fields (`splitHeldFields`, `fieldNamesText`: they need a connection) or when the queue has no room; it then closes the form and shows the result (`refreshShownTasks`): the entry leaves History and the task joins the end of the Queue as `reopenTask` builds it. `shownTasks` replays over `replayEntries` (the page's History entries, else the saved copy's, read only while a REOPEN waits) because a REOPEN finds its entry there, so the task shows on a cold start before History has been opened. `sendQueuedAction` posts a REOPEN's `reopenBody` to `reopenCompletedTask` and an entry EDIT's `entryEditBody` to `updateCompletedTask`. A completion that is still waiting is not reopened but taken back (`takeBackWaitingCompletion`, `takeBackCompletion`): its COMPLETE leaves the queue with the actions that depend on it, and a timer that was running is paused at the completion's `at` (a TIMER PAUSE action), so the task is back stopped with its accrued time and nothing is sent. Reopen has no Undo; discarding a waiting REOPEN (`cancelActions`) also drops later actions on its task but leaves the entry's EDIT, which has its own card.

- Held task edits (page): `saveTaskEdits` closes the form and posts as online; on a connection failure (`isNetworkError`), or before posting while any action is PENDING or a drain runs, `holdTaskEdit` keeps one EDIT of the fields that differ from the task shown (`taskEditChanges`, so an untouched field is never sent and an edit made on another device meanwhile is overwritten only in the fields changed here): title, priority, estimatedMinutes, tags, dueDate, recurrence, travelKm, phone, email, url, location and description. `checkEditFields` cleans each value as the server stores it (`normalizeSnooze`, `normalizeTravelKm`, `normalizePhone`, `normalizeEmail`, `normalizeUrl`, `normalizeLocation`, `normalizeRecurrence`, `normalizeMaterials` and `normalizeMaterialCost` are page copies of the server's, held equal by `actionQueue.test.js`, as is `applyEditFields` against `applyDirectUpdate`) and names an unusable value in an alert. A changed materials list is held whole (`taskEditChanges` compares texts, ticks and costs, never ids); `holdTaskEdit` first gives every new row an id of its own (`withMaterialIds`, `newRequestId`), which the server keeps, so the shown list and the sent one agree and a repeat after a lost reply changes nothing more; the list is as the form shows it, so it replaces the task's list on the server, as an online save does. A change to the project, its order number or the task number (`serverOnlyEditChanges`) is refused with an alert that names it and nothing is kept; the form comes back (`reopenEditForm`) when the refusal follows a failed post. Snooze (`snoozeTask`) holds the same way through `holdSnooze`: an EDIT of `snoozedUntil` (null unsnoozes). `sendQueuedAction` posts a task EDIT's `taskEditBody` (`updateTaskDirect` UPDATE of the held fields) and, after a held snooze is saved, runs `rescheduleTask` when `snoozeNeedsReschedule` says the task has an event to move. The cards show the change at once (`withPendingActions`) and the action card's label names the fields (`actionLabel`).

- Held entry edits (page): `saveCompletedEdit` posts as online; on a connection failure (`isNetworkError`), or before posting while any action is PENDING or a drain runs, or when the entry is a completion still waiting to be sent (`waitingRequestId`), `holdEntryEdit` keeps one EDIT of the changed fields (`completedChanges`, so only what differs from the entry shown) and closes the form; the entry shows the change at once and the card names the fields (`actionLabel`). A change to materials, the project or the completion time (`splitHeldFields`' other fields: they need ids or the zone the server holds) is refused with an alert that names it, nothing is kept and the form stays open. A waiting entry opens (`openCompletedEditor`, `completedFormLimited`) with only the held fields enabled and its photos, comments, job sheet and Delete disabled; its EDIT is sent after its COMPLETE and goes with it when the completion is discarded or taken back (`actionDependsOn`). `checkEditFields` cleans an entry's tags (`cleanEntryTags`) and time (`MAX_TRACKED_SECONDS`) as `applyCompletedEdit` does.

- Held comments (page): `postComment` posts as online; on a connection failure (`isNetworkError`), or before posting while any action is PENDING or a drain runs, or when the entry is a completion still waiting to be sent, `holdComment` keeps a COMMENT with the comment's own id (the one `commentIdFor` fixed, so a repeat adds nothing), its trimmed text and `at` (device clock plus `clockOffsetMs`, the time it was written, not the time it arrives), then clears the box and returns true, so a Save, Snooze or Complete that added it first goes on. The task card, the entry and the timeline show it at once (`withPendingActions`, `addCommentToList`) marked "Waiting to send" (`waitingCommentIds`); a task with a waiting COMMENT shows the waiting chip. A comment on a waiting entry is sent after its COMPLETE and goes with it when the completion is discarded or taken back; one on a task follows any REOPEN of it. `sendQueuedAction` posts `commentBody` to `addComment`; a server answer marks the action FAILED with its text (a comment more than 14 days old is refused), and the reply patches an open form (`applyCommentResult`, only for an entry the page holds). A full queue or unusable storage refuses with an alert and the text stays in the box. Deleting a comment (`deleteComment`) asks first, then: a comment still waiting in the queue is taken out of it and nothing is sent (unless its COMMENT is on its way, when the deletion goes behind it); otherwise the call is made as online and held as a COMMENT_DELETE (`holdCommentAction`, fields `{id}`) after a connection failure, behind waiting changes, or on an entry whose completion is waiting. The comment leaves the timeline, card and entry at once (`removeCommentFromList`, against the server's `removeComment`); `sendQueuedAction` posts `commentDeleteBody` to `deleteComment`, where a comment already gone is a harmless repeat. Its delete controls are never disabled.

- Held Miscellaneous changes (page): an add or a tick on the Materials page's Miscellaneous list is shown at once and saved through `queueShopping` as online (one after another on `shoppingChain`, the change as `{kind, requestId, fields}`); on a connection failure (`isNetworkError`), or when a shopping action is already PENDING in the queue (`hasPendingShopping`, checked before any send, so the order holds), `holdShoppingChange` keeps it as a SHOPPING_ADD (`{text}`) or SHOPPING_REMOVE (`{id, text}`) and it stays shown; any other failure takes it back as online. An add is shown under `shoppingTempId(requestId)` ("pending-" and its request id), so it keeps its id across a reload. `withPendingShopping` puts the PENDING shopping actions on top of the server's list (`serverShopping`, or the saved copy's) in `shownShopping`, applied when a list arrives and on load, with the same rules as the server's add (`shoppingWithAdded`; a text already there, ignoring case, is not added again, so a repeat after a lost reply adds nothing) and removal (a removal naming a temporary id also finds the item by its text once the server has saved it); a held add shows a "Waiting to send" chip (`waitingShoppingIds`). Ticking an item whose add is still waiting (`checkShoppingItem`) takes the add out of the queue (`cancelActions`) and sends nothing; a removal behind an add depends on it (`actionDependsOn`), so discarding the add takes both. `sendQueuedAction` hands a shopping action to `sendShoppingAction`, which posts `shoppingBody` to `updateShoppingList`; a removal's id is `shoppingRemovalId` (its own, the one learned when the add was sent, else the item of the same text on the list read first, and nothing is sent when it is not there). The server's list then replaces the page's with what still waits on top (`setShoppingFromServer`); a refused, discarded or retried action shows the list again (`refreshShownShopping`).

- Held Multi-Select changes (page): `batchSend` (To top, Snooze, Due date, Project) first closes the dialog (Project has none, its picker having closed), then posts as online; before posting while any action is PENDING or a drain runs, or after a connection failure (`isNetworkError`), `holdBatch` keeps one BATCH action: `fields` `{action, taskIds, projectId | dueDate | snoozedUntil}` (`MOVE_TO_TOP`, `SET_PROJECT`, `SET_DUE`, `SNOOZE`, the value as `batchUpdateTasks` takes it, a date cleared as null), `title` the project's name for `SET_PROJECT` (`projectId` null, None, has no title and reads "Take 2 tasks out of their project"), `taskIds` the selected tasks still on the list. It keeps Multi-Select and the selection, shows the change at once (`withPendingActions`, `batchInList`, a copy of the server's `applyBatch` held equal by `actionQueue.test.js`: a task already in the project keeps its order number, any other loses it, and a null `projectId` removes project and order number; `MOVE_TO_TOP` renumbers every `order`), notes "Waiting to send" in `#batchStatus` and marks every task it names with the waiting chip (`waitingTaskIds`). A new project is refused with an alert (`newProject` needs the server) and so is a selection holding a task a waiting Reopen brought back (`unheldBatchId`: it is shown under a temporary id), or a full queue; the selection and Multi-Select stay. The card says what it does (`actionLabel`: "Move 3 tasks to the top", "Snooze 3 tasks until 2026-11-09"), no other action depends on a BATCH and it depends on none. `sendQueuedAction` posts `batchActionBody` to `batchUpdateTasks`, which also moves the calendar events after a snooze; a server answer, "No matching tasks" when every task is gone included, marks the action FAILED with its text, and ids the server no longer has are otherwise ignored.
