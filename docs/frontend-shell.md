# Frontend: page shell

The one-page app's shell: installable app and sharing, dark mode, service worker, API calls, sign-in, tabs and the page's own dialogs.

## PWA, manifest and sharing

- Frontend: one page, `public/index.html`, vanilla HTML/CSS/JS, no build step, installable as a standalone Android app (PWA): `public/manifest.webmanifest` (standalone, no `theme_color`, dark `background_color`, start `/`), `public/icons/` (192, 512, maskable 512 and the Apple touch icon, a white tick on blue) and `public/sw.js`, registered by the page. The manifest's `share_target` (GET to `/` with `title`, `text` and `url`; Hosting's rewrite serves the page, so the worker needs no route) makes TaskHub appear in Android's share sheet once the app is (re)installed: at load `captureShare` keeps `sharedText` (the text, else the title, plus the link unless the text holds it, one line, at most 2000 characters) in `sessionStorage` (`taskhub-share`, so a redirect sign-in keeps it) and cleans the address; after sign-in `applyPendingShare` opens the Queue tab and puts it in the add field for the owner to review, adding nothing.

## Dark mode

- The page follows the device's light or dark setting until the owner uses the Dark mode checkbox (an Appearance card under the settings card on the Settings page, outside the saved form): it applies at once and is kept in `localStorage` (`taskhub-theme`, "light" or "dark", per device, never sent to the server). A saved choice sets `data-theme` on `<html>` (an inline script in the head does it before the first paint; `applyTheme` handles the rest), which overrides the device query; with none saved the checkbox shows the device's state and follows it when it changes. Every colour is a CSS variable on `:root` with its dark value in two identical blocks, under `@media (prefers-color-scheme: dark)` for `:root:not([data-theme="light"])` and for `:root[data-theme="dark"]`; `color-scheme` lets the browser draw dark form controls, and two `theme-color` metas (`data-scheme` light and dark) colour the browser UI, their `media` rewritten by `applyTheme` to match a choice (Android paints an installed app's bottom navigation bar from the manifest, which cannot follow the device's scheme, so the manifest has a dark `background_color` and no `theme_color`: the navigation bar and install splash are dark in both modes and the status bar follows the metas). A new colour needs a variable with a dark value in both blocks; `darkmode.test.js` fails on a hex colour outside the variable blocks and on blocks that differ.

## Service worker

- The worker caches only the shell files in its `SHELL` list (`/index.html` and the manifest and two icons), same-origin GETs only, network first with the cache as the offline fallback; it never touches the functions, Firebase Auth's `/__/` pages or any other origin, so task data is never cached; it also shows push messages and handles taps on them (see Push notifications in infrastructure.md). Bump `CACHE` in `sw.js` when `SHELL` changes.

## Page code, API calls and escaping

- Calls the functions over HTTPS; the functions base URL, SDK URL, optional Web Push key, Places API key and Places region live in one `CONFIG` block at the top of the script. `apiFetch` throws the server's error text on any non-OK response, so a failed call never replaces the task list. All task-derived text goes through `esc()` before `innerHTML`; list and filter clicks use event delegation on `data-` attributes.

## Sign-in

- The page is gated behind Google sign-in (Firebase Auth, JS SDK 12.18.0 from gstatic via dynamic `import()`, web config from Hosting's `/__/firebase/init.json`); sign-in uses `signInWithPopup` and, when that fails with a code in `REDIRECT_SIGN_IN_CODES` (`needsRedirectSignIn`: popup blocked or unsupported here), `signInWithRedirect`, whose result `getRedirectResult` completes on the next load (a failure shows on the sign-in screen through `noteGate`); `apiFetch` adds the ID token to every call, and a 401 or 403 signs out and returns to the sign-in screen (the page has no Sign out button).

## Tabs

- A pinned header holds only four tabs at the top of the page, flush with its top edge (the body has no top margin, so the header looks the same scrolled or not; no title, no Sign out button), Queue, Materials (with the count of materials to get), History and Settings, sized to their text at 13px so they fit one row; each tab is a page and only one shows at a time (`showTab`, `normalizeTab`; Queue first, and an unknown name falls back to it; the tab ids are `queue`, `materials`, `history` and `settings`).

## Overlays and the Back button

- Every modal and dialog (`#editModal`, `#completedEditModal`, `#photoModal`, `#snoozeModal`, `#batchModal`, `#proposalModal`, `#pickerModal`, `#confirmModal`) is a layer: it is shown with `showLayer(id, onBack)` and hidden with `hideLayer(id)`, never by setting its `display` or `body.modal-open` directly. `layerStack` (`createLayerStack`, in the page's pure-helpers block) keeps the list of open layers, locks the page (`body.modal-open`) while any is open and keeps the browser history one entry deeper per open layer, so Android's Back button or gesture takes an entry away instead of minimising the app. With no layer open Back leaves the app as usual.
- `onBack` is what Back does to that layer, the same close as its Cancel button (`closePhotoViewer`, `closeSnoozeModal`, `closeBatchModal`, `closeProposalModal`, `closePicker`; a question or alert answers as dismissed, `settleConfirm(false)`). The two edit forms use `backFromEditModal` and `backFromCompletedEditor`, which run their Cancel close at once when nothing has changed and otherwise ask Save, Discard or Keep editing (frontend-edit-modal.md). Back reaches only the topmost layer, so a dialog over a form closes alone and the form keeps what was typed. A close that refuses (`closeProposalModal` while busy) or first asks a question (the edit forms) leaves the layer open and the entry is put back.
- The history entries are anonymous counters, each with the state `{ taskhubLayers: depth }` (`layerStateOf`, `layerDepthOf`): the page's own entry has none. History changes are made one timer tick after the layers change (`layerHistoryStep`), so closing one overlay and opening another at once changes nothing, and a `popstate` that lands on the depth the page's own `history.go()` was heading for is not taken as Back (`layerPopStep`); a `go()` that has not landed after a second is given up. A forward entry with no layer open, or a reload that kept an old entry's state, is gone back over at once. Android hides the keyboard on the first Back before the page is told, so Back may take two presses while typing.

## Dialogs: the picker

- The picker sits at the top of the visible screen, not the middle, so the on-screen keyboard leaves its list in view: `#pickerModal` aligns its card to the top and, while open, takes the top and height of `window.visualViewport` (`pickerViewportBox`, `fitPickerToViewport`, on its resize and scroll); the card is a column whose list scrolls inside it, the title, search bar and Cancel staying put.
- `#pickerModal` is one list-and-search dialog for choosing a project or a client (and for the Queue's project filter), a layer above the edit forms that open it and under the question dialog. `openPicker(kind, current, onPick, options)` takes the kind (`PICKER_KINDS`: the title, search label and placeholder, and the lines for an empty list, a search with no match and the Add row), the id now chosen (its row is marked), a callback and `options` (`opener`, which gets the focus back on closing; `allowAdd`, default true (the History Project picker, kind `hours`, and History's Multi-Select Project pass false); `title`, replacing the kind's title; `noneLabel`, a leading row with id "" labelled so (the Project fields and both Multi-Select Project buttons use "None", the Client field of a project "No client", the History Project picker and the Queue's "All"), shown only while the search is blank and marked when `current` is empty, `withNoneRow`; `noneDetail`, the muted text at that row's right; `onAdd`, which shows an Add button beside the search bar, see below). The callback runs after the modal has closed, with `{id}` for a row or `{name}` for the Add row; Back, Cancel, a tap outside and Escape close it unchosen.
- It opens with an empty search bar, focused, and the list already shown. `pickerRows(kind, query, items, context)` (pure) makes the list: at most `PICKER_MAX_ROWS` (8) rows, most used first (projects by queued tasks, `projectTaskCounts`; clients by their projects) and equal use in name order, with a "Keep typing to narrow" line when more match. Projects match with `filterProjects` (name or client's name, the client muted at the row's right); clients match when every word of the query is in the name. Kind `hours` (the History Project filter) takes rows already shaped `{id, name, detail}` (`historyProjectChoices`: newest week first, the detail the project's total hours), keeps their order, matches every word of the query in the name and has no Add row. An Add row ("＋ Add “Name” as a new project") shows while the text is not empty and no name equals it, case and blank runs ignored as the server's `hasName` reads it, over all items, not only the rows shown. Kind `queue` (the Queue's Project field, frontend-queue.md) takes the stored projects, lists every one that matches by `filterProjects` in the order given, uncapped, with its queued task count and client at the right (`2 · Smith Ltd`), and has no Add row: it passes `onAdd` instead, which shows an Add button (`#pickerAddBtn`) beside the search bar. Add (the button, or Enter when no row or Add row can be picked) calls `addFromPicker`, which hands the trimmed text to `onAdd` and, when that returns the id of what it made, marks that row, empties the search bar and redraws the whole list, leaving the modal open; a blank text focuses the search bar and sends nothing, and a refusal keeps the text. Results of the Add show in the modal's status line (`#pickerStatus`, empty and hidden otherwise, cleared on typing, on opening and on closing). A list with only its leading row and no items shows that kind's empty line under it. Kind `queue` also holds two collapsible sections, Manage and Start from template (`#pickerManage`, `#pickerTemplates`, frontend-queue.md), in that order between the status line and Cancel; each has the card's `max-height`, so it scrolls inside the card. A picker opened while another is open (the client picker over the Queue's modal) takes the same dialog and layer: `openPicker` keeps the one underneath in `pickerParents` with its search text, and closing the new one (a pick, Cancel, Back, Escape or a tap outside) brings the other back, as it was, with the focus on the button that opened the new one; Back reaches the nearest picker first and the layer closes only when none is left.
- The search bar is a plain text field and the list (`#pickerList`) is a `.project-list` (notes use `.project-list-empty`). Rows are `.project-item` rows, the same size as the Queue filter's, tapped or chosen with ArrowUp and ArrowDown (`aria-activedescendant`) and Enter, which picks the highlighted row, the first at each keystroke, or the Add row when nothing matches. The search bar has the combobox role, the list the listbox role and the rows option; all text is set escaped. The Project field's use of it is in frontend-edit-modal.md, the Client field's under a new project in frontend-tasks.md.

## Dialogs: questions

- Every "are you sure" question uses the page's own dialog, never the browser's `confirm()`: `askConfirm(text, {tone, confirmLabel})` (`#confirmModal`, a layer above every other modal, z-index 1100) resolves true on the confirm button and false on Cancel, a tap outside the card, Escape or a newer question. `confirmView` (pure) takes the first paragraph of the prompt text as the title and later paragraphs as detail (a paragraph starting with a bullet is shown as a list), so every prompt helper separates its question from its detail with a blank line. `tone` is `danger`, `warning`, `success`, `info`, `edit`, `save` or `error` and sets the icon and the confirm button's colour; `danger` and `warning` open with Cancel focused. The owner's text is set as text, never markup. The swipe handler awaits the answer while the card stays pulled aside.

## Dialogs: choices

- A question with buttons of its own uses the same dialog: `askChoice(text, {tone, choices})` takes 2 to 4 `choices` (`{id, label, kind, focus}`; `kind` is `primary`, `danger` or plain; `confirmView` drops entries without a text id or label and repeated ids, and `askChoice` asks nothing when fewer than two remain). They show as stacked buttons in place of Cancel and OK, the first with `focus` focused, labels set as text, and Tab stays among them. It resolves with the chosen id, or null for Back, a tap outside the card, Escape or a newer question.

## Dialogs: names

- Asking for a name (rename project, save as template, rename template) uses the same dialog with a text field, never the browser's `prompt()`: `askInput(text, {tone, confirmLabel, value, placeholder, maxLength})` resolves with the trimmed text (null on any way of cancelling), starts with the text selected, limits it to 100 characters unless told otherwise and keeps the confirm button off while the field is blank; Enter in the field confirms.

## Dialogs: messages

- Messages use the same dialog with one button, never the browser's `alert()`: `askAlert(text, {tone, confirmLabel})` resolves with nothing once dismissed (the button, a tap outside the card or Escape), has no Cancel and no text field and opens with its button focused; a value the owner must fix is a `warning` alert (a validation message), a failed call an `error` alert whose title is what failed and whose detail is the server's error text (`failureText(what, err)`). An alert never cancels another dialog: it waits until the one in front is closed, and several alerts show one after another (`alertQueue`, `pumpAlerts`); code that goes on to focus the field a message is about awaits it first.
- A passing message that needs no answer is a toast, not a dialog: `showToast(text)` fills `#toast`, a rounded bubble fixed over the bottom of the page (coloured from `--text-strong` and `--surface`, so it suits light and dark; above the Undo footnote while that shows; never taking a tap or any layout space) that goes after `TOAST_MS` 4000 or at `hideToast`. It is one slot: a new toast replaces the last and restarts the clock. The reorder hold's hint is its only use so far (frontend-queue.md).
