# Offline

How the page works without a connection: the add queue, the saved task and completed lists, the action queue, held completions and Undo. Held edits, Reopen and comments are in `offline-edits.md`. The plan for the remaining offline changes is the roadmap in PROJECT.md.

- Offline adds: an add that fails because of the connection (`submitTask`'s catch: `isNetworkError` and a body that was built) is kept on the device by `queueFailedAdd`, shown on the Queue as waiting, and sent once the connection returns, once each and in order. Every add carries a `requestId` made before its first attempt (`newRequestId`) and a kept add reuses it, so one the server saved before the reply was lost is not added twice. The add card then clears as after a sent add (`resetAddForm`); a full queue (`ADD_QUEUE_MAX`, 50) or unusable storage refuses with an alert (`addQueueRefusal`) and the card keeps its text. Nothing retries on a timer: a kept add waits for the triggers below. Free-text and manual adds both queue; a queued add never starts a timer (`startNow` is dropped) and a queued free-text add is sent without `allowProposal`, so it never opens the project dialog. The queue model is in the page's pure-helpers block (`makeQueuedAdd`, `parseQueue`, `serializeQueue`, `isNetworkError`, `drainQueue`; their comments give the item shape and contracts). The page keeps the queue in `localStorage` (`ADD_QUEUE_KEY`, every access in try/catch; unavailable storage sets `addQueueUsable` false) and draws it at the top of the Queue, above the Active task, even before the task list loads (`renderAddQueue`: one card per item showing `queueCardView`, "Waiting to send" or the error, with Discard after a confirmation, `queueDiscardPrompt` and `queueWithout`). `drainAddQueue` sends the waiting items (one run at a time, never without a signed-in user): on sign-in after the first task list, on the window's `online` event, after any successful `apiFetch` and from the Retry button on a FAILED card (`queueRetry`). `sendQueuedAdd` posts the item's `body` with `apiFetch`, and a lost or rejected sign-in keeps the item PENDING (`keepQueued`); a sent add updates the list with the response (`applyQueuedAddResult`). `drainQueue`'s `onItem` makes `settleQueuedAdd` apply each result to the queue as stored then, so an add queued meanwhile is kept; the card of the add on its way reads "Sending…" and cannot be discarded.

- Saved task list: `setTasks` keeps every list the server sends, as it came (before the page hides removals still waiting), in `localStorage` (`TASK_CACHE_KEY`, `taskhub-task-cache`: `serializeTaskCache`, `parseTaskCache`, tied to the signed-in `uid`, every access in try/catch; the page's `saveTaskCache`, `readTaskCache`, `clearTaskCache`), cleared when the auth state is signed out. When `fetchTasks` fails on the connection (`isNetworkError`) the Queue shows the saved copy if the page has no list yet, or keeps the list on screen if it has, instead of the load error, under a note (`#offlineNote`, `offlineNoteText`: "You're offline. Showing the list as it was 5 minutes ago.") with a Retry button; the `online` event reads the list again (then drains the add queue) and any list from the server removes the note (`savedListAt`). Other failures still show the error. Only the task list, History's newest entries and the Miscellaneous list (next bullets) are saved: projects, clients and settings still need a connection, and changes the action queue does not hold, while the copy is shown, fail with their usual alert. The page itself still needs its Firebase SDK and `/__/firebase/init.json`, which the service worker does not cache, so a cold start with no connection can reach the saved list only while the browser still has them.

- Saved completed list: `fetchCompleted` keeps the server's newest `COMPLETED_CACHE_ROWS` (200) entries as they came in `localStorage` (`COMPLETED_CACHE_KEY`, `taskhub-completed-cache`: `serializeCompletedCache`, `parseCompletedCache`, tied to the `uid`, `limited` when the copy holds fewer entries than the server has; the page's `saveCompletedCache`, `readCompletedCache`, `clearCompletedCache`), cleared on sign-out and dropped first when `saveTaskCache` finds the storage full (a full storage never costs the task copy). When `fetchCompleted` fails on the connection and a copy exists, History shows it (`showCompletedCopy`) under `#completedOfflineNote` (`completedOfflineNoteText`) with a Retry button: search and paging work on it, Stats and Project hours say they need a connection, and an entry's form opens with every control disabled except the fields in `OFFLINE_COMPLETED_FIELDS` (priority, time spent, tags, travel, location, phone, email, description; `COMPLETED_FORM_CONTROLS`, `completedFieldDisabled`; Extra fields open) and a photos note that says photos need a connection. The `online` event and any list from the server replace the copy (`savedCompletedAt`). Save, Reopen and adding a comment in that form are held (`offline-edits.md`); Delete still fails with its usual alert until a later step queues it.

- Saved Miscellaneous list: `setShoppingFromServer` keeps every list the server sends (`loadShoppingList` and the reply to a change once none is waiting) as `[{id, text}]` in `localStorage` (`SHOPPING_CACHE_KEY`, `taskhub-shopping-cache`: `serializeShoppingCache`, `parseShoppingCache`, tied to the `uid`, at most `MAX_SHOPPING_ITEMS`; the page's `saveShoppingCache`, `readShoppingCache`, `clearShoppingCache`), never the page's list with changes not yet saved, and clears it on sign-out. When `loadShoppingList` fails on the connection (`isNetworkError`) the Materials page shows the saved copy if the page has no list yet, or keeps its list if it has, under `#shoppingOfflineNote` (`shoppingOfflineNoteText`, `savedShoppingAt`) with a Retry button; the `online` event reloads the list and any list from the server removes the note. Adds and ticks made while the copy is shown still fail with their usual message (the page takes the change back) until a later step holds them.

- Action queue (offline changes; the page makes TIMER, COMPLETE, DELETE, UNDO, REOPEN, EDIT, COMMENT and COMMENT_DELETE actions, an EDIT being a queued task's changed fields (its materials list included, whole, from a check-off on the Materials card or the edit form), a Snooze, or an entry's changed fields, from the History form's Save or carried by a Reopen; roadmap: Offline changes): pure helpers in the page's pure-helpers block, with the queue's page code beside the add queue's. `makeQueuedAction`, `parseActionQueue`, `serializeActionQueue` and `cleanActionQueue` hold actions of kind TIMER, COMPLETE, DELETE, UNDO, REOPEN, EDIT, COMMENT or COMMENT_DELETE (a DELETE names a task and carries no fields; a task's EDIT holds `EDIT_FIELDS` (`materials` as `heldMaterials` checks it: every item with an id of its own), an entry's `ENTRY_EDIT_FIELDS`, the archive row's plain fields: priority, trackedSeconds, tags, travelKm, phone, email, location, description; a COMMENT's `fields` are `{id, text}`, a COMMENT_DELETE's `{id}`; an UNDO's `fields` are `{task, spawnedId?}`, the task as archived or as deleted, and it names an `archiveId` only for a completion, at most `UNDO_TASK_MAX_CHARS` (20000) characters of JSON) under `ACTION_QUEUE_KEY` (`taskhub-action-queue`, `ACTION_QUEUE_MAX` 50); `clockOffsetFrom` gives the correction that makes an action's `at` (`noteServerTime` takes it from the `serverTime` of `getTasks` and `toggleTimer` replies, `setClockOffset`/`serverNow` apply it, `CLOCK_OFFSET_KEY` `taskhub-clock-offset` keeps it across reloads, and running timers and the long-timer warning are measured on `serverNow()`), `newArchiveId` the id of a local History entry. `withPendingActions(tasks, completed, actions, {projectIds?})` returns the lists with the PENDING actions replayed (FAILED ones and ones whose target is missing change nothing; a completion adds an entry marked `waitingRequestId` and no next occurrence; a DELETE takes the task off the list; an UNDO is `undoInList` with the record it carries and takes the entry of its `archiveId` out of History), and `cancelActions` takes an action out with the later ones that depend on it (`actionDependsOn`: a completion's undo, reopen and edits of its entry, a delete's undo, a reopen's or undo's later actions on its task). The replay uses page copies of `setTimerInList`, `settleTimer`, `recordCompletion`, the completion's History row (`completedRowOf`), `undoInList`, `completionRecord` and `deletionRecord` (the server's `removalRecord` less its kind and time; a delete's task has its timer paused at the delete's `at`), `reopenTask`, the entry edit (`applyEditFields` with `ENTRY_EDIT_FIELDS`, against `applyCompletedEdit`) `addCommentToList` and `removeCommentFromList` (against `addComment` and `removeComment`), each held equal to the server's by `actionQueue.test.js`, so a change to one of those server rules is made in its page copy too. `actionCardView`, `actionDiscardPrompt` and `actionLabel` draw the cards. On the page: `actionQueue` mirrors `localStorage` (`loadActionQueue`, `saveActionQueue`, every access in try/catch; `actionQueueRefusal` says why a change cannot be kept), `serverTasks` is the server's last list and `allTasks` what is shown, `shownTasks(list)` = that list less pending removals with the PENDING actions replayed (`setTasks` and the saved-copy path use it; the saved copy holds the server's list only). `sendTimerAction` posts as before and, on a connection failure (`isNetworkError`), calls `queueTimerAction`, which keeps a TIMER action (title, `fields {action, capSeconds?}`, `at` = device clock + `clockOffsetMs`) and shows it at once; while any action is PENDING or a drain runs, a new timer change goes behind them even with a connection, so the order holds. `drainAllQueues` (the add queue's triggers) sends the add queue then `drainActionQueue`: `drainQueue` over `sendQueuedAction` (posts a TIMER action's `{taskId, action, capSeconds?, at}` to `toggleTimer`, a COMPLETE's `completeBody` to `completeTask` and an UNDO's `undoBody` to `undoRemove`, never an action `blockedBy` an earlier FAILED one it depends on; takes the action out of the stored queue before showing the list it answers with), repeating rounds while changes are PENDING and the connection holds; a server answer marks the action FAILED with its text (`settleQueuedAction`; it stops changing the list). `renderAddQueue` draws the action cards after the add cards inside one card that starts closed (`actionQueueOpen`, toggled by `toggleActionQueue`, closed again once the queue is empty); its header (`actionQueueSummary`) gives the count and how many wait or were not accepted, so a refusal shows while it is closed; its cards have Retry on a FAILED one and Discard (after `actionDiscardPrompt`, through `cancelActions`, never while the action is on its way); a task with a PENDING action shows a "⏳ Waiting to send" chip (`waitingTaskIds`, `waitingIds`). The server's `undoInList` also takes the comments the archive row holds (`undoRemove` passes them); the page copy takes them as its third argument (the replay passes the entry's comments), so an Undo shows the comments written after the completion.

- Held completions, deletes and Undo (page): `removeTask` fixes a removal's `requestId`, `at` and, for a completion, `archiveId` before its first attempt and sends `removalBody(item, false)` (`completeBody` or `deleteBody`), so the first online attempt carries no `at` (the server uses its own clock) and a held send carries it; a held delete's `at` is when the task's running timer is stopped (`updateTaskDirect`). After a connection failure, or at once while actions are PENDING or a drain runs (a held timer is part of what the completion stops), `keepRemoval` keeps a COMPLETE or DELETE in the action queue and the queue hides the task; a delete's photos and calendar events are untouched until the send removes them (`updateTaskDirect`), and a repeat of a delete after a lost reply finds the task gone and changes nothing. The footnote's Undo (`undoRemovalInfo`: request id, archive id (null for a delete), the task as `completionRecord` or `deletionRecord` made it, `spawnedId` from the reply) follows `undoPlan`: CANCEL while the COMPLETE or DELETE is still waiting (`cancelActions`, nothing is sent), NONE once it was refused (the task is back already), else SEND, which `sendUndo` does as a call with its own request id or, behind waiting actions, during a drain or after a connection failure, as an UNDO kept by `keepUndo`. `blockedBy` exists because `drainQueue` goes on after a refusal and an UNDO behind a refused COMPLETE or DELETE would put back some other removal (the server keeps only the last); the footnote goes when its COMPLETE or DELETE is refused or discarded. History keeps `completedServer` (the entries as the server or the saved copy sent them) apart from `completedAll` (what is shown, `shownCompleted()`: `withPendingActions` over `serverTasks`), so the saved copy stays the server's; a waiting completion is a card at the top with a "⏳ Waiting to send" chip that cannot be opened (no `data-completed-open`), and `refreshHistoryIfOpen` reads History again when the queue changes or a completion is sent while History is on screen. A sent COMPLETE or UNDO clears `templates`.
