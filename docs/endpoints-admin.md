# Endpoints: schedule, settings, projects, clients and lists

The functions for scheduling runs, settings and notifications, tidying up, projects, clients, project templates and the Miscellaneous list. Every endpoint needs the owner's sign-in (see PROJECT.md).

| Function | Purpose | AI |
|---|---|---|
| `generateWeeklySchedule` | Manual full run, the "Update now" button; first pulls the voice inbox (`infrastructure.md`) | No |
| `rescheduleTask` | Replace one task's calendar event (engine run for that task only). 404 for an unknown task, 409 when the task is pinned to the personal calendar or is held back for materials | No |
| `voiceInboxPoll` | Scheduled every minute (not HTTP): pulls the voice inbox (`infrastructure.md`) | No |
| `autoScheduleDaily` | Dispatcher on a 15-minute cron (not HTTP; see below); first sends any start reminders due (`sendStartReminders`), then runs the same engine when the settings say a run is due, skipping it when nothing changed since the last full run; pushes the run-failed and weather-moved alerts | No |
| `getSettings` | Read `settings/app` with defaults filled in; the device tokens are left out and replaced by a `pushDevices` count | No |
| `updatePushToken` | Body `{action, token}`: `REGISTER` adds the device's FCM token to `pushTokens` (a token already listed stays; past 5 the oldest goes), `UNREGISTER` removes it; 400 for another action or an unusable token. Responds `{success, devices}` | No |
| `sendTestNotification` | No body. Sends the test message to every registered device (`sendToTokens`) and drops the devices the push service reports as gone. 400 when no device is registered, 502 with the error codes when nothing was delivered. Responds `{success, sent, failed, removed, devices}` | No |
| `removeDuplicateTasks` | Body `{dryRun?: true}`. A queued task is a copy of an earlier one when title (ignoring case and extra spaces), `dueDate`, `projectId` and `recurrence` match; the earliest added is kept (no `addedAt` counts as oldest, then queue order) and the more recent copies are removed, except any with a running timer or tracked time. With `dryRun` nothing changes and it responds `{success, duplicates: [{id, title, dueDate}], tasks}`; without it the copies are deleted in one transaction, then their calendar events and photos, and it responds `{success, removed, tasks}`. No undo. Added as a backup for the unexplained duplication of the queue (see below). |
| `getProjects` | Read all projects, sorted by name | No |
| `getClients` | Read all clients, sorted by name | No |
| `updateClient` | Body `{action, clientId?, client?}`: `CREATE` (`client` `{name, address?, phone?, email?, hourlyRate?, useWhatsApp?, location?, url?}`), `UPDATE` (`clientId`, `client` replacing the fields) or `DELETE`; 400 with the reason for an unusable field (`url` included: an http or https link, null or empty for none), a taken name (ignoring case) or an unknown action, 404 for an unknown `clientId`. `DELETE` takes the client off its projects (they stay); the response includes `clients` and, for `DELETE`, `projects`. No calendar changes | No |
| `updateProject` | Body `{action, projectId?, name?}`: `CREATE` (name), `UPDATE` (rename) or `DELETE`; 400 with the reason for an unusable or taken name or an unknown action, 404 for an unknown `projectId`. `SET_CLIENT` (with `clientId`) gives the project a client, or takes it off for null or empty text (400 `Client not found` for an id that is not stored, checked in the same transaction); with `newClient` (the whole client, as `updateClient` CREATE takes it) the client is created in the same transaction and given to the project instead, winning over `clientId` (400 for an unusable field or a taken name, nothing saved), and the response then also holds `client` and `clients`; a rename keeps the client. `SET_LOCATION` (with `location`, `{name, latitude?, longitude?}`) sets the project's own location, or removes it for null so the project inherits its client's again (400 for a missing or unusable one); a rename keeps it. `SET_URL` (with `url`, an http or https link) sets the project's own link, or removes it for null or empty text so the project uses its client's again (400 for a missing or unusable one); a rename keeps it. `DELETE` takes the project out of its member tasks (the tasks stay); the response includes `projects` and, for `DELETE`, `tasks`. No calendar changes | No |
| `getProjectTemplates` | Read all project templates, sorted by name | No |
| `updateProjectTemplate` | Body `{action, projectId?, templateId?, name?, startNow?}`: `SAVE` (`projectId`, optional `name`, which defaults to the project's name) stores the project's queued tasks as a template (`buildTemplateSteps`); `RENAME` (`templateId`, `name`); `DELETE` (`templateId`); `START` (`templateId`, `name`) creates the project `name` and one new task per step in one transaction (`startFromTemplate`: each task at the end of the list in step order, with the step's priority, estimate, tags, description, order number and unchecked materials, no due date, and the next job number from the counter), `startNow: true` starting the first task's timer. 400 with the reason for an unusable or taken name (template or project), a project with no queued tasks or more than 100, or an unknown action; 404 for an unknown `projectId` or `templateId`. SAVE, RENAME and DELETE respond with `templates` (SAVE and RENAME also `template`); START with `tasks`, `added`, `project` and `projects`. No calendar changes | No |
| `getShoppingList` | Read the Miscellaneous list: `{items}` in the order added | No |
| `updateShoppingList` | Body `{action: "ADD", text}` appends an item (400 for an unusable text or a full list; an item already there, ignoring case, is not added twice and still answers 200) or `{action: "REMOVE", itemId}` takes one off (an id that is not there changes nothing). 400 for another action. Responds `{items}`, the whole list, plus `item` for ADD. No calendar changes | No |
| `updateSettings` | Body `{settings: {location?, timeZone?, scheduleDays?, weatherDays?, gapMinutes?, timerWarnHours?, scheduleOrder?, day?, lunch?, schedule?, jobSheet?, notify?}}`, any subset of the editable fields, validated (IANA zone, latitude -90..90, longitude -180..180, name 1..100 characters, `scheduleDays` a whole number 1..28, `weatherDays` a whole number 1..16, `gapMinutes` a whole number 0..60, `day.start` and `day.end` `HH:MM` with `end` at least 60 minutes after `start` (checked on the merged result, so one end can be sent alone), `lunch.enabled` a boolean, `lunch.minutes` a whole number 5..180, `HH:MM`, interval from the allowed list, `jobSheet.contractorInfo` text of at most 1000 characters, `jobSheet.hourlyRate` an amount 0.01..10000 or null, `notify` booleans and `notify.leadMinutes` 30, 60 or 120) and merged in a transaction; 400 with the reason and nothing saved when a field is invalid | No |

`autoScheduleDaily` ticks every 15 minutes (the Cloud Scheduler cron is fixed at deploy). Each tick calls `claimAutoRun`, one transaction that checks `isRunDue` against `settings/app` and, if due, records `lastAutoRunAt`; only a tick that gets `due: true` runs the full engine, so a duplicate delivery cannot start a second run. A disabled schedule never runs. DAILY runs once the local time in the configured zone has reached `time`, if the last attempt was not on today's local date (a missed tick catches up on the next one; a `time` already passed today runs at the next tick). INTERVAL runs when `intervalMinutes` have passed since `lastAutoRunAt` (with a one-minute grace for tick jitter) and only between 8:00 and 20:00 local (20:00 itself excluded); a first run happens at the first tick in that window. The attempt is recorded when the run starts, so a failing run is not retried until the next due time (Update now still works) and a failure is only logged. A due automatic run that finds nothing changed is skipped (see scheduling-engine.md); the attempt still counts, so the next run waits for the next due time. Before any of that, each tick runs the reminder check: if start reminders are on and a device is registered, `claimReminderWindow` takes the stretch since the previous check (one tick back the first time, never more than 30 minutes) and records now in one transaction, so a duplicate tick covers nothing twice, and every task with a timed slot whose start less `notify.leadMinutes` falls in that stretch, that has not started and has no running timer, is announced in one message (TTL 20 minutes); a reminder therefore arrives between 15 minutes and the full lead before the start, a task booked closer to its start than that gets none, and a check that fails only logs. A failed automatic run (including a failed claim) sends the run-failed message (TTL 1 hour); a run's weather moves are sent after it succeeds (TTL 6 hours). A skipped run sends nothing.
