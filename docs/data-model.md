# Data model

Firestore collections and documents, the runtime settings and the Task shape.

- `tasks/{id}`: one document per active Task, the document id being the task's `id`. Read in `order` rank (sorted in code, so no index).
- `settings/app`: one document of runtime settings, read and written only through `getSettings`/`updateSettings`. Missing or unusable fields fall back to defaults in code (`settings.js`), so the document may be absent.
  - `location {name, latitude, longitude}`: default Whangaparāoa (-36.63, 174.78).
  - `timeZone`: IANA name, default Pacific/Auckland.
  - `scheduleDays`: how many days ahead a run schedules, a whole number 1..28, default 7.
  - `gapMinutes`: free minutes kept between scheduled tasks, a whole number 0..60, default 0.
  - `timerWarnHours`: hours a timer may run since it was started before the page warns it may have been left on, a whole number 1..48, default 6; read only by the page.
  - `scheduleOrder`: the order the planner takes tasks in, `URGENCY` (default) or `NUMBER` (task number, i.e. queue order); see the scheduling engine.
  - `day {start "HH:MM", end "HH:MM"}`: the daily window tasks are scheduled in, at least 60 minutes long, `end` after `start`; default 09:00-17:00. A stored window that breaks this falls back to the default as a whole.
  - `lunch {enabled, time "HH:MM", minutes}`: a break kept free every day, `minutes` a whole number 5..180; default disabled, 12:00, 30 minutes.
  - `travelGrouping {enabled, radiusKm, maxDeferDays}`: the planner's area preference (see scheduling-engine.md): `radiusKm` a number 0.5..100, how close two tasks must be to count as the same area, and `maxDeferDays` a whole number 0..14, how many days a task may wait to join one; default enabled, 5 km, 3 days. A Scheduling checkbox with the two numbers sets it.
  - `schedule {enabled, frequency DAILY|INTERVAL, time "HH:MM", intervalMinutes 15|30|60|120|240}`: default enabled, DAILY at 20:00 (`time` applies to DAILY, `intervalMinutes` to INTERVAL).
  - `jobSheet {contractorInfo, hourlyRate, travelRate}`: `hourlyRate` is dollars as a number from 0.01 to 10000 rounded to cents, null (the default) for none, and 0 or empty text saves as null; job sheets bill labour at it, except for a client with its own `hourlyRate`. `travelRate` is dollars per km, 0.01 to 100 rounded to cents, default 1.20 (the IRD's 2025-26 Tier 1 petrol kilometre rate); 0 or empty text saves as null, which is no travel charge and stays null (only a missing stored value takes the default). `contractorInfo` is free text printed at the top of every job sheet, under its title; line breaks kept, trailing spaces and blank lines at either end removed, at most 1000 characters, default empty.
  - `notify {runFailed, weatherMoved, taskStarting, leadMinutes}`: which alerts are sent (booleans, all true by default) and how long before a task starts its reminder is due, 30, 60 or 120 minutes (default 30; all longer than the 15-minute tick, so a reminder never arrives after the start).
  - `pushTokens`: up to 5 FCM registration tokens, one per device with notifications on (`push.js`); like the run state, never settable through `updateSettings`, carried through every settings write, and kept on the server: `getSettings`, `updateSettings` and `exportData` show a `pushDevices` count instead.
  - `lastReminderAt` (ISO; when the latest reminder check ran) is run state like the next two.
  - `lastAutoRunAt` (ISO; the start of the latest automatic run attempt, successful or not) and `lastRunFingerprint` (hex SHA-256 recorded by the latest successful full run, manual or automatic): run state, never settable through `updateSettings`.
  - The backend reads `location` and `timeZone` on every request that needs them (engine, weather, prompts, `addOrUpdateTask`, `completeTask`, `getCompletedTasks`) and `schedule` and `lastAutoRunAt` on every dispatcher tick.
- `projects/{id}`: one document per project, `{id, name, clientId?, location?}`, the document id being the project's id; `clientId` (the key absent for none) names a client; `location` (`{name, latitude?, longitude?}`, the key absent for none) is the project's own location, overriding its client's: only own locations are stored, and `effectiveLocation` resolves the one in force. Names are 1..100 characters and unique ignoring case. Read in name order (sorted in code, so no index).
- `clients/{id}`: one document per client, `{id, name, phone, email, hourlyRate?, useWhatsApp?, location?}`, the document id being the client's id. `name` is 1..100 characters and unique ignoring case; `phone` at most 40, `email` at most 100 and address-shaped when not empty; those two are empty text when unset. A client's address is its `location`; an `address` sent by an old page is ignored. `hourlyRate` is dollars from 0 to 10000 rounded to cents, overriding `settings.jobSheet.hourlyRate` on the job sheets of the client's projects; 0 is a real rate (labour billed at $0.00, for unpaid work); the key is absent for none (null or empty text), and then the global rate applies. `useWhatsApp` is `true` when the client's Call and Text buttons open WhatsApp instead of the phone; the key is absent for no (false or null), and any other type is a 400. `location` (`normalizeLocation`) is where the client is: the name is shown and used for navigation, the coordinates are the planner's only input; the key is absent for none (null, blank text or an empty object), and a value that does not pass is a 400. Read in name order (sorted in code, so no index).
- `project_templates/{id}`: one document per template, `{id, name, steps}`, the document id being the template's id. Names are 1..100 characters and unique ignoring case; read in name order (sorted in code, so no index). `steps` (1..100, in the order the project runs them) are `{title, priority, estimatedMinutes, tags, materials?, description?, travelKm?, projectOrder?}`: `materials` is `[{text, cost?}]` (no ids, never checked), the optional keys are absent when unset, and nothing else of a task is kept (no dates, schedule, timer, history, job number, recurrence or snooze). Saving takes the project's queued tasks only, not its completed ones; a template is a snapshot, so later edits to the project do not change it and deleting the project leaves it.
- `settings/shoppingList`: one document, `{items: [{id, text}]}`, the Miscellaneous list on the Materials tab: loose items to get that belong to no task, in the order added, at most 100, `text` 1..100 characters, unique ignoring case. Absent until the first item; read and written only through `getShoppingList` and `updateShoppingList`; included in `exportData`.
- `completed_tasks/{auto-id}`: a copy of the Task plus `completedAt` and the job's history including this completion (`completedCount`, `recentSeconds`; rows archived before history was kept have neither, and `buildTemplates` derives them from the rows sharing the title); its `trackedSeconds` is always present (0 for a task never timed), its `firstStartedAt` is kept when the timer was ever started, and it has no `timerStartedAt` or `active`; rows archived before time tracking began have no `trackedSeconds`, and rows archived before `firstStartedAt` was kept have none. Written once at completion; afterwards only corrected by hand through `updateCompletedTask`, removed by `deleteCompletedTask` or moved back to the queue by `reopenCompletedTask` (priority, estimate, tracked time, tags, materials, description, travel, location, phone, email, link, project and completion time; the `completedCount` and `recentSeconds` snapshot on a row is never changed, so a correction does not reach the history already carried by later rows or by the live next occurrence of a repeating task).
- `completed_photos/{auto-id}`: one document per photo of a task, `{archiveId | taskId, data (base64 JPEG), bytes (decoded size), addedAt}`: `archiveId` for a completed task, `taskId` (and no `archiveId`) for one still in the queue, at most 3 per task, kept out of the task list and the archive row so those stay light. `completeTask` re-keys a task's photos from `taskId` to its new archive id in the same transaction (a photo added in that instant is moved just after by a sweep); `undoRemove` of a completion and `reopenCompletedTask` move them back to the task's id; `updateTaskDirect` DELETE deletes them with the task (undoing a delete returns the task without them); `deleteCompletedTask` deletes them with their archive row; printed on job sheets; left out of `exportData`.
- `settings/jobCounter`: one document, `{last}`, the last job number issued (absent before the first). Read and moved forward only in the transaction that creates tasks (`updateTaskList` with `withJobCounter`), so a number is never issued twice or reused, even after its task is deleted; never rolled back by an undo; included in `exportData`.
- `settings/addRequests`: one document, `{ids}`, the `requestId`s of the newest 200 adds, completions, reopens and undos (oldest first; absent before the first). Read in the transaction of the change (`updateTaskList` with `withAddRequests`) and written in the same commit, so a repeated id changes nothing and takes no job number (`addRequests.js`); not in `exportData`.
- `settings/lastRemoved`: one document, replaced by every delete (`updateTaskDirect` DELETE) and completion (`completeTask`) in the same transaction: `{kind: "DELETE"|"COMPLETE", task, archiveId, spawnedId, at}` (`removalRecord`). Only `undoRemove` reads it, and it counts for 10 minutes (`isUndoable`).
- Task: `id`, `title`, `priority` (HIGH/MEDIUM/LOW), `dueDate` (YYYY-MM-DD or empty), `estimatedMinutes`, `tags[]`, `status` (PENDING/COMPLETED), `googleCalendarEventId`, `scheduledStart`/`scheduledEnd` (set only while scheduled; ISO 8601 with the local UTC offset, or YYYY-MM-DD with an exclusive end date for all-day), `locked` (true only while the owner has pinned the task by moving its event to the personal calendar), `recurrence` (optional `{frequency: DAILY|WEEKLY|MONTHLY|YEARLY, interval: 1..365}`; the key is absent for a task that does not repeat; completing the task spawns its next occurrence), `projectId` (optional; the project the task belongs to, the key is absent outside any project) and `materials` (optional list `[{id, text, checked, cost?}]`, manually written in the edit form or the manual add form, never set by Gemini; text 1..100 characters, at most 30 items; `cost` a number of dollars from 0 to 1,000,000 rounded to cents (`money.js`), the key absent when there is none, carried to the next occurrence of a repeating task; the key is absent when there are none; a task with an unchecked item is held back from the schedule, see scheduling-engine.md), `snoozedUntil` (optional local date YYYY-MM-DD: the scheduler does not place the task before that day; the due date is untouched; a date that is not after today restricts nothing and is left as stored; the key is absent when not snoozed; set by `updateTaskDirect` and, as a cooldown, by `completeTask` on the next occurrence of a repeating task (equal to its `dueDate`); never by Gemini; any other snooze is not carried to the next occurrence), `addedAt` (ISO timestamp of when the task was created, set by the server on every new task, including the next occurrence of a repeating task; never set by Gemini or changed by an edit; absent on tasks created before it existed), `trackedSeconds` (optional whole number of seconds accrued on the task's timer, absent until first used; kept when the timer is paused) and `firstStartedAt` (optional ISO instant the timer was first started on the task, set once by the first START and never moved by later starts, pauses or edits, and erased by an abort; kept on the archive row; not carried to the next occurrence of a repeating task, nor to a copy) and `timerStartedAt` (optional ISO instant the running timer started, absent while paused; at most one task has it) and `active` (optional `true` on the task whose timer was started last, kept through a pause and taken away by the next start on another task; at most one task has it; all four are set only by `toggleTimer` and the server's clock, never by Gemini or an edit, and none is carried to the next occurrence of a repeating task), `description` (optional text, 1..2000 characters, trimmed; free notes the owner writes in the edit form or the manual add form; never read or shown to Gemini, and set by it only on the steps of a suggested project the owner accepts (see `addOrUpdateTask`); the key is absent when empty; carried to the next occurrence of a repeating task), `comments` (optional array of `{id, at, text}`, the timestamped updates on the task, in the order written; absent for none; changed only by `addComment` and `deleteComment`, kept in the archive row and on reopen, not carried anywhere else; see `docs/endpoints-comments.md`), `travelKm` (optional number of kilometres driven for the task, 0.1 to 10000 rounded to one decimal (`travel.js`); the key is absent for none, 0 and empty meaning none; set by the owner in the edit form, the manual add form or a template, never by Gemini; carried to the next occurrence of a repeating task, to a copy of a completed task and to a project template step), `location` (optional `{name, latitude?, longitude?}`, the task's own place as `normalizeLocation` checks it; the key is absent for none; set by the owner in the edit form, the manual add form or a completed-task copy, never by Gemini; carried to the next occurrence of a repeating task and to a copy of a completed task, not to a project template step; where a task is, is its own location, else its project's, else its project's client's, `effectiveLocation`), `phone` and `email` (optional contact details of the task's own, validated by `contact.js`, the keys absent when empty; they override those of the task's project's client, which is used for whichever is absent; set by the owner in the edit form or the manual add form, never by Gemini; carried to the next occurrence of a repeating task and to a copy of a completed task, not to a project template step), `url` (optional link of the task's own: an http or https address of at most 500 characters, `https://` put in front of text with no scheme, validated by `normalizeUrl` in `contact.js`; set, carried and absent exactly as `phone` and `email` are), `completedCount` (optional whole number >= 1: how many times this job has been completed before this instance) and `recentSeconds` (optional list of up to 5 whole numbers: the tracked seconds of the job's latest completions that had any, oldest first; the rolling average of these, rounded to the nearest 5 minutes and at least 5, is the estimate of the next occurrence of a repeating task and of a task copied from a completed one; both are the job's history, carried forward to the next occurrence and to a copy, set by the server on completion, by a manual add from a copied completed task, never by Gemini or an edit, and absent on a job never completed), `projectOrder` (optional whole number 1..999, only with `projectId`; members of a project sharing a number form a tier that the scheduling engine places after every lower tier, and a member without one is unordered; leaving a project or moving to another clears it; unrelated to `order`), `jobNumber` (optional whole number from 1: a strictly sequential serial given to every new task from `settings/jobCounter`, by a free-text, manual or accepted-suggestion add and for the next occurrence of a repeating task (each occurrence is its own job); printed as at least 6 digits ("000123", `formatJobNumber`); never set by Gemini or changed by an edit, kept on the archive row and by a reopen, not carried to a copy; absent on tasks created before it existed, which stay unnumbered), `order` (rank from 1, renumbered 1..n whenever tasks are added or moved by `queueNumber`; removals leave gaps, which the page's task numbers ignore; it only breaks ties after priority in the planner, so a low task number does not outrank a higher priority or earlier due date; new ids are server-generated UUIDs).
