# TaskHub Next

An AI-enhanced to-do list that turns free-text input into structured tasks and schedules them onto Google Calendar. Single user. Location and time zone are runtime settings, defaulting to Whangaparāoa, NZ (Pacific/Auckland).

## Stack

- Firebase project `taskhub-next`. Hosting serves `public/`. Functions are v2 on Node 24, all in australia-southeast1 (set once with `setGlobalOptions` in `index.js`), as is Firestore.
- Calendar access uses service account `task-calendar-agent@gen-lang-client-0299359787.iam.gserviceaccount.com` (it lives in Google Cloud project `gen-lang-client-0299359787`, not `taskhub-next`). It has edit access to the agent calendar (`USER_CALENDAR_ID`) and "Make changes and see all event details" on the owner's personal calendar. The engine must only ever read the personal calendar, never write to it.
- Setup and deploy commands are in `README.md`. `.firebaserc` defaults to `taskhub-next`, and the `deploy` and `logs` scripts in `functions/package.json` pass `--project taskhub-next`.
- Firestore rules: deny-all. Every read and write goes through the functions via the Admin SDK, which bypasses rules.
- A separate app, a kids' chore tracker, lives in its own Firebase project (`screen-time-chore-tracker`). Never deploy to it from this repo; always target `taskhub-next` explicitly (`--project taskhub-next`).
- Frontend: one file, `public/index.html`, vanilla HTML/CSS/JS, no build step. Calls the functions over HTTPS; the functions base URL and SDK URL live in one `CONFIG` block at the top of the script. `apiFetch` throws the server's error text on any non-OK response, so a failed call never replaces the task list. All task-derived text goes through `esc()` before `innerHTML`; list and filter clicks use event delegation on `data-` attributes. Overdue tasks (`dueDate` before today in the configured time zone) sort to the top, most overdue first, then by `order`. Each task row shows an Overdue chip when overdue, a Repeats chip ("Weekly", "Every 2 weeks") when `recurrence` is set, its schedule (`scheduledStart`/`scheduledEnd`, formatted in the configured time zone) and a Locked chip when `locked`; all are read-only. The edit modal's due date field has a Clear button that empties it; saving then stores an empty `dueDate`. Its Repeats control (frequency, plus an interval when it repeats) is saved with the other fields as `recurrence`, null for "Does not repeat". A collapsible Recently Completed card loads `getCompletedTasks` each time it opens (and after a completion while open), read-only; above the list it shows the summary (total completed and estimated time, a per-week bar list, priority and tag chips). Its Reschedule button saves the edits, then calls `rescheduleTask` and reports the result in the schedule status line. The Settings card is the first card on the page and holds the Update now button (the manual full run, `generateWeeklySchedule`) beside Save settings; Update now is disabled while a run is in progress and shows the engine's error text on failure. Its result line (`#scheduleStatus`, also used by Reschedule) sits under the collapsed-by-default Settings details so it stays visible. Organized Queue is a collapsible section, open by default. Every date and time on the page uses one configured zone: `loadSettings` reads `getSettings` after sign-in and `applySettings` switches the formatters (default Pacific/Auckland until the settings arrive or if they fail to load), redraws the list and the completed list, and sets the page title to the location name. The Settings card edits the location (place search against the Open-Meteo geocoding API called from the browser with plain `fetch`, never `apiFetch`, so no Firebase token goes to a third party; picking a result sets name, latitude, longitude and time zone together), the automatic schedule (enabled, once a day at a time, or every 15/30/60/120/240 minutes during 8:00-19:00) and shows the last automatic run; Save posts the whole form to `updateSettings` and shows the server's error text when it rejects a field. The page is gated behind Google sign-in (Firebase Auth, JS SDK 12.18.0 from gstatic via dynamic `import()`, web config from Hosting's `/__/firebase/init.json`); `apiFetch` adds the ID token to every call, and a 401 or 403 signs out and returns to the sign-in screen.
- Backend: `functions/index.js` (endpoints and engine), `functions/calendar.js` (event listing, cleanup and busy-window helpers), `functions/auth.js` (owner check for the HTTP endpoints), `functions/schedule.js` (pure validation of Gemini's slots), `functions/tasks.js` (pure merge of model changes and engine results into the task list), `functions/recurrence.js` (pure date arithmetic for the next occurrence of a recurring task), `functions/due.js` (pure overdue check and urgency ordering for the scheduling prompt), `functions/completed.js` (pure limit clamping, serialising of archive documents and the weekly/tag/priority summary), `functions/weather.js` (pure: Open-Meteo URL for a location, the one-line weather description and `weatherKey`, the coarse WET/DRY/OTHER condition used in the run fingerprint), `functions/fingerprint.js` (pure: `computeFingerprint`, `normalizeBusy`, `hasEndedSlot` and `shouldSkipRun`, the quota guard described under the scheduling engine), `functions/prompts.js` (pure: `buildSchedulePrompt`, the Gemini scheduling prompt built from the settings), `functions/settings.js` (pure: defaults, field validation, `mergeSettings`, `applySettingsUpdate` and the `isRunDue` check and `claimRun` for the auto-run schedule), `functions/store.js` (`makeTaskStore(db)`: `updateTaskList` and `getTasks` over the `tasks/{id}` collection, plus the pure `diffTasks`; `makeSettingsStore(db)`: `getSettings`, `updateSettings`, the transactional `claimAutoRun` and `setRunFingerprint` over `settings/app`) and `functions/time.js` (local date, minutes-of-day, UTC offset, day-start and formatting helpers; every one takes the IANA time zone as its first argument and throws without one). Tests are `node --test` specs in `functions/test/` (`npm test`), covering every module except the endpoints and engine in `index.js`; the frontend's pure helpers (formatters, due-day count, schedule text, geocoding mapping, settings payload) sit between `// <pure-helpers>` and `// </pure-helpers>` in `public/index.html`, and `frontend.test.js` extracts that block and runs it, so keep it free of DOM and network access; `calendar.js` and `store.js` are tested against fake clients. Gemini (`@google/genai`, model constant `MODEL_NAME`) for parsing and scheduling. Google Calendar via the `googleapis` service-account JWT. Weather from Open-Meteo for the configured location.
- Secrets: `GEMINI_API_KEY`, `GOOGLE_CALENDAR_CREDENTIALS` (service-account JSON; bound to every function that touches Calendar, including `completeTask` and `updateTaskDirect`).
- Firebase Auth in `taskhub-next`: the Google provider is enabled and a web app is registered (Hosting serves its config at `/__/firebase/init.json`). Auth users are per project and unrelated to the chore tracker's.
- Config (Firebase params read from `functions/.env` at deploy): `OWNER_EMAIL` (the one Google account allowed to call the endpoints), `USER_CALENDAR_ID` (the agent calendar that tasks are scheduled onto) and `USER_PERSONAL_CALENDAR_ID` (the owner's personal calendar, read-only, used for free/busy).

## Data model

- `tasks/{id}`: one document per active Task, the document id being the task's `id`. Read in `order` rank (sorted in code, so no index).
- `settings/app`: one document of runtime settings, read and written only through `getSettings`/`updateSettings`. Missing or unusable fields fall back to defaults in code (`settings.js`), so the document may be absent.
  - `location {name, latitude, longitude}`: default Whangaparāoa (-36.63, 174.78).
  - `timeZone`: IANA name, default Pacific/Auckland.
  - `schedule {enabled, frequency DAILY|INTERVAL, time "HH:MM", intervalMinutes 15|30|60|120|240}`: default enabled, DAILY at 20:00 (`time` applies to DAILY, `intervalMinutes` to INTERVAL).
  - `lastAutoRunAt` (ISO; the start of the latest automatic run attempt, successful or not) and `lastRunFingerprint` (hex SHA-256 recorded by the latest successful full run, manual or automatic): run state, never settable through `updateSettings`.
  - The backend reads `location` and `timeZone` on every request that needs them (engine, weather, prompts, `addOrUpdateTask`, `completeTask`, `getCompletedTasks`) and `schedule` and `lastAutoRunAt` on every dispatcher tick.
- `completed_tasks/{auto-id}`: a copy of the Task plus `completedAt`. Write-only archive for future analytics.
- Task: `id`, `title`, `priority` (HIGH/MEDIUM/LOW), `dueDate` (YYYY-MM-DD or empty), `estimatedMinutes`, `tags[]`, `status` (PENDING/COMPLETED), `googleCalendarEventId`, `scheduledStart`/`scheduledEnd` (set only while scheduled; ISO 8601 with the local UTC offset, or YYYY-MM-DD with an exclusive end date for all-day), `locked` (true only while the owner has pinned the task by moving its event to the personal calendar), `recurrence` (optional `{frequency: DAILY|WEEKLY|MONTHLY|YEARLY, interval: 1..365}`; the key is absent for a task that does not repeat; completing the task spawns its next occurrence), `order` (rank from 1, renumbered 1..n whenever tasks are added or reranked; new ids are server-generated UUIDs).

## Endpoints

| Function | Purpose | AI |
|---|---|---|
| `getTasks` | Read the active list | No |
| `addOrUpdateTask` | Free text in; Gemini returns only new or changed tasks (title, priority, dueDate, estimatedMinutes, tags, recurrence, rank), merged server-side. Omitting `recurrence` leaves an existing task's unchanged; frequency NONE removes it. Cannot delete or complete tasks | Yes |
| `updateTaskDirect` | UPDATE or DELETE one task by id; DELETE also removes its calendar events. An UPDATE's `recurrence` is validated (null or frequency NONE removes it, an unusable value is ignored) | No |
| `getCompletedTasks` | Read the newest entries of `completed_tasks`, newest first (`?limit=`, default 50, at most 200), plus `summary` over the last 8 local weeks (Monday start, current week included, from up to 1000 archive rows regardless of `limit`): `totalCount`, `totalMinutes`, per-week, per-priority and per-tag `count` and `minutes`, and `truncated` when the window held more rows than were read | No |
| `completeTask` | Archive to `completed_tasks`, remove from the list, remove its calendar events. A recurring task also gets its next occurrence in the same transaction (`completeInList`): same title, priority, estimate, tags and recurrence, the completed task's rank, PENDING, no schedule, and a `dueDate` stepped forward from the old one in whole intervals until it is after today in the configured time zone (finishing early keeps the rhythm, finishing late skips missed occurrences; no due date counts from today; month ends clamp without drifting). The response includes `spawned` (the new task or null) | No |
| `generateWeeklySchedule` | Manual full run, the "Update now" button | Yes |
| `rescheduleTask` | Replace one task's calendar event (engine run for that task only). 404 for an unknown task, 409 when the task is pinned to the personal calendar | Yes |
| `autoScheduleDaily` | Dispatcher on a 15-minute cron (not HTTP; see below); runs the same engine when the settings say a run is due, skipping it when nothing changed since the last full run | Yes |
| `getSettings` | Read `settings/app` with defaults filled in | No |
| `updateSettings` | Body `{settings: {location?, timeZone?, schedule?}}`, any subset of the editable fields, validated (IANA zone, latitude -90..90, longitude -180..180, name 1..100 characters, `HH:MM`, interval from the allowed list) and merged in a transaction; 400 with the reason and nothing saved when a field is invalid | No |

Every HTTP endpoint requires `Authorization: Bearer <Firebase ID token>` for the verified Google account in `OWNER_EMAIL` (`ownerOnly`): 401 for a missing or invalid token, 403 for any other account or when `OWNER_EMAIL` is empty. Revocation takes effect when the current token expires (up to an hour). CORS allows only `https://taskhub-next.web.app` and `https://taskhub-next.firebaseapp.com` (`ALLOWED_ORIGINS`), so localhost is rejected. `autoScheduleDaily` is not HTTP and is unaffected.

`autoScheduleDaily` ticks every 15 minutes (the Cloud Scheduler cron is fixed at deploy, and 15 minutes is the finest interval offered). Each tick calls `claimAutoRun`, one transaction that checks `isRunDue` against `settings/app` and, if due, records `lastAutoRunAt`; only a tick that gets `due: true` runs the full engine, so a duplicate delivery cannot start a second run. A disabled schedule never runs. DAILY runs once the local time in the configured zone has reached `time`, if the last attempt was not on today's local date (a missed tick catches up on the next one; a `time` already passed today runs at the next tick). INTERVAL runs when `intervalMinutes` have passed since `lastAutoRunAt` (with a one-minute grace for tick jitter) and only between 8:00 and 19:00 local; a first run happens at the first tick in that window. The attempt is recorded when the run starts, so a failing run is not retried until the next due time (Update now still works) and a failure is only logged. A due automatic run that finds nothing changed is skipped (see the scheduling engine); the attempt still counts, so the next run waits for the next due time.

Every write to `tasks` is a Firestore transaction (via `updateTaskList` in `store.js`: it reads the whole collection, runs the modification, and writes only the tasks that changed or were removed). `addOrUpdateTask` calls Gemini outside the transaction and merges its changes into the list as stored at commit time: a change naming a task that no longer exists is skipped, and id, status, calendar and schedule fields, and `locked` are never taken from the model. `completeTask` commits the archive write and the list removal together. Calendar cleanup runs after the commit.

Deleting or completing a task removes its calendar events by stored `googleCalendarEventId` and by the `taskId` private extended property on the event, so a task whose stored id was lost still gets cleaned up.

## Scheduling engine (`runScheduleEngine`)

Nothing on the calendar changes until Gemini's slots pass validation. The personal calendar is only ever read.

1. Load tasks. Read the personal calendar's free/busy for the next 7 days.
2. Lock detection: list the events ending after now on the personal calendar that carry the marker "Generated by AI Task Agent", and match each to a task (`matchLockedEvents`: stored `googleCalendarEventId`, then the `taskId` private extended property, then title). A matched task is locked: it is not offered to Gemini, its old events are not deleted, and its event window counts as busy even if the event is marked free. Locks are recomputed on every run, so a lock is released once its event has ended. If either read in this step fails, abort.
3. List the agent calendar's existing app events from the start of today in the configured time zone. The events to replace are the stored ids of the unlocked tasks being scheduled plus every event carrying the marker. Collect agent-calendar busy time from opaque events that are not the app's own (events list, not free/busy, so the app's old events don't block rescheduling). Merge it with the personal and locked windows (overlaps combined) and pass Gemini only those time windows, never event titles.
4. Quota guard (full runs only, when there are unlocked tasks): fetch the weather, then compute the fingerprint, a SHA-256 over a version constant, the time zone and location, today's local date, the weather's WET/DRY/OTHER key, the unlocked tasks' scheduling fields (id, title, priority, dueDate, estimatedMinutes, tags, recurrence, order; never the calendar or schedule fields) and the merged busy windows (a window clipped to now or to the horizon is reduced to the marker "now" or "horizon", so the clipping does not change the hash). An automatic run (`skipIfUnchanged`) returns `{skipped: true}` before calling Gemini, with no calendar change, when the fingerprint equals `lastRunFingerprint` and no unlocked task has a scheduled slot that has ended (`hasEndedSlot`; such a task is still on the list, so it forces a run). Manual runs and `rescheduleTask` always go through. A successful full run stores its fingerprint (a failure to store only logs a warning); a failed run stores nothing. Bump `FINGERPRINT_VERSION` whenever the prompt or engine rules change.
5. Prompt Gemini (`requestSchedule`) with the current local time, the zone and its real UTC offset (for example +12:00 or +13:00 depending on daylight saving), today's local date, the weather at the configured location, the merged busy windows and the unlocked tasks. Tasks are annotated and ordered by `annotateDue` (`overdue`, `daysUntilDue`; most overdue first, then earliest due, then undated), and the prompt tells Gemini to place overdue tasks first and, where possible, on or before their due date; a missed due date is not a validation failure. Rules: 8:00–19:00 local time in the configured zone, opaque for focus tasks and transparent for quick chores, no outdoor tasks in rain, each task at most once. Skipped when every task is locked.
6. Validate (`validateSchedule`). Any failure, or an empty result, aborts and keeps the old events. Timed slots need an ISO time with offset, a start in the future, an end within 7 days, one local day inside 8:00–19:00, no overlap with busy windows or each other. All-day slots (always transparent) need a date from today to the horizon date and skip overlap checks. Each task id must be an unlocked task and appear once.
7. Insert the new events on the agent calendar (all-day events use an exclusive end date). If an insert fails, delete the ones already created and abort.
8. Delete the old events (agent calendar only; already-missing ones are ignored), then save in a transaction onto the list as stored then (`applyScheduleResults`): only the schedule fields of tasks the run read are rewritten, so edits and additions made meanwhile survive, and events created for tasks deleted or completed meanwhile are removed. Each scheduled task gets `googleCalendarEventId`, `scheduledStart` and `scheduledEnd`. Each locked task gets `locked: true`, the personal event's id and its actual start and end. Other tasks have all four fields cleared.

`runScheduleEngine({taskIds})` runs the same steps for a subset: only those tasks are offered to Gemini and have their events replaced (stored id plus events tagged with their `taskId`; orphans are left for full runs), every other app event on the agent calendar counts as busy whatever its transparency, and only the subset's schedule fields are rewritten. Locks are still detected across all tasks. `rescheduleTask` calls it with one id.

The cron and the manual trigger run the full engine and both use `USER_CALENDAR_ID`; neither the frontend nor the request chooses the calendar. All writes go to that calendar only. Busy time marked "free" (transparent) on either calendar does not count as busy, except locked windows. Deleting or completing a locked task never touches its event on the personal calendar.
