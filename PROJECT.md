# TaskHub Next

An AI-enhanced to-do list that turns free-text input into structured tasks and schedules them onto Google Calendar. Single user. Location and time zone are runtime settings, defaulting to Whangaparāoa, NZ (Pacific/Auckland).

## Maintaining this document

This file is a snapshot of the project's present state and intended direction. It is not a log.

- Read it at the start of every working session. Treat it as the source of truth, but verify against the code when the two disagree, and fix whichever is wrong.
- Update it in the same turn as any change that affects what it says (architecture, endpoints, config, data model, roadmap).
- Edit in place. Replace outdated statements; never leave a stale line with a correction beside it.
- No history. No "previously", "now fixed", "changed from", dates of changes or changelog entries. When a roadmap step is finished, delete it and update the sections that describe the new reality.
- Keep it short. Prefer one line to a paragraph, and a table to prose where content is tabular. Don't add narrative, rationale essays or duplicated information.
- Keep the roadmap ordered, with the next step first. Every step must be completable in a single turn; split any that aren't.
- Record only what's true now or planned. Unresolved questions go in Open questions and are removed once answered.

## Delivering changes

- End every turn that changes files by supplying a git patch of those changes, `PROJECT.md` updates included. Make it with `git format-patch` so it applies with `git am` from the repo root, with a short imperative commit message.
- Verify the patch applies cleanly to the previous state before delivering it.
- The patch contains only changed files: no `node_modules`, `__MACOSX` or unchanged files.
- Lint before delivering. The deploy's predeploy step runs `npm run lint` in `functions/` and a single error stops the whole deploy, so run it, with `npm test`, before every patch and deliver nothing until it reports no errors. It covers `functions/test/` as well as the source files. If `functions/node_modules` is missing, `npm install --no-save --no-package-lock` there installs ESLint and the rest without touching `package.json` or the lockfile. Fix what it reports with `npx eslint --fix <file>` and run the tests again.
- Write new JavaScript in `functions/` to the lint rules from the start (`.eslintrc.js`: `eslint:recommended` and the Google style). The ones that keep failing: strings in double quotes, never single (a string that contains double quotes is a template literal or has them escaped; in tests this is mostly HTML and regex text); parentheses around an arrow function's parameter, `(m) => m[1]`, never `m => m[1]`; two-space indent, semicolons, trailing commas in multi-line literals and calls. Long lines are fine: the files open with `/* eslint-disable max-len */` and `/* eslint-disable require-jsdoc */`, so a new file starts with them too. `public/index.html` is not linted and keeps its own style.

## Stack

- Firebase project `taskhub-next`. Hosting serves `public/`. Functions are v2 on Node 24, all in australia-southeast1 (set once with `setGlobalOptions` in `index.js`), as is Firestore.
- Calendar access uses service account `task-calendar-agent@gen-lang-client-0299359787.iam.gserviceaccount.com` (it lives in Google Cloud project `gen-lang-client-0299359787`, not `taskhub-next`). It has edit access to the agent calendar (`USER_CALENDAR_ID`) and "Make changes and see all event details" on the owner's personal calendar. The engine must only ever read the personal calendar, never write to it.
- `firebase.json` is tracked: the Firestore database, rules and indexes, the `functions` codebase (predeploy runs lint) and Hosting, which serves `public/` and rewrites every path to `/index.html` (existing files win, so the manifest, icons and `sw.js` are served as files; `sw.js` and the manifest are sent `no-cache`, the manifest as `application/manifest+json`).
- Setup and deploy commands are in `README.md`. `.firebaserc` defaults to `taskhub-next`, and the `deploy` and `logs` scripts in `functions/package.json` pass `--project taskhub-next`.
- Weekly backup: `weeklyBackup` (scheduled, Sunday 03:00 Pacific/Auckland, 120 s) starts a Firestore export of the whole database, photos included, to `gs://BACKUP_BUCKET/backups/<UTC stamp>/` (`FirestoreAdminClient.exportDocuments` from `@google-cloud/firestore`; it does not wait for the long operation) and then deletes all but the newest `KEEP_BACKUPS` 4 folders under `backups/`, touching only folders whose names are stamps (`backup.js`). An unset or invalid `BACKUP_BUCKET` logs an error and skips; a failed export logs and deletes nothing. The one-off bucket, role setup and restore command are in `README.md`. The page cannot download these backups (the Backup card's export is separate).
- Push notifications: Firebase Cloud Messaging through the Admin SDK (`admin.messaging()`, sent as the functions' own service account, no secret). Each device the owner turns notifications on for keeps its FCM token in `localStorage` (`taskhub-push-token`) and registers it with `updatePushToken`; the server keeps at most 5 on `settings/app` (`pushTokens`), dropping the oldest, and drops one the push service reports as gone. Messages are data-only (`buildMessage`: title, body, link, tag, a TTL, high urgency), so `public/sw.js` alone shows them (`notificationFromPush`; no Firebase code in the worker) and a tap opens or focuses the app at a same-site link (`notificationTarget`). The page gets its token through the app's own worker (`getToken` with `serviceWorkerRegistration`) from `firebase-messaging.js`, loaded only when needed from the same pinned SDK version as Auth; `CONFIG.vapidKey` (a Web Push certificate from the Firebase console) is optional and empty uses Firebase's default key. Notifications work in an installed app (and on iOS only once added to the Home Screen). Three alerts use it, each switchable in Settings (`notify`), through `notifyOwner` (which checks the switch and that a device is registered, never fails the work that raised it and drops devices reported gone): a failed automatic run (`runFailedMessage`, tag `run-failed`, the dispatcher's catch; manual runs show their error on the page), Outdoor or Garden tasks an automatic run took off a rainy day (`weatherMoves`: booked on a rainy date from today on and now on another date or none; one message, `weatherMoveMessage`, tag `weather-moved`) and a scheduled task about to start (`sendStartReminders`, below).
- Address autocomplete: the page calls Google's Places API (New) straight from the browser with plain `fetch` (never `apiFetch`, so no Firebase token goes to Google) using `CONFIG.placesApiKey`, a browser key restricted to `taskhub-next.web.app` and `taskhub-next.firebaseapp.com` and to that API, with daily quotas and a budget alert set in the Google Cloud console (setup in `README.md`); empty switches it off and the Open-Meteo search is used. `makePlacesAutocomplete` asks `places:autocomplete` once the text has `PLACES_MIN_CHARS` 3 characters and a `PLACES_DEBOUNCE_MS` 300 ms pause (limited to `CONFIG.placesRegion`, ranked toward the settings location, `autocompleteBody`; a reply to an older request is dropped), lists up to 5 suggestions with Google's "Powered by Google" attribution, and a tap fetches that place with `PLACES_DETAILS_FIELDS` (`id,formattedAddress,location,addressComponents`, all Place Details Essentials, the cheapest tier with 10,000 free requests a month; adding any other field raises the price, and a test fails on one) and calls `onPick(place, context)` with `placeFromDetails` (name, position) and the `getContext()` read at the tap, so a pick lands on what was chosen then even if the owner moves on while Google answers. One session token (`newSessionToken`) runs from the first autocomplete request to the details request, so Google bills the search once, and is renewed after each pick. The Clients form's Location field, the chosen project's Location row and the Location field of the add card's manual fields, the queued edit modal and the completed task's form use it (without a Places key the Open-Meteo search is used instead). A task form's box holds the task's own location only: a pick sets its text and map position, typed text is a name without a position, Clear removes it (`locationFromBox`), and while it is empty the note reads "From project: …" or "From client: …" (`taskLocationView`). An edit sends `location` only when it changed. A task row shows a 📍 chip with its effective location (`taskLocationChip`). Both edit modals show a 🧭 Navigate button while the form points at a location (`formLocation`: its own box, else its project's, else its client's), a Google Maps directions link (`navigationHref`: the text as the destination, else the coordinates).
- Timeouts and memory: the scheduling endpoints (`generateWeeklySchedule`, `rescheduleTask`), `autoScheduleDaily`, `addOrUpdateTask` and `batchUpdateTasks` (its snooze runs the engine) allow 120 s, and the scheduling functions, `batchUpdateTasks` included, get 512 MiB (a run that exhausts memory dies without a JSON error, so the page shows only "Request failed (500)" and the calendar can be left with extra events, which the next full run removes); `getJobSheet` allows 60 s and 512 MiB (it holds the photos it prints).
- Firestore rules: deny-all. Every read and write goes through the functions via the Admin SDK, which bypasses rules.
- A separate app, a kids' chore tracker, lives in its own Firebase project (`screen-time-chore-tracker`). Never deploy to it from this repo; always target `taskhub-next` explicitly (`--project taskhub-next`).
- Frontend: one page, `public/index.html`, vanilla HTML/CSS/JS, no build step, installable as a standalone Android app (PWA): `public/manifest.webmanifest` (standalone, no `theme_color`, dark `background_color`, start `/`), `public/icons/` (192, 512, maskable 512 and the Apple touch icon, a white tick on blue) and `public/sw.js`, registered by the page. The manifest's `share_target` (GET to `/` with `title`, `text` and `url`; Hosting's rewrite serves the page, so the worker needs no route) makes TaskHub appear in Android's share sheet once the app is (re)installed: at load `captureShare` keeps `sharedText` (the text, else the title, plus the link unless the text holds it, one line, at most 2000 characters) in `sessionStorage` (`taskhub-share`, so a redirect sign-in keeps it) and cleans the address; after sign-in `applyPendingShare` opens the Queue tab and puts it in the add field for the owner to review, adding nothing. The page follows the device's light or dark setting until the owner uses the Dark mode checkbox (an Appearance card under the settings card on the Settings page, outside the saved form): it applies at once and is kept in `localStorage` (`taskhub-theme`, "light" or "dark", per device, never sent to the server). ## Data model

- `tasks/{id}`: one document per active Task, the document id being the task's `id`. Read in `order` rank (sorted in code, so no index).
- `settings/app`: one document of runtime settings, read and written only through `getSettings`/`updateSettings`. Missing or unusable fields fall back to defaults in code (`settings.js`), so the document may be absent.
  - `location {name, latitude, longitude}`: default Whangaparāoa (-36.63, 174.78).
  - `timeZone`: IANA name, default Pacific/Auckland.
  - `scheduleDays`: how many days ahead a run schedules, a whole number 1..28, default 7.
  - `gapMinutes`: free minutes kept between scheduled tasks, a whole number 0..60, default 0.
  - `timerWarnHours`: hours a timer may run since it was started before the page warns it may have been left on, a whole number 1..48, default 6; read only by the page.
  - `scheduleOrder`: the order the planner takes tasks in, `URGENCY` (default) or `NUMBER` (task number, i.e. queue order); see the scheduling engine.
  - `day {start "HH:MM", end "HH:MM"}`: the daily window tasks are scheduled in, at least 60 minutes long, `end` after `start`; default 09:00-17:00. A stored window that breaks this falls back to the default as a whole.
  - `lunch {enabled, time "HH:MM", minutes}`: a break kept free every day, `minutes` a whole number 5..180; default disabled, 12:00, 30 minutes.
  - `travelGrouping {enabled, radiusKm, maxDeferDays}`: the planner's area preference (see the scheduling engine): `radiusKm` a number 0.5..100, how close two tasks must be to count as the same area, and `maxDeferDays` a whole number 0..14, how many days a task may wait to join one; default enabled, 5 km, 3 days. A Scheduling checkbox with the two numbers sets it.
  - `schedule {enabled, frequency DAILY|INTERVAL, time "HH:MM", intervalMinutes 15|30|60|120|240}`: default enabled, DAILY at 20:00 (`time` applies to DAILY, `intervalMinutes` to INTERVAL).
  - `jobSheet {contractorInfo, hourlyRate, travelRate}`: `hourlyRate` is dollars as a number from 0.01 to 10000 rounded to cents, null (the default) for none, and 0 or empty text saves as null; job sheets bill labour at it, except for a client with its own `hourlyRate`. `travelRate` is dollars per km, 0.01 to 100 rounded to cents, default 1.20 (the IRD's 2025-26 Tier 1 petrol kilometre rate); 0 or empty text saves as null, which is no travel charge and stays null (only a missing stored value takes the default). `contractorInfo` is free text printed at the top of every job sheet, under its title; line breaks kept, trailing spaces and blank lines at either end removed, at most 1000 characters, default empty.
  - `notify {runFailed, weatherMoved, taskStarting, leadMinutes}`: which alerts are sent (booleans, all true by default) and how long before a task starts its reminder is due, 30, 60 or 120 minutes (default 30; all longer than the 15-minute tick, so a reminder never arrives after the start).
  - `pushTokens`: up to 5 FCM registration tokens, one per device with notifications on (`push.js`); like the run state, never settable through `updateSettings`, carried through every settings write, and kept on the server: `getSettings`, `updateSettings` and `exportData` show a `pushDevices` count instead.
  - `lastReminderAt` (ISO; when the latest reminder check ran) is run state like the next two.
  - `lastAutoRunAt` (ISO; the start of the latest automatic run attempt, successful or not) and `lastRunFingerprint` (hex SHA-256 recorded by the latest successful full run, manual or automatic): run state, never settable through `updateSettings`.
  - The backend reads `location` and `timeZone` on every request that needs them (engine, weather, prompts, `addOrUpdateTask`, `completeTask`, `getCompletedTasks`) and `schedule` and `lastAutoRunAt` on every dispatcher tick.
- `projects/{id}`: one document per project, `{id, name, clientId?, location?}`, the document id being the project's id; `clientId` (the key absent for none) names a client; `location` (`{name, latitude?, longitude?}`, the key absent for none) is the project's own location, overriding its client's: only own locations are stored, and `effectiveLocation` resolves the one in force. Names are 1..100 characters and unique ignoring case. Read in name order (sorted in code, so no index).
- `clients/{id}`: one document per client, `{id, name, phone, email, hourlyRate?, useWhatsApp?, location?}`, the document id being the client's id. `name` is 1..100 characters and unique ignoring case; `phone` at most 40, `email` at most 100 and address-shaped when not empty; those two are empty text when unset. A client's address is its `location`; an `address` sent by an old page is ignored. `hourlyRate` is dollars from 0 to 10000 rounded to cents, overriding `settings.jobSheet.hourlyRate` on the job sheets of the client's projects; 0 is a real rate (labour billed at $0.00, for unpaid work); the key is absent for none (null or empty text), and then the global rate applies. `useWhatsApp` is `true` when the client's Call and Text buttons open WhatsApp instead of the phone; the key is absent for no (false or null), and any other type is a 400. `location` (`normalizeLocation`) is where the client is: the name is shown and used for navigation, the coordinates are the planner's only input; the key is absent for none (null, blank text or an empty object), and a value that does not pass is a 400. Read in name order (sorted in code, so no index).
- `project_templates/{id}`: one document per template, `{id, name, steps}`, the document id being the template's id. Names are 1..100 characters and unique ignoring case; read in name order (sorted in code, so no index). `steps` (1..100, in the order the project runs them) are `{title, priority, estimatedMinutes, tags, materials?, comments?, travelKm?, projectOrder?}`: `materials` is `[{text, cost?}]` (no ids, never checked), the optional keys are absent when unset, and nothing else of a task is kept (no dates, schedule, timer, history, job number, recurrence or snooze). Saving takes the project's queued tasks only, not its completed ones; a template is a snapshot, so later edits to the project do not change it and deleting the project leaves it.
- `settings/shoppingList`: one document, `{items: [{id, text}]}`, the Miscellaneous list on the Materials tab: loose items to get that belong to no task, in the order added, at most 100, `text` 1..100 characters, unique ignoring case. Absent until the first item; read and written only through `getShoppingList` and `updateShoppingList`; included in `exportData`.
- `completed_tasks/{auto-id}`: a copy of the Task plus `completedAt` and the job's history including this completion (`completedCount`, `recentSeconds`; rows archived before history was kept have neither, and `buildTemplates` derives them from the rows sharing the title); its `trackedSeconds` is always present (0 for a task never timed), its `firstStartedAt` is kept when the timer was ever started, and it has no `timerStartedAt` or `active`; rows archived before time tracking began have no `trackedSeconds`, and rows archived before `firstStartedAt` was kept have none. Written once at completion; afterwards only corrected by hand through `updateCompletedTask`, removed by `deleteCompletedTask` or moved back to the queue by `reopenCompletedTask` (priority, estimate, tracked time, tags, materials, comments, travel, location, project and completion time; the `completedCount` and `recentSeconds` snapshot on a row is never changed, so a correction does not reach the history already carried by later rows or by the live next occurrence of a repeating task).
- `completed_photos/{auto-id}`: one document per photo of a task, `{archiveId | taskId, data (base64 JPEG), bytes (decoded size), addedAt}`: `archiveId` for a completed task, `taskId` (and no `archiveId`) for one still in the queue, at most 3 per task, kept out of the task list and the archive row so those stay light. `completeTask` re-keys a task's photos from `taskId` to its new archive id in the same transaction (a photo added in that instant is moved just after by a sweep); `undoRemove` of a completion and `reopenCompletedTask` move them back to the task's id; `updateTaskDirect` DELETE deletes them with the task (undoing a delete returns the task without them); `deleteCompletedTask` deletes them with their archive row; printed on job sheets; left out of `exportData`.
- `settings/jobCounter`: one document, `{last}`, the last job number issued (absent before the first). Read and moved forward only in the transaction that creates tasks (`updateTaskList` with `withJobCounter`), so a number is never issued twice or reused, even after its task is deleted; never rolled back by an undo; included in `exportData`.
- `settings/addRequests`: one document, `{ids}`, the `requestId`s of the newest 200 adds (oldest first; absent before the first). Read in the transaction of an add (`updateTaskList` with `withAddRequests`) and written in the same commit as the task, so a repeated id adds nothing and takes no job number (`addRequests.js`); not in `exportData`.
- `settings/lastRemoved`: one document, replaced by every delete (`updateTaskDirect` DELETE) and completion (`completeTask`) in the same transaction: `{kind: "DELETE"|"COMPLETE", task, archiveId, spawnedId, at}` (`removalRecord`). Only `undoRemove` reads it, and it counts for 10 minutes (`isUndoable`).
- Task: `id`, `title`, `priority` (HIGH/MEDIUM/LOW), `dueDate` (YYYY-MM-DD or empty), `estimatedMinutes`, `tags[]`, `status` (PENDING/COMPLETED), `googleCalendarEventId`, `scheduledStart`/`scheduledEnd` (set only while scheduled; ISO 8601 with the local UTC offset, or YYYY-MM-DD with an exclusive end date for all-day), `locked` (true only while the owner has pinned the task by moving its event to the personal calendar), `recurrence` (optional `{frequency: DAILY|WEEKLY|MONTHLY|YEARLY, interval: 1..365}`; the key is absent for a task that does not repeat; completing the task spawns its next occurrence), `projectId` (optional; the project the task belongs to, the key is absent outside any project) and `materials` (optional list `[{id, text, checked, cost?}]`, manually written in the edit form or the manual add form, never set by Gemini; text 1..100 characters, at most 30 items; `cost` a number of dollars from 0 to 1,000,000 rounded to cents (`money.js`), the key absent when there is none, carried to the next occurrence of a repeating task; the key is absent when there are none; a task with an unchecked item is held back from the schedule, see the scheduling engine), `snoozedUntil` (optional local date YYYY-MM-DD: the scheduler does not place the task before that day; the due date is untouched; a date that is not after today restricts nothing and is left as stored; the key is absent when not snoozed; set by `updateTaskDirect` and, as a cooldown, by `completeTask` on the next occurrence of a repeating task (equal to its `dueDate`); never by Gemini; any other snooze is not carried to the next occurrence), `addedAt` (ISO timestamp of when the task was created, set by the server on every new task, including the next occurrence of a repeating task; never set by Gemini or changed by an edit; absent on tasks created before it existed), `trackedSeconds` (optional whole number of seconds accrued on the task's timer, absent until first used; kept when the timer is paused) and `firstStartedAt` (optional ISO instant the timer was first started on the task, set once by the first START and never moved by later starts, pauses or edits, and erased by an abort; kept on the archive row; not carried to the next occurrence of a repeating task, nor to a copy) and `timerStartedAt` (optional ISO instant the running timer started, absent while paused; at most one task has it) and `active` (optional `true` on the task whose timer was started last, kept through a pause and taken away by the next start on another task; at most one task has it; all four are set only by `toggleTimer` and the server's clock, never by Gemini or an edit, and none is carried to the next occurrence of a repeating task), `comments` (optional text, 1..2000 characters, trimmed; free notes the owner writes in the edit form or the manual add form; never read or shown to Gemini, and set by it only on the steps of a suggested project the owner accepts (see `addOrUpdateTask`); the key is absent when empty; carried to the next occurrence of a repeating task), `travelKm` (optional number of kilometres driven for the task, 0.1 to 10000 rounded to one decimal (`travel.js`); the key is absent for none, 0 and empty meaning none; set by the owner in the edit form, the manual add form or a template, never by Gemini; carried to the next occurrence of a repeating task, to a copy of a completed task and to a project template step), `location` (optional `{name, latitude?, longitude?}`, the task's own place as `normalizeLocation` checks it; the key is absent for none; set by the owner in the edit form, the manual add form or a completed-task copy, never by Gemini; carried to the next occurrence of a repeating task and to a copy of a completed task, not to a project template step; where a task is, is its own location, else its project's, else its project's client's, `effectiveLocation`), `phone` and `email` (optional contact details of the task's own, validated by `contact.js`, the keys absent when empty; they override those of the task's project's client, which is used for whichever is absent; set by the owner in the edit form or the manual add form, never by Gemini; carried to the next occurrence of a repeating task and to a copy of a completed task, not to a project template step), `completedCount` (optional whole number >= 1: how many times this job has been completed before this instance) and `recentSeconds` (optional list of up to 5 whole numbers: the tracked seconds of the job's latest completions that had any, oldest first; the rolling average of these, rounded to the nearest 5 minutes and at least 5, is the estimate of the next occurrence of a repeating task and of a task copied from a completed one; both are the job's history, carried forward to the next occurrence and to a copy, set by the server on completion, by a manual add from a copied completed task, never by Gemini or an edit, and absent on a job never completed), `projectOrder` (optional whole number 1..999, only with `projectId`; members of a project sharing a number form a tier that the scheduling engine places after every lower tier, and a member without one is unordered; leaving a project or moving to another clears it; unrelated to `order`), `jobNumber` (optional whole number from 1: a strictly sequential serial given to every new task from `settings/jobCounter`, by a free-text, manual or accepted-suggestion add and for the next occurrence of a repeating task (each occurrence is its own job); printed as at least 6 digits ("000123", `formatJobNumber`); never set by Gemini or changed by an edit, kept on the archive row and by a reopen, not carried to a copy; absent on tasks created before it existed, which stay unnumbered), `order` (rank from 1, renumbered 1..n whenever tasks are added or moved by `queueNumber`; removals leave gaps, which the page's task numbers ignore; it only breaks ties after priority in the planner, so a low task number does not outrank a higher priority or earlier due date; new ids are server-generated UUIDs).

## Endpoints

| Function | Purpose | AI |
|---|---|---|
| `getTasks` | Read the active list | No |
| `addOrUpdateTask` | Free text in; Gemini returns only new or changed tasks (title, priority, dueDate, estimatedMinutes, tags, recurrence, rank), merged server-side; the rank counts only on a new task (inserted at that place in the queue, lowest rank first, clamped; the end when none) and is ignored on a change to an existing task, so the model can never reorder existing tasks; the prompt shows it the queue as 1..n. With a `manual` body `{title, priority?, dueDate?, estimatedMinutes?, tags?, recurrence?, projectId?, projectOrder?, newProject?, materials?, comments?, travelKm?, phone?, email?, location?, history?}` instead of `input` the model parses nothing: the task is added at the end of the list with the fields validated like the model's (an unusable one takes the new-task default; 400 without a title); `newProject` (a name) creates that project in the same transaction as the task and gives the task its id, overriding `projectId`, keeping `projectOrder`: 400 for an unusable name before anything else happens, 400 for a name already taken (ignoring case) with nothing added, and the response then also holds `project` and `projects`; `recurrence` is validated like the model's, `projectId` counts only for a project stored at commit time (with `projectOrder` through `applyProjectFields`) and `materials` goes through `normalizeMaterials`, `comments` through `normalizeComments` `travelKm` through `normalizeTravelKm` and `location` through `normalizeLocation`, a new task only, as does `history` (`normalizeHistory`, the job history of a copied completed task). A manual entry with no usable tag gets tags from the model (title and the tags already on the list only, 1 to 3, cleaned by `cleanTags`; a failure only logs and the task is added untagged) (so a copy of a completed task with no tags gets them too). Any body with `startNow: true` starts the timer of the first task it adds (the same effect as `toggleTimer` START, in the same transaction), making it the active task. Omitting `recurrence` leaves an existing task's unchanged; frequency NONE removes it. The model's changes never carry `projectId` or `projectOrder`: `withoutProjectFields` strips them from the model's output and from an `apply` list, and the prompt and response schema leave them out, so a free-text add never puts a task in a project, moves it or reorders it (a task joins a project only through a manual entry or an accepted suggestion), and the model cannot create, rename or delete projects, and its changes never read or change `materials` or `comments` (only a manual entry sets them, on a new task) or `snoozedUntil`. A free-text body with `allowProposal: true` also lets the model suggest a project (`projectProposal`, asked for only then, checked by `normalizeProposal`: a step may carry `comments`, the detail the input gives for it (asked for only where there is some, 2000 characters at most, stored on its task by an accepted project; the dialog shows them cut to two lines); dropped as a whole under 3 or over 12 usable steps, when its name matches an existing project (ignoring case), or when the input names an existing project (`namesProject`)); when one survives, nothing is committed and the response is `{success, needsChoice: true, proposal: {name, steps}, singleChanges}`, `singleChanges` being the model's ordinary changes. Without `allowProposal` the model is not asked and the behaviour is as described above. The owner's choice comes back without calling the model: `{acceptProposal: {name, steps}}` re-validates the suggestion with `normalizeProposal` against the projects stored at commit time (400 with the reason when it no longer passes, e.g. the name was taken meanwhile), then in one transaction creates the project and adds its steps at the end of the list, step n with that `projectId` and `projectOrder` n (`acceptProposalInList`), and responds `{success, tasks, added, updated, skipped, project, projects}`; `{apply: {changes}}` (the declined path: `singleChanges`, a list of at most 100 change objects, else 400) is merged by `mergeTaskChanges` like any model output. `startNow: true` works with both and starts the first task added. Every new task it adds, however added, takes the next job number in the same transaction (`jobCounter` passed to `mergeTaskChanges` and `acceptProposalInList`). A body may carry `requestId` (8 to 64 letters, digits, `-` and `_`; else 400): on a manual, free-text or `apply` body it is recorded in `settings/addRequests` with the add that used it, and a body with an id already there adds nothing and takes no job number, responding `{success, tasks, added: 0, updated: 0, skipped: 0, duplicate: true}` (a repeated free-text body may still call the model, and an add that changes nothing records no id; `acceptProposal` ignores it). Cannot delete or complete tasks | Yes |
| `updateTaskDirect` | UPDATE or DELETE one task by id; DELETE also removes its calendar events. An UPDATE's `newProject` (a name) creates that project in the same transaction and puts the task in it, overriding `projectId` and keeping `projectOrder` (400 for an unusable or taken name, nothing saved; the response then also holds `project` and `projects`). An UPDATE's `recurrence` is validated (null or frequency NONE removes it, an unusable value is ignored), and so are `projectId` (null or empty leaves the project, an id that is not a stored project is ignored; checked against the projects at commit time) and `projectOrder` (null clears it; ignored for a task outside a project), and `materials` (validated by `normalizeMaterials`: items without text are dropped, ids that are missing, invalid or repeated are regenerated, null or an empty list removes it, an unusable value is ignored) and `snoozedUntil` (validated by `normalizeSnooze`: a real YYYY-MM-DD date sets it, null or an empty string removes it, an unusable value is ignored) and `comments` (validated by `normalizeComments`: text is trimmed and cut to 2000 characters, null or blank text removes it, a non-string is ignored) and `travelKm` (validated by `normalizeTravelKm`: a number or plain decimal text is rounded to one decimal, null, empty text or 0 removes it, an unusable value is ignored) and `phone` and `email` (validated by `normalizePhone` and `normalizeEmail`: null or blank text removes it, an unusable value is ignored) and `location` (validated by `normalizeLocation`: null, blank text or an empty object removes it, an unusable value is ignored) and `queueNumber` (a whole number: moves the task to that place in the queue, clamped to 1..n, the others closing up and every `order` renumbered 1..n, `moveToQueueNumber`; `order` itself is never taken from an edit) | No |
| `batchUpdateTasks` | Body `{action, taskIds, ...}` (at most 500 ids; ids matching no task are ignored, 404 when none match) changes the named queued tasks in one transaction (`applyBatch`): `MOVE_TO_TOP` (they go to the top, keeping their relative queue order, every `order` renumbered 1..n), `SET_PROJECT` (`projectId` of a stored project, or `newProject`, a name created in the same transaction, 400 for an unusable or taken name; a task already in the project keeps its `projectOrder`, any other loses it), `SET_DUE` (`dueDate`, a real YYYY-MM-DD date; null or empty clears it to "") or `SNOOZE` (`snoozedUntil` as `updateTaskDirect` takes it; null or empty unsnoozes). After a `SNOOZE`, one `runScheduleEngine({taskIds})` moves the events of the tasks that have one, are not locked and are not waiting on materials (`needsReschedule`); a failure there keeps the snooze and sets `rescheduleError`. 400 with the reason for an unusable action, id list or value. Responds `{success, tasks, count, rescheduled, rescheduleError?}`, plus `project` and `projects` when one was created. Every HTTP endpoint requires `Authorization: Bearer <Firebase ID token>` for the verified Google account in `OWNER_EMAIL` (`ownerOnly`): 401 for a missing or invalid token, 403 for any other account or when `OWNER_EMAIL` is empty. Revocation takes effect when the current token expires (up to an hour). CORS allows only `https://taskhub-next.web.app` and `https://taskhub-next.firebaseapp.com` (`ALLOWED_ORIGINS`), so localhost is rejected. `autoScheduleDaily` is not HTTP and is unaffected.

`autoScheduleDaily` ticks every 15 minutes (the Cloud Scheduler cron is fixed at deploy, and 15 minutes is the finest interval offered). Each tick calls `claimAutoRun`, one transaction that checks `isRunDue` against `settings/app` and, if due, records `lastAutoRunAt`; only a tick that gets `due: true` runs the full engine, so a duplicate delivery cannot start a second run. A disabled schedule never runs. DAILY runs once the local time in the configured zone has reached `time`, if the last attempt was not on today's local date (a missed tick catches up on the next one; a `time` already passed today runs at the next tick). INTERVAL runs when `intervalMinutes` have passed since `lastAutoRunAt` (with a one-minute grace for tick jitter) and only between 8:00 and 20:00 local (20:00 itself excluded); a first run happens at the first tick in that window. The attempt is recorded when the run starts, so a failing run is not retried until the next due time (Update now still works) and a failure is only logged. A due automatic run that finds nothing changed is skipped (see the scheduling engine); the attempt still counts, so the next run waits for the next due time. Before any of that, each tick runs the reminder check: if start reminders are on and a device is registered, `claimReminderWindow` takes the stretch since the previous check (one tick back the first time, never more than 30 minutes) and records now in one transaction, so a duplicate tick covers nothing twice, and every task with a timed slot whose start less `notify.leadMinutes` falls in that stretch, that has not started and has no running timer, is announced in one message (TTL 20 minutes); a reminder therefore arrives between 15 minutes and the full lead before the start, a task booked closer to its start than that gets none, and a check that fails only logs. A failed automatic run (including a failed claim) sends the run-failed message (TTL 1 hour); a run's weather moves are sent after it succeeds (TTL 6 hours). A skipped run sends nothing.

Every write to `tasks` is a Firestore transaction (via `updateTaskList` in `store.js`: it reads the whole collection, runs the modification, and writes only the tasks that changed or were removed). `addOrUpdateTask` calls Gemini outside the transaction and merges its changes into the list as stored at commit time: a change naming a task that no longer exists is skipped, and id, status, calendar and schedule fields, and `locked` are never taken from the model, nor are `projectId` and `projectOrder`; a manual entry's or an accepted suggestion's project fields count only for a project stored at commit time (the transaction reads `projects` too), applied through `applyProjectFields`. `completeTask` commits the archive write and the list removal together. Calendar cleanup runs after the commit.

Deleting or completing a task removes its calendar events by stored `googleCalendarEventId` and by the `taskId` private extended property on the event, so a task whose stored id was lost still gets cleaned up.

## Scheduling engine (`runScheduleEngine`)

Nothing on the calendar changes until the slots pass validation. The personal calendar is only ever read. A task is held (not scheduled) while it has an unchecked material, and so are the members of its project with a higher order number than the lowest held one; a locked task is never held and holds no one. A snoozed task is not held: it is scheduled, but not before its snooze date (steps 5 and 6).

1. Load tasks. Read the personal calendar's free/busy from now to the horizon (`scheduleDays` days ahead, default 7).
2. Lock detection: list the events ending after now on the personal calendar that carry the marker "Generated by AI Task Agent", and match each to a task (`matchLockedEvents`: stored `googleCalendarEventId`, then the `taskId` private extended property, then title). A matched task is locked (and never held): it is not offered to the planner, its old events are not deleted, and its event window counts as busy even if the event is marked free. Locks are recomputed on every run, so a lock is released once its event has ended. If either read in this step fails, abort.
3. Held tasks (`heldTaskIds`, over all tasks) are left out of the request but count as replaced: their old events are deleted and their schedule fields cleared, like those of tasks the planner leaves out. List the agent calendar's existing app events from the start of today in the configured time zone. The events to replace are the stored ids of the unlocked tasks being scheduled plus every event carrying the marker. Collect agent-calendar busy time from opaque events that are not the app's own (events list, not free/busy, so the app's old events don't block rescheduling). Merge it with the personal and locked windows (overlaps combined) and the lunch break (`lunchWindows`: with `lunch` enabled, one window per local day from now to the horizon, cut to that range, so it is busy time for the planner, the validation and the fingerprint); with a gap set, every window except the lunch break (the personal calendar's busy time, the agent calendar's foreign events, the locked windows and a subset run's kept app events) is first widened by it on both sides (`padWindows`), so tasks keep the gap from every calendar event and from the tasks the run does not place.
4. Quota guard (full runs only, when there are unlocked tasks): fetch the weather (current conditions and the daily forecast for the first 3 local days; if the request fails the run goes on without it), then compute the fingerprint, a SHA-256 over a version constant, the time zone, location, `scheduleDays`, `scheduleOrder`, the daily window and, with the area preference on, its radius and deferral, the unlocked tasks' effective coordinates and the anchors, today's local date, the forecast key (`forecastKey`: one W (rainy) or D (dry) per forecast day, or the current WET/DRY/OTHER key when there is no forecast), the unlocked tasks' scheduling fields (id, title, priority, dueDate, estimatedMinutes, tags, recurrence, order, projectId, projectOrder, snoozedUntil; never the calendar or schedule fields), `gapMinutes` and the merged busy windows (a window clipped to now or to the horizon is reduced to the marker "now" or "horizon", so the clipping does not change the hash). An automatic run (`skipIfUnchanged`) returns `{skipped: true}` before scheduling anything, with no calendar change, when the fingerprint equals `lastRunFingerprint` and no unlocked task has a scheduled slot that has ended (`hasEndedSlot`; such a task is still on the list, so it forces a run). Manual runs and `rescheduleTask` always go through. A successful full run stores its fingerprint (a failure to store only logs a warning); a failed run stores nothing. Bump `FINGERPRINT_VERSION` whenever the planner or the engine rules change.
5. Get slots from the planner (`planSchedule` in `planner.js`, no model call): for each local day from today to the horizon's date it takes the daily window (`day`, default 9:00–17:00; cut to now and the horizon; starts are rounded up to 5 minutes) less the merged busy windows and the slots already placed. Tasks are taken most urgent first (`sortByUrgency`: overdue, then earliest due date, then undated; ties by priority, then rank) or, when `scheduleOrder` is `NUMBER`, in task number order (`sortByNumber`: `order`, ties in list order, so due dates and priority no longer decide who gets the earliest gap; the weather, snooze and project rules still apply), except that a task never comes before a lower-numbered member of its own project in the run. Each goes in the earliest gap that fits, so a short task can fill a gap a longer one skipped and days fill up before the next starts; with `gapMinutes` set, each task it places also blocks that long before and after itself, so consecutive tasks are at least that far apart (the busy windows arrive already widened by the gap, and all-day reminders get none). Tasks tagged Outdoor or Garden skip days outside the forecast window and rainy days (the same `weatherWindow` rule as below). Area preference (`travelGrouping` enabled; the engine reads projects and clients, resolves every task's `effectiveLocation` and passes the coordinates as `locations`): a task that is not overdue and not HIGH priority, has coordinates and gets a timed slot is placed, unless its earliest feasible day already holds a task within `radiusKm`, on the earliest day within `maxDeferDays` of that day, on or before its due date, that has a gap for it and already holds a task of the run or an anchor within `radiusKm`, otherwise as before; the weather, snooze, project-order and gap rules apply to that day as to any, and an all-day task counts as holding its day but is never moved. Anchors are the slots the run leaves in place and that have coordinates: pinned tasks, and in a subset run every other scheduled task. A task with `snoozedUntil` skips the days before that local date (one snoozed beyond the horizon gets no slot, and its `dropped` reason names the snooze date). A task starts after every lower-numbered member of its project has ended and ends before any fixed higher-numbered member starts; a task with a lower-numbered member that has no slot gets none. An estimate missing or unusable counts as 15 minutes. A task of 15 minutes or less is transparent, a longer one opaque, and one longer than the daily window becomes a transparent all-day reminder on the earliest allowed day. A task with no gap gets no slot and is reported in `dropped` with the reason. Skipped when every task is locked.
6. Validate (`repairSchedule`, built on the same per-slot checks as `validateSchedule`). A rejected slot of the planner's is a bug, so the run aborts with the old events kept, while an empty result is valid (nothing fits) and replaces the old events like any task left out (`repairSchedule` itself drops a slot that breaks a rule and keeps the rest). Per-slot rules: timed slots need an ISO time with offset, a start in the future, an end within the horizon, one local day inside the daily window, no overlap with busy windows; of two slots that overlap, or that are closer than `gapMinutes`, the earlier is kept. Snooze rule: a slot (timed or all-day) must fall on a local date on or after the task's `snoozedUntil`. Weather rule (`weatherWindow`, passed as `weather`): a slot of a task tagged Outdoor or Garden (timed or all-day) must fall on a local date inside the 3-day window that is not rainy; without a forecast a WET current condition makes every window day rainy; with no `weather` nothing is restricted. All-day slots (always transparent) need a date from today to the horizon date and skip overlap checks. Each task id must be an unlocked task; a repeated task keeps its first slot. Project order (`checkProjectOrder`, `projectOrderViolations`): within a project, every task of a tier must start at or after the end of every task of each lower tier (tasks sharing a number, members without a number and tasks outside a project are unconstrained); an all-day slot occupies its whole local date, so it compares by date. A violation drops the later-tier task of the run (or the run's lower-tier task when the later tier is fixed outside the run), repeated until none remains, so a dropped task takes the higher tiers of its project with it. The fixed project members count as slots, so a run must place its tasks after a fixed lower tier and before a fixed higher one; two fixed members are not checked against each other, and a fixed higher tier does not require its lower tiers to have slots. The result also lists `weatherMoves` (`weatherMoves` in `alerts.js`, worked out after the save from the tasks' old slots and the new ones: Outdoor or Garden tasks that were booked on a date now forecast rainy and are now on another date or none; locked tasks never), which the dispatcher turns into an alert. The result reports `heldCount` (held tasks among the run's tasks; `unscheduledCount` counts only tasks that were offered), `scheduleDays`, `lastScheduledDate` (the local date of the latest slot, null with none), `unscheduledCount` and `dropped` ([{taskId, reason}]).
7. Insert the new events on the agent calendar (all-day events use an exclusive end date). If an insert fails, delete the ones already created and abort.
8. Delete the old events (agent calendar only; already-missing ones are ignored), then save in a transaction onto the list as stored then (`applyScheduleResults`): only the schedule fields of tasks the run read are rewritten, so edits and additions made meanwhile survive, and events created for tasks deleted or completed meanwhile are removed. Each scheduled task gets `googleCalendarEventId`, `scheduledStart` and `scheduledEnd`. Each locked task gets `locked: true`, the personal event's id and its actual start and end. Other tasks have all four fields cleared.

`runScheduleEngine({taskIds})` runs the same steps for a subset: only those tasks are offered to the planner and have their events replaced (stored id plus events tagged with their `taskId`; orphans are left for full runs), every other app event on the agent calendar counts as busy whatever its transparency, and only the subset's schedule fields are rewritten. Locks are still detected across all tasks. `rescheduleTask` calls it with one id.

The cron and the manual trigger run the full engine and both use `USER_CALENDAR_ID`; neither the frontend nor the request chooses the calendar. All writes go to that calendar only. Busy time marked "free" (transparent) on either calendar does not count as busy, except locked windows. Deleting or completing a locked task never touches its event on the personal calendar.

## Roadmap

Each step fits in one turn. Do them in order unless told otherwise. Each step adds tests for any new pure logic.

Offline adds: a task added with no connection is kept on the device, shown on the Queue as waiting, and sent once the connection returns, once each and in order. Free-text and manual adds both queue; a queued add never starts a timer (`startNow` is dropped) and a queued free-text add is sent without `allowProposal`, so it never opens the project dialog. The queue model is in the page's pure-helpers block (`makeQueuedAdd`, `parseQueue`, `serializeQueue`, `isNetworkError`, `drainQueue`; their comments give the item shape and contracts). The page keeps the queue in `localStorage` (`ADD_QUEUE_KEY`, every access in try/catch; unavailable storage sets `addQueueUsable` false) and draws it at the top of the Queue, above the Active task, even before the task list loads (`renderAddQueue`: one card per item showing `queueCardView`, "Waiting to send" or the error, with Discard after a confirmation, `queueDiscardPrompt` and `queueWithout`). Nothing adds to the queue or sends it yet.

1. Sending (page): `drainQueue` wired to the page (one run at a time): on sign-in, on the window's `online` event, after any successful call, and from a Retry button on FAILED cards (resets it to PENDING and drains). It does not start without a signed-in user, and its `send` posts the item's `body` with `apiFetch`, marking a lost or rejected sign-in `keepQueued` so the item stays PENDING. A sent add updates the list with the response (`setTasks`), as `finishAdd` does; the cards update as each item finishes.
2. Go live (page): `submitTask` queues the add instead of alerting when the failure `isNetworkError` (the form clears as after an add; a full queue or unusable storage refuses with an alert).

## Open questions

- Should the page keep the last task list and show it offline? Offline adds queue only the adds; with no connection the Queue shows the load error and the waiting adds, not the tasks.
- Should Navigate follow the device's default maps app (the Navigate button)? A `geo:` link on Android or an Apple Maps link on iOS opens whatever app the device prefers, but shows the place rather than starting directions; the Google Maps link starts directions and opens in the app where it is installed. The plan uses the Google Maps link; change it if default-app behaviour matters more.
- Is the project suggestion reliable? A large multi-step job once skipped the dialog and was added as plain tasks, then worked after the prompt was reworded to say that stages the input lists itself still count (a model run-to-run difference is not ruled out). If a multi-stage job is added with no dialog, run `npm run logs` in `functions/` and find the line `No project suggestion (…)`: its reason says which check dropped it (the model returned no `projectProposal`, the name is unusable, too few or too many steps, the name matches an existing project, or the input names an existing project). "The model returned no projectProposal" means the prompt (`PROPOSAL_INSTRUCTIONS` in `prompts.js`) needs tuning; any other reason points at that check in `checkProposal`. No such line means the add did not reach the suggestion code (a free-text add with `allowProposal`), so check the request. Remove this question once it has held up over normal use.
- Does Google sign-in work in the installed Android window? The popup is tried first and the redirect fallback is in place, both untested there. If redirect sign-in fails on `taskhub-next.web.app`, set `authDomain` to the page's own host (that host's `/__/auth/handler` must then be an authorized redirect URI of the OAuth client).
- Public multi-user version: lock detection (an event moved to the personal calendar pins its task) lists events on the personal calendar, which a busy-time-only scope cannot do. Drop pinning in the public build, or request a broader read scope and accept a heavier review?
