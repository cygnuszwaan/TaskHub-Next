# TaskHub Next

An AI-enhanced to-do list that turns free-text input into structured tasks and schedules them onto Google Calendar. Single user. Location and time zone are runtime settings, defaulting to Whangaparāoa, NZ (Pacific/Auckland).

## Stack

- Firebase project `taskhub-next`. Hosting serves `public/`. Functions are v2 on Node 24, all in australia-southeast1 (set once with `setGlobalOptions` in `index.js`), as is Firestore.
- Calendar access uses service account `task-calendar-agent@gen-lang-client-0299359787.iam.gserviceaccount.com` (it lives in Google Cloud project `gen-lang-client-0299359787`, not `taskhub-next`). It has edit access to the agent calendar (`USER_CALENDAR_ID`) and "Make changes and see all event details" on the owner's personal calendar. The engine must only ever read the personal calendar, never write to it.
- `firebase.json` is tracked: the Firestore database, rules and indexes, the `functions` codebase (predeploy runs lint) and Hosting, which serves `public/` and rewrites every path to `/index.html` (existing files win, so the manifest, icons and `sw.js` are served as files; `sw.js` and the manifest are sent `no-cache`, the manifest as `application/manifest+json`).
- Setup and deploy commands are in `README.md`. `.firebaserc` defaults to `taskhub-next`, and the `deploy` and `logs` scripts in `functions/package.json` pass `--project taskhub-next`.
- Timeouts: the scheduling endpoints (`generateWeeklySchedule`, `rescheduleTask`), `autoScheduleDaily` and `addOrUpdateTask` allow 120 s; `getJobSheet` allows 60 s and 512 MiB (it holds the photos it prints).
- Firestore rules: deny-all. Every read and write goes through the functions via the Admin SDK, which bypasses rules.
- A separate app, a kids' chore tracker, lives in its own Firebase project (`screen-time-chore-tracker`). Never deploy to it from this repo; always target `taskhub-next` explicitly (`--project taskhub-next`).
- Frontend: one page, `public/index.html`, vanilla HTML/CSS/JS, no build step, installable as a standalone Android app (PWA): `public/manifest.webmanifest` (standalone, no `theme_color`, dark `background_color`, start `/`), `public/icons/` (192, 512, maskable 512 and the Apple touch icon, a white tick on blue) and `public/sw.js`, registered by the page. The page follows the device's light or dark setting until the owner uses the Dark mode checkbox (an Appearance card under the settings card on the Settings page, outside the saved form): it applies at once and is kept in `localStorage` (`taskhub-theme`, "light" or "dark", per device, never sent to the server). A saved choice sets `data-theme` on `<html>` (an inline script in the head does it before the first paint; `applyTheme` handles the rest), which overrides the device query; with none saved the checkbox shows the device's state and follows it when it changes. Every colour is a CSS variable on `:root` with its dark value in two identical blocks, under `@media (prefers-color-scheme: dark)` for `:root:not([data-theme="light"])` and for `:root[data-theme="dark"]`; `color-scheme` lets the browser draw dark form controls, and two `theme-color` metas (`data-scheme` light and dark) colour the browser UI, their `media` rewritten by `applyTheme` to match a choice (Android paints an installed app's bottom navigation bar from the manifest, which cannot follow the device's scheme, so the manifest has a dark `background_color` and no `theme_color`: the navigation bar and install splash are dark in both modes and the status bar follows the metas). ## Data model

- `tasks/{id}`: one document per active Task, the document id being the task's `id`. Read in `order` rank (sorted in code, so no index).
- `settings/app`: one document of runtime settings, read and written only through `getSettings`/`updateSettings`. Missing or unusable fields fall back to defaults in code (`settings.js`), so the document may be absent.
  - `location {name, latitude, longitude}`: default Whangaparāoa (-36.63, 174.78).
  - `timeZone`: IANA name, default Pacific/Auckland.
  - `scheduleDays`: how many days ahead a run schedules, a whole number 1..28, default 7.
  - `gapMinutes`: free minutes kept between scheduled tasks, a whole number 0..60, default 0.
  - `day {start "HH:MM", end "HH:MM"}`: the daily window tasks are scheduled in, at least 60 minutes long, `end` after `start`; default 09:00-17:00. A stored window that breaks this falls back to the default as a whole.
  - `lunch {enabled, time "HH:MM", minutes}`: a break kept free every day, `minutes` a whole number 5..180; default disabled, 12:00, 30 minutes.
  - `schedule {enabled, frequency DAILY|INTERVAL, time "HH:MM", intervalMinutes 15|30|60|120|240}`: default enabled, DAILY at 20:00 (`time` applies to DAILY, `intervalMinutes` to INTERVAL).
  - `jobSheet {contractorInfo}`: free text printed at the top of every job sheet, under its title; line breaks kept, trailing spaces and blank lines at either end removed, at most 1000 characters, default empty.
  - `lastAutoRunAt` (ISO; the start of the latest automatic run attempt, successful or not) and `lastRunFingerprint` (hex SHA-256 recorded by the latest successful full run, manual or automatic): run state, never settable through `updateSettings`.
  - The backend reads `location` and `timeZone` on every request that needs them (engine, weather, prompts, `addOrUpdateTask`, `completeTask`, `getCompletedTasks`) and `schedule` and `lastAutoRunAt` on every dispatcher tick.
- `projects/{id}`: one document per project, `{id, name}`, the document id being the project's id. Names are 1..100 characters and unique ignoring case. Read in name order (sorted in code, so no index).
- `completed_tasks/{auto-id}`: a copy of the Task plus `completedAt` and the job's history including this completion (`completedCount`, `recentSeconds`; rows archived before history was kept have neither, and `buildTemplates` derives them from the rows sharing the title); its `trackedSeconds` is always present (0 for a task never timed), its `firstStartedAt` is kept when the timer was ever started, and it has no `timerStartedAt` or `active`; rows archived before time tracking began have no `trackedSeconds`, and rows archived before `firstStartedAt` was kept have none. Written once at completion; afterwards only corrected by hand through `updateCompletedTask` and `deleteCompletedTask` (priority, estimate, tracked time, tags, materials, comments, project and completion time; the `completedCount` and `recentSeconds` snapshot on a row is never changed, so a correction does not reach the history already carried by later rows or by the live next occurrence of a repeating task).
- `completed_photos/{auto-id}`: one document per photo of a completed task, `{archiveId, data (base64 JPEG), bytes (decoded size), addedAt}`, at most 3 per `archiveId`, kept out of the archive row so the stats scans stay light. Removed with their archive row by `deleteCompletedTask` and `undoRemove`; printed on job sheets; left out of `exportData`.
- `settings/lastRemoved`: one document, replaced by every delete (`updateTaskDirect` DELETE) and completion (`completeTask`) in the same transaction: `{kind: "DELETE"|"COMPLETE", task, archiveId, spawnedId, at}` (`removalRecord`). Only `undoRemove` reads it, and it counts for 10 minutes (`isUndoable`).
- Task: `id`, `title`, `priority` (HIGH/MEDIUM/LOW), `dueDate` (YYYY-MM-DD or empty), `estimatedMinutes`, `tags[]`, `status` (PENDING/COMPLETED), `googleCalendarEventId`, `scheduledStart`/`scheduledEnd` (set only while scheduled; ISO 8601 with the local UTC offset, or YYYY-MM-DD with an exclusive end date for all-day), `locked` (true only while the owner has pinned the task by moving its event to the personal calendar), `recurrence` (optional `{frequency: DAILY|WEEKLY|MONTHLY|YEARLY, interval: 1..365}`; the key is absent for a task that does not repeat; completing the task spawns its next occurrence), `projectId` (optional; the project the task belongs to, the key is absent outside any project) and `materials` (optional list `[{id, text, checked}]`, manually written in the edit form or the manual add form, never set by Gemini; text 1..100 characters, at most 30 items; the key is absent when there are none; a task with an unchecked item is held back from the schedule, see the scheduling engine), `snoozedUntil` (optional local date YYYY-MM-DD: the scheduler does not place the task before that day; the due date is untouched; a date that is not after today restricts nothing and is left as stored; the key is absent when not snoozed; set by `updateTaskDirect` and, as a cooldown, by `completeTask` on the next occurrence of a repeating task (equal to its `dueDate`); never by Gemini; any other snooze is not carried to the next occurrence), `addedAt` (ISO timestamp of when the task was created, set by the server on every new task, including the next occurrence of a repeating task; never set by Gemini or changed by an edit; absent on tasks created before it existed), `trackedSeconds` (optional whole number of seconds accrued on the task's timer, absent until first used; kept when the timer is paused) and `firstStartedAt` (optional ISO instant the timer was first started on the task, set once by the first START and never moved by later starts, pauses or edits; kept on the archive row; not carried to the next occurrence of a repeating task, nor to a copy) and `timerStartedAt` (optional ISO instant the running timer started, absent while paused; at most one task has it) and `active` (optional `true` on the task whose timer was started last, kept through a pause and taken away by the next start on another task; at most one task has it; all four are set only by `toggleTimer` and the server's clock, never by Gemini or an edit, and none is carried to the next occurrence of a repeating task), `comments` (optional text, 1..2000 characters, trimmed; free notes the owner writes in the edit form or the manual add form; never read or shown to Gemini, and set by it only on the steps of a suggested project the owner accepts (see `addOrUpdateTask`); the key is absent when empty; carried to the next occurrence of a repeating task), `completedCount` (optional whole number >= 1: how many times this job has been completed before this instance) and `recentSeconds` (optional list of up to 5 whole numbers: the tracked seconds of the job's latest completions that had any, oldest first; the rolling average of these, rounded to the nearest 5 minutes and at least 5, is the estimate of the next occurrence of a repeating task and of a task copied from a completed one; both are the job's history, carried forward to the next occurrence and to a copy, set by the server on completion, by a manual add from a copied completed task, never by Gemini or an edit, and absent on a job never completed), `projectOrder` (optional whole number 1..999, only with `projectId`; members of a project sharing a number form a tier that the scheduling engine places after every lower tier, and a member without one is unordered; leaving a project or moving to another clears it; unrelated to `order`), `order` (rank from 1, renumbered 1..n whenever tasks are added or reranked; new ids are server-generated UUIDs).

`autoScheduleDaily` ticks every 15 minutes (the Cloud Scheduler cron is fixed at deploy, and 15 minutes is the finest interval offered). Each tick calls `claimAutoRun`, one transaction that checks `isRunDue` against `settings/app` and, if due, records `lastAutoRunAt`; only a tick that gets `due: true` runs the full engine, so a duplicate delivery cannot start a second run. A disabled schedule never runs. DAILY runs once the local time in the configured zone has reached `time`, if the last attempt was not on today's local date (a missed tick catches up on the next one; a `time` already passed today runs at the next tick). INTERVAL runs when `intervalMinutes` have passed since `lastAutoRunAt` (with a one-minute grace for tick jitter) and only between 8:00 and 20:00 local (20:00 itself excluded); a first run happens at the first tick in that window. The attempt is recorded when the run starts, so a failing run is not retried until the next due time (Update now still works) and a failure is only logged. A due automatic run that finds nothing changed is skipped (see the scheduling engine); the attempt still counts, so the next run waits for the next due time.

Every write to `tasks` is a Firestore transaction (via `updateTaskList` in `store.js`: it reads the whole collection, runs the modification, and writes only the tasks that changed or were removed). `addOrUpdateTask` calls Gemini outside the transaction and merges its changes into the list as stored at commit time: a change naming a task that no longer exists is skipped, and id, status, calendar and schedule fields, and `locked` are never taken from the model; its `projectId` counts only when it names a project stored at commit time (the transaction reads `projects` too), and its `projectOrder` only as a number, both applied through `applyProjectFields`. `completeTask` commits the archive write and the list removal together. Calendar cleanup runs after the commit.

Deleting or completing a task removes its calendar events by stored `googleCalendarEventId` and by the `taskId` private extended property on the event, so a task whose stored id was lost still gets cleaned up.

## Scheduling engine (`runScheduleEngine`)

Nothing on the calendar changes until the slots pass validation. The personal calendar is only ever read. A task is held (not scheduled) while it has an unchecked material, and so are the members of its project with a higher order number than the lowest held one; a locked task is never held and holds no one. A snoozed task is not held: it is scheduled, but not before its snooze date (steps 5 and 6).

1. Load tasks. Read the personal calendar's free/busy from now to the horizon (`scheduleDays` days ahead, default 7).
2. Lock detection: list the events ending after now on the personal calendar that carry the marker "Generated by AI Task Agent", and match each to a task (`matchLockedEvents`: stored `googleCalendarEventId`, then the `taskId` private extended property, then title). A matched task is locked (and never held): it is not offered to the planner, its old events are not deleted, and its event window counts as busy even if the event is marked free. Locks are recomputed on every run, so a lock is released once its event has ended. If either read in this step fails, abort.
3. Held tasks (`heldTaskIds`, over all tasks) are left out of the request but count as replaced: their old events are deleted and their schedule fields cleared, like those of tasks the planner leaves out. List the agent calendar's existing app events from the start of today in the configured time zone. The events to replace are the stored ids of the unlocked tasks being scheduled plus every event carrying the marker. Collect agent-calendar busy time from opaque events that are not the app's own (events list, not free/busy, so the app's old events don't block rescheduling). Merge it with the personal and locked windows (overlaps combined) and the lunch break (`lunchWindows`: with `lunch` enabled, one window per local day from now to the horizon, cut to that range, so it is busy time for the planner, the validation and the fingerprint); with a gap set, every window except the lunch break (the personal calendar's busy time, the agent calendar's foreign events, the locked windows and a subset run's kept app events) is first widened by it on both sides (`padWindows`), so tasks keep the gap from every calendar event and from the tasks the run does not place.
4. Quota guard (full runs only, when there are unlocked tasks): fetch the weather (current conditions and the daily forecast for the first 3 local days; if the request fails the run goes on without it), then compute the fingerprint, a SHA-256 over a version constant, the time zone, location, `scheduleDays` and the daily window, today's local date, the forecast key (`forecastKey`: one W (rainy) or D (dry) per forecast day, or the current WET/DRY/OTHER key when there is no forecast), the unlocked tasks' scheduling fields (id, title, priority, dueDate, estimatedMinutes, tags, recurrence, order, projectId, projectOrder, snoozedUntil; never the calendar or schedule fields), `gapMinutes` and the merged busy windows (a window clipped to now or to the horizon is reduced to the marker "now" or "horizon", so the clipping does not change the hash). An automatic run (`skipIfUnchanged`) returns `{skipped: true}` before scheduling anything, with no calendar change, when the fingerprint equals `lastRunFingerprint` and no unlocked task has a scheduled slot that has ended (`hasEndedSlot`; such a task is still on the list, so it forces a run). Manual runs and `rescheduleTask` always go through. A successful full run stores its fingerprint (a failure to store only logs a warning); a failed run stores nothing. Bump `FINGERPRINT_VERSION` whenever the planner or the engine rules change.
5. Get slots from the planner (`planSchedule` in `planner.js`, no model call): for each local day from today to the horizon's date it takes the daily window (`day`, default 9:00–17:00; cut to now and the horizon; starts are rounded up to 5 minutes) less the merged busy windows and the slots already placed. Tasks are taken most urgent first (`sortByUrgency`: overdue, then earliest due date, then undated; ties by priority, then rank), except that a task never comes before a lower-numbered member of its own project in the run. Each goes in the earliest gap that fits, so a short task can fill a gap a longer one skipped and days fill up before the next starts; with `gapMinutes` set, each task it places also blocks that long before and after itself, so consecutive tasks are at least that far apart (the busy windows arrive already widened by the gap, and all-day reminders get none). Tasks tagged Outdoor or Garden skip days outside the forecast window and rainy days (the same `weatherWindow` rule as below). A task with `snoozedUntil` skips the days before that local date (one snoozed beyond the horizon gets no slot, and its `dropped` reason names the snooze date). A task starts after every lower-numbered member of its project has ended and ends before any fixed higher-numbered member starts; a task with a lower-numbered member that has no slot gets none. An estimate missing or unusable counts as 15 minutes. A task of 15 minutes or less is transparent, a longer one opaque, and one longer than the daily window becomes a transparent all-day reminder on the earliest allowed day. A task with no gap gets no slot and is reported in `dropped` with the reason. Skipped when every task is locked.
6. Validate (`repairSchedule`, built on the same per-slot checks as `validateSchedule`). A rejected slot of the planner's is a bug, so the run aborts with the old events kept, while an empty result is valid (nothing fits) and replaces the old events like any task left out (`repairSchedule` itself drops a slot that breaks a rule and keeps the rest). Per-slot rules: timed slots need an ISO time with offset, a start in the future, an end within the horizon, one local day inside the daily window, no overlap with busy windows; of two slots that overlap, or that are closer than `gapMinutes`, the earlier is kept. Snooze rule: a slot (timed or all-day) must fall on a local date on or after the task's `snoozedUntil`. Weather rule (`weatherWindow`, passed as `weather`): a slot of a task tagged Outdoor or Garden (timed or all-day) must fall on a local date inside the 3-day window that is not rainy; without a forecast a WET current condition makes every window day rainy; with no `weather` nothing is restricted. All-day slots (always transparent) need a date from today to the horizon date and skip overlap checks. Each task id must be an unlocked task; a repeated task keeps its first slot. Project order (`checkProjectOrder`, `projectOrderViolations`): within a project, every task of a tier must start at or after the end of every task of each lower tier (tasks sharing a number, members without a number and tasks outside a project are unconstrained); an all-day slot occupies its whole local date, so it compares by date. A violation drops the later-tier task of the run (or the run's lower-tier task when the later tier is fixed outside the run), repeated until none remains, so a dropped task takes the higher tiers of its project with it. The fixed project members count as slots, so a run must place its tasks after a fixed lower tier and before a fixed higher one; two fixed members are not checked against each other, and a fixed higher tier does not require its lower tiers to have slots. The result reports `heldCount` (held tasks among the run's tasks; `unscheduledCount` counts only tasks that were offered), `scheduleDays`, `lastScheduledDate` (the local date of the latest slot, null with none), `unscheduledCount` and `dropped` ([{taskId, reason}]).
7. Insert the new events on the agent calendar (all-day events use an exclusive end date). If an insert fails, delete the ones already created and abort.
8. Delete the old events (agent calendar only; already-missing ones are ignored), then save in a transaction onto the list as stored then (`applyScheduleResults`): only the schedule fields of tasks the run read are rewritten, so edits and additions made meanwhile survive, and events created for tasks deleted or completed meanwhile are removed. Each scheduled task gets `googleCalendarEventId`, `scheduledStart` and `scheduledEnd`. Each locked task gets `locked: true`, the personal event's id and its actual start and end. Other tasks have all four fields cleared.

`runScheduleEngine({taskIds})` runs the same steps for a subset: only those tasks are offered to the planner and have their events replaced (stored id plus events tagged with their `taskId`; orphans are left for full runs), every other app event on the agent calendar counts as busy whatever its transparency, and only the subset's schedule fields are rewritten. Locks are still detected across all tasks. `rescheduleTask` calls it with one id.

The cron and the manual trigger run the full engine and both use `USER_CALENDAR_ID`; neither the frontend nor the request chooses the calendar. All writes go to that calendar only. Busy time marked "free" (transparent) on either calendar does not count as busy, except locked windows. Deleting or completing a locked task never touches its event on the personal calendar.

### Public multi-user version

Target: one hosted copy that anyone signs into with Google and grants Calendar access through a consent screen, with no CLI, no Firebase project, no API keys and no calendar shared with a service account. Concessions: no Gemini (manual entry only) and one calendar (an app-created "TaskHub" calendar the tasks are written to, plus read-only busy time from the user's main calendar). The pure modules (planner, schedule, recurrence, history, settings and the rest) are user-agnostic and carry over unchanged. Constraints outside the code:
- Every Calendar scope is sensitive, so Google's app verification is required beyond its testing limits; until then users see an "unverified app" warning and at most 100 can authorize. Review can take weeks.
- Cloud Functions need the pay-as-you-go (Blaze) plan on the hosting project; the free quotas still apply.
- Holding other people's calendar tokens and tasks means a privacy policy, deletion on request and care with security.
- A first release can go to a small circle under the 100-user cap, with the warning screen, and verification deferred until it outgrows that.

1. Per-user data: move `tasks`, `projects`, `completed_tasks`, `settings/app` and `settings/lastRemoved` under `users/{uid}/` by giving `makeTaskStore`, `makeProjectStore` and `makeSettingsStore` a uid, threaded through every endpoint; migrate the owner's existing data; the rules stay deny-all.
2. Auth: replace `ownerOnly` with a check that returns the verified uid of any Google account; drop `OWNER_EMAIL`; every endpoint reads and writes only that uid's data.
3. Calendar OAuth: a server-side consent flow (authorization code, offline access) that stores each user's refresh token encrypted, with the key in Secret Manager; `calendar.js` builds its client from the user's token instead of the service account; a revoked or expired token shows a reconnect prompt instead of failing silently. Use the narrowest scopes that work (`calendar.app.created` plus a busy-time read).
4. One calendar: on first connect create the app's own calendar and use it as the agent calendar; read busy time from the user's main calendar only; remove the `USER_CALENDAR_ID` and `USER_PERSONAL_CALENDAR_ID` params.

## Open questions

- Is the project suggestion reliable? A large multi-step job once skipped the dialog and was added as plain tasks, then worked after the prompt was reworded to say that stages the input lists itself still count (a model run-to-run difference is not ruled out). If a multi-stage job is added with no dialog, run `npm run logs` in `functions/` and find the line `No project suggestion (…)`: its reason says which check dropped it (the model returned no `projectProposal`, the name is unusable, too few or too many steps, the name matches an existing project, the input names an existing project, or the model put a task into one). "The model returned no projectProposal" means the prompt (`PROPOSAL_INSTRUCTIONS` in `prompts.js`) needs tuning; any other reason points at that check in `checkProposal`. No such line means the add did not reach the suggestion code (a free-text add with `allowProposal`), so check the request. Remove this question once it has held up over normal use.
- Does Google sign-in work in the installed Android window? The popup is tried first and the redirect fallback is in place, both untested there. If redirect sign-in fails on `taskhub-next.web.app`, set `authDomain` to the page's own host (that host's `/__/auth/handler` must then be an authorized redirect URI of the OAuth client).
- Public multi-user version: lock detection (an event moved to the personal calendar pins its task) lists events on the personal calendar, which a busy-time-only scope cannot do. Drop pinning in the public build, or request a broader read scope and accept a heavier review?
