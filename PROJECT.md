# TaskHub Next

An AI-enhanced to-do list that turns free-text input into structured tasks and schedules them onto Google Calendar. Single user. Location and time zone are runtime settings, defaulting to Whangaparāoa, NZ (Pacific/Auckland).

## Data model

- `tasks/{id}`: one document per active Task, the document id being the task's `id`. Read in `order` rank (sorted in code, so no index).
- `settings/app`: one document of runtime settings, read and written only through `getSettings`/`updateSettings`. Missing or unusable fields fall back to defaults in code (`settings.js`), so the document may be absent.
  - `location {name, latitude, longitude}`: default Whangaparāoa (-36.63, 174.78).
  - `timeZone`: IANA name, default Pacific/Auckland.
  - `scheduleDays`: how many days ahead a run schedules, a whole number 1..28, default 7.
  - `gapMinutes`: free minutes kept between scheduled tasks, a whole number 0..60, default 0.
  - `day {start "HH:MM", end "HH:MM"}`: the daily window tasks are scheduled in, at least 60 minutes long, `end` after `start`; default 09:00-17:00. A stored window that breaks this falls back to the default as a whole.
  - `lunch {enabled, time "HH:MM", minutes}`: a break kept free every day, `minutes` a whole number 5..180; default disabled, 12:00, 30 minutes.
  - `schedule {enabled, frequency DAILY|INTERVAL, time "HH:MM", intervalMinutes 15|30|60|120|240}`: default enabled, DAILY at 20:00 (`time` applies to DAILY, `intervalMinutes` to INTERVAL).
  - `lastAutoRunAt` (ISO; the start of the latest automatic run attempt, successful or not) and `lastRunFingerprint` (hex SHA-256 recorded by the latest successful full run, manual or automatic): run state, never settable through `updateSettings`.
  - The backend reads `location` and `timeZone` on every request that needs them (engine, weather, prompts, `addOrUpdateTask`, `completeTask`, `getCompletedTasks`) and `schedule` and `lastAutoRunAt` on every dispatcher tick.
- `projects/{id}`: one document per project, `{id, name}`, the document id being the project's id. Names are 1..100 characters and unique ignoring case. Read in name order (sorted in code, so no index).
- `completed_tasks/{auto-id}`: a copy of the Task plus `completedAt`. Write-only archive for future analytics.
- Task: `id`, `title`, `priority` (HIGH/MEDIUM/LOW), `dueDate` (YYYY-MM-DD or empty), `estimatedMinutes`, `tags[]`, `status` (PENDING/COMPLETED), `googleCalendarEventId`, `scheduledStart`/`scheduledEnd` (set only while scheduled; ISO 8601 with the local UTC offset, or YYYY-MM-DD with an exclusive end date for all-day), `locked` (true only while the owner has pinned the task by moving its event to the personal calendar), `recurrence` (optional `{frequency: DAILY|WEEKLY|MONTHLY|YEARLY, interval: 1..365}`; the key is absent for a task that does not repeat; completing the task spawns its next occurrence), `projectId` (optional; the project the task belongs to, the key is absent outside any project) and `materials` (optional list `[{id, text, checked}]`, manually written in the edit form, never set by Gemini; text 1..100 characters, at most 30 items; the key is absent when there are none; a task with an unchecked item is held back from the schedule, see the scheduling engine), `projectOrder` (optional whole number 1..999, only with `projectId`; members of a project sharing a number form a tier that the scheduling engine places after every lower tier, and a member without one is unordered; leaving a project or moving to another clears it; unrelated to `order`), `order` (rank from 1, renumbered 1..n whenever tasks are added or reranked; new ids are server-generated UUIDs).

## Endpoints

| Function | Purpose | AI |
|---|---|---|
| `getTasks` | Read the active list | No |
| `addOrUpdateTask` | Free text in; Gemini returns only new or changed tasks (title, priority, dueDate, estimatedMinutes, tags, recurrence, rank), merged server-side. With a `manual` body `{title, priority?, dueDate?, estimatedMinutes?, tags?}` instead of `input` no model is called: the task is added at the end of the list with the fields validated like the model's (an unusable one takes the new-task default; 400 without a title), and it has no recurrence, project or materials until edited. Omitting `recurrence` leaves an existing task's unchanged; frequency NONE removes it. May set `projectId` (an existing project's id) and `projectOrder`, which put a new task into a project or move or reorder an existing one; omitting them, an empty, null or unknown value changes nothing, so it never removes a task from a project or clears an order number, and it cannot create, rename or delete projects, and it never reads or changes `materials`. Cannot delete or complete tasks | Yes |
| `updateTaskDirect` | UPDATE or DELETE one task by id; DELETE also removes its calendar events. An UPDATE's `recurrence` is validated (null or frequency NONE removes it, an unusable value is ignored), and so are `projectId` (null or empty leaves the project, an id that is not a stored project is ignored; checked against the projects at commit time) and `projectOrder` (null clears it; ignored for a task outside a project), and `materials` (validated by `normalizeMaterials`: items without text are dropped, ids that are missing, invalid or repeated are regenerated, null or an empty list removes it, an unusable value is ignored) | No |
| `getCompletedTasks` | Read the newest entries of `completed_tasks`, newest first (`?limit=`, default 50, at most 200), plus `summary` over the last 8 local weeks (Monday start, current week included, from up to 1000 archive rows regardless of `limit`): `totalCount`, `totalMinutes`, per-week, per-priority and per-tag `count` and `minutes`, and `truncated` when the window held more rows than were read | No |
| `completeTask` | Archive to `completed_tasks`, remove from the list, remove its calendar events. A recurring task also gets its next occurrence in the same transaction (`completeInList`): same title, priority, estimate, tags, recurrence, project and order number, and materials (all unchecked, with new ids), the completed task's rank, PENDING, no schedule, and a `dueDate` stepped forward from the old one in whole intervals until it is after today in the configured time zone (finishing early keeps the rhythm, finishing late skips missed occurrences; no due date counts from today; month ends clamp without drifting). The response includes `spawned` (the new task or null) | No |
| `generateWeeklySchedule` | Manual full run, the "Update now" button | Only when `SCHEDULER` is `gemini` |
| `rescheduleTask` | Replace one task's calendar event (engine run for that task only). 404 for an unknown task, 409 when the task is pinned to the personal calendar or is held back for materials | Only when `SCHEDULER` is `gemini` |
| `autoScheduleDaily` | Dispatcher on a 15-minute cron (not HTTP; see below); runs the same engine when the settings say a run is due, skipping it when nothing changed since the last full run | Only when `SCHEDULER` is `gemini` |
| `getSettings` | Read `settings/app` with defaults filled in | No |
| `getProjects` | Read all projects, sorted by name | No |
| `updateProject` | Body `{action, projectId?, name?}`: `CREATE` (name), `UPDATE` (rename) or `DELETE`; 400 with the reason for an unusable or taken name or an unknown action, 404 for an unknown `projectId`. `DELETE` takes the project out of its member tasks (the tasks stay); the response includes `projects` and, for `DELETE`, `tasks`. No calendar changes | No |
| `updateSettings` | Body `{settings: {location?, timeZone?, scheduleDays?, gapMinutes?, day?, lunch?, schedule?}}`, any subset of the editable fields, validated (IANA zone, latitude -90..90, longitude -180..180, name 1..100 characters, `scheduleDays` a whole number 1..28, `gapMinutes` a whole number 0..60, `day.start` and `day.end` `HH:MM` with `end` at least 60 minutes after `start` (checked on the merged result, so one end can be sent alone), `lunch.enabled` a boolean, `lunch.minutes` a whole number 5..180, `HH:MM`, interval from the allowed list) and merged in a transaction; 400 with the reason and nothing saved when a field is invalid | No |

Every HTTP endpoint requires `Authorization: Bearer <Firebase ID token>` for the verified Google account in `OWNER_EMAIL` (`ownerOnly`): 401 for a missing or invalid token, 403 for any other account or when `OWNER_EMAIL` is empty. Revocation takes effect when the current token expires (up to an hour). CORS allows only `https://taskhub-next.web.app` and `https://taskhub-next.firebaseapp.com` (`ALLOWED_ORIGINS`), so localhost is rejected. `autoScheduleDaily` is not HTTP and is unaffected.

`autoScheduleDaily` ticks every 15 minutes (the Cloud Scheduler cron is fixed at deploy, and 15 minutes is the finest interval offered). Each tick calls `claimAutoRun`, one transaction that checks `isRunDue` against `settings/app` and, if due, records `lastAutoRunAt`; only a tick that gets `due: true` runs the full engine, so a duplicate delivery cannot start a second run. A disabled schedule never runs. DAILY runs once the local time in the configured zone has reached `time`, if the last attempt was not on today's local date (a missed tick catches up on the next one; a `time` already passed today runs at the next tick). INTERVAL runs when `intervalMinutes` have passed since `lastAutoRunAt` (with a one-minute grace for tick jitter) and only between 8:00 and 20:00 local (20:00 itself excluded); a first run happens at the first tick in that window. The attempt is recorded when the run starts, so a failing run is not retried until the next due time (Update now still works) and a failure is only logged. A due automatic run that finds nothing changed is skipped (see the scheduling engine); the attempt still counts, so the next run waits for the next due time.

Every write to `tasks` is a Firestore transaction (via `updateTaskList` in `store.js`: it reads the whole collection, runs the modification, and writes only the tasks that changed or were removed). `addOrUpdateTask` calls Gemini outside the transaction and merges its changes into the list as stored at commit time: a change naming a task that no longer exists is skipped, and id, status, calendar and schedule fields, and `locked` are never taken from the model; its `projectId` counts only when it names a project stored at commit time (the transaction reads `projects` too), and its `projectOrder` only as a number, both applied through `applyProjectFields`. `completeTask` commits the archive write and the list removal together. Calendar cleanup runs after the commit.

Deleting or completing a task removes its calendar events by stored `googleCalendarEventId` and by the `taskId` private extended property on the event, so a task whose stored id was lost still gets cleaned up.

## Scheduling engine (`runScheduleEngine`)

Nothing on the calendar changes until the slots pass validation. The personal calendar is only ever read. A task is held (not scheduled) while it has an unchecked material, and so are the members of its project with a higher order number than the lowest held one; a locked task is never held and holds no one.

1. Load tasks. Read the personal calendar's free/busy from now to the horizon (`scheduleDays` days ahead, default 7).
2. Lock detection: list the events ending after now on the personal calendar that carry the marker "Generated by AI Task Agent", and match each to a task (`matchLockedEvents`: stored `googleCalendarEventId`, then the `taskId` private extended property, then title). A matched task is locked (and never held): it is not offered to Gemini, its old events are not deleted, and its event window counts as busy even if the event is marked free. Locks are recomputed on every run, so a lock is released once its event has ended. If either read in this step fails, abort.
3. Held tasks (`heldTaskIds`, over all tasks) are left out of the request but count as replaced: their old events are deleted and their schedule fields cleared, like those of tasks Gemini leaves out. List the agent calendar's existing app events from the start of today in the configured time zone. The events to replace are the stored ids of the unlocked tasks being scheduled plus every event carrying the marker. Collect agent-calendar busy time from opaque events that are not the app's own (events list, not free/busy, so the app's old events don't block rescheduling). Merge it with the personal and locked windows (overlaps combined) and the lunch break (`lunchWindows`: with `lunch` enabled, one window per local day from now to the horizon, cut to that range, so it is busy time for both schedulers, the validation and the fingerprint); with a gap set, every window except the lunch break (the personal calendar's busy time, the agent calendar's foreign events, the locked windows and a subset run's kept app events) is first widened by it on both sides (`padWindows`), so tasks keep the gap from every calendar event and from the tasks the run does not place; Gemini, when it schedules, gets only those time windows, never event titles.
4. Quota guard (full runs only, when there are unlocked tasks): fetch the weather (current conditions and the daily forecast for the first 3 local days; if the request fails the run goes on without it), then compute the fingerprint, a SHA-256 over a version constant, the scheduler, the time zone, location, `scheduleDays` and the daily window, today's local date, the forecast key (`forecastKey`: one W (rainy) or D (dry) per forecast day, or the current WET/DRY/OTHER key when there is no forecast), the unlocked tasks' scheduling fields (id, title, priority, dueDate, estimatedMinutes, tags, recurrence, order, projectId, projectOrder; never the calendar or schedule fields), `gapMinutes` and the merged busy windows (a window clipped to now or to the horizon is reduced to the marker "now" or "horizon", so the clipping does not change the hash). An automatic run (`skipIfUnchanged`) returns `{skipped: true}` before scheduling anything, with no calendar change, when the fingerprint equals `lastRunFingerprint` and no unlocked task has a scheduled slot that has ended (`hasEndedSlot`; such a task is still on the list, so it forces a run). Manual runs and `rescheduleTask` always go through. A successful full run stores its fingerprint (a failure to store only logs a warning); a failed run stores nothing. Bump `FINGERPRINT_VERSION` whenever the prompt, the planner or the engine rules change.
5. Get slots from the scheduler `SCHEDULER` names (a constant in `index.js`, `deterministic` by default; changing it re-runs the schedule). Deterministic (`planSchedule` in `planner.js`, no model call): for each local day from today to the horizon's date it takes the daily window (`day`, default 9:00–17:00; cut to now and the horizon; starts are rounded up to 5 minutes) less the merged busy windows and the slots already placed. Tasks are taken most urgent first (`sortByUrgency`: overdue, then earliest due date, then undated; ties by priority, then rank), except that a task never comes before a lower-numbered member of its own project in the run. Each goes in the earliest gap that fits, so a short task can fill a gap a longer one skipped and days fill up before the next starts; with `gapMinutes` set, each task it places also blocks that long before and after itself, so consecutive tasks are at least that far apart (the busy windows arrive already widened by the gap, and all-day reminders get none). Tasks tagged Outdoor or Garden skip days outside the forecast window and rainy days (the same `weatherWindow` rule as below). A task starts after every lower-numbered member of its project has ended and ends before any fixed higher-numbered member starts; a task with a lower-numbered member that has no slot gets none. An estimate missing or unusable counts as 15 minutes. A task of 15 minutes or less is transparent, a longer one opaque, and one longer than the daily window becomes a transparent all-day reminder on the earliest allowed day. A task with no gap gets no slot and is reported in `dropped` with the reason. Gemini (`requestValidSchedule` calls `requestSchedule` and step 6's repair; `scheduleDays` is stated in the prompt; tasks go in the earliest gaps, so the schedule ends well before the horizon when the tasks fit sooner; it reads the projects) is prompted with the current local time, the zone and its real UTC offset (for example +12:00 or +13:00 depending on daylight saving), today's local date, the current weather and the daily forecast (date, conditions, temperatures, precipitation, rain chance and a `rainy` flag: a wet dominant condition or at least 1 mm) at the configured location, the merged busy windows, the unlocked tasks (each member of a project carries its project name, `projectId` and `projectOrder`) and the fixed project members (project name, order number and window of every ordered member the run does not place: locked tasks, and in a subset run every other scheduled task). Tasks are annotated and ordered by `annotateDue` (`overdue`, `daysUntilDue`; most overdue first, then earliest due, then undated), and the prompt tells Gemini to place overdue tasks first and, where possible, on or before their due date; a missed due date is not a validation failure. Project order wins over due dates and priority; where a task cannot be scheduled, the prompt has Gemini leave out the higher tiers of its project too. Gemini's rules: the daily window in local time in the configured zone, at least `gapMinutes` between two slots (stated only when the gap is above 0), opaque for focus tasks and transparent for quick chores, tasks tagged Outdoor or Garden only inside the first 3 local days (`WEATHER_DAYS`, the days with a forecast) and never on a day the forecast marks rainy (without a forecast the current conditions stand in for those 3 days), and never later, since the weather there is unknown; other tasks ignore the weather; each task at most once. Skipped when every task is locked.
6. Validate and repair (`repairSchedule`, built on the same per-slot checks as `validateSchedule`). The planner's slots go through the same checks; there a rejected slot is a bug, so the run aborts with the old events kept, while an empty result is valid (nothing fits) and replaces the old events like any task left out. Gemini is asked up to 3 times (`SCHEDULE_ATTEMPTS`, each request cut off after 60 s): a failed request (overload, timeout, cut-off or malformed JSON; `parseScheduleResponse`) is retried after a pause, and an answer with no usable slot is retried with its problems listed in the prompt. A slot that breaks a rule is dropped and the task is left unscheduled; the rest of the schedule is kept. Only when no attempt yields a slot does the run abort and keep the old events. Per-slot rules: timed slots need an ISO time with offset, a start in the future, an end within the horizon, one local day inside the daily window, no overlap with busy windows; of two slots that overlap, or that are closer than `gapMinutes`, the earlier is kept. Weather rule (`weatherWindow`, passed as `weather`): a slot of a task tagged Outdoor or Garden (timed or all-day) must fall on a local date inside the 3-day window that is not rainy; without a forecast a WET current condition makes every window day rainy; with no `weather` nothing is restricted. All-day slots (always transparent) need a date from today to the horizon date and skip overlap checks. Each task id must be an unlocked task; a repeated task keeps its first slot. Project order (`checkProjectOrder`, `projectOrderViolations`): within a project, every task of a tier must start at or after the end of every task of each lower tier (tasks sharing a number, members without a number and tasks outside a project are unconstrained); an all-day slot occupies its whole local date, so it compares by date. A violation drops the later-tier task of the run (or the run's lower-tier task when the later tier is fixed outside the run), repeated until none remains, so a dropped task takes the higher tiers of its project with it. The fixed project members count as slots, so a run must place its tasks after a fixed lower tier and before a fixed higher one; two fixed members are not checked against each other, and a fixed higher tier does not require its lower tiers to have slots. The result reports `heldCount` (held tasks among the run's tasks; `unscheduledCount` counts only tasks that were offered), `scheduleDays`, `lastScheduledDate` (the local date of the latest slot, null with none), `unscheduledCount` and `dropped` ([{taskId, reason}]).
7. Insert the new events on the agent calendar (all-day events use an exclusive end date). If an insert fails, delete the ones already created and abort.
8. Delete the old events (agent calendar only; already-missing ones are ignored), then save in a transaction onto the list as stored then (`applyScheduleResults`): only the schedule fields of tasks the run read are rewritten, so edits and additions made meanwhile survive, and events created for tasks deleted or completed meanwhile are removed. Each scheduled task gets `googleCalendarEventId`, `scheduledStart` and `scheduledEnd`. Each locked task gets `locked: true`, the personal event's id and its actual start and end. Other tasks have all four fields cleared.

`runScheduleEngine({taskIds})` runs the same steps for a subset: only those tasks are offered to the scheduler and have their events replaced (stored id plus events tagged with their `taskId`; orphans are left for full runs), every other app event on the agent calendar counts as busy whatever its transparency, and only the subset's schedule fields are rewritten. Locks are still detected across all tasks. `rescheduleTask` calls it with one id.

The cron and the manual trigger run the full engine and both use `USER_CALENDAR_ID`; neither the frontend nor the request chooses the calendar. All writes go to that calendar only. Busy time marked "free" (transparent) on either calendar does not count as busy, except locked windows. Deleting or completing a locked task never touches its event on the personal calendar.
