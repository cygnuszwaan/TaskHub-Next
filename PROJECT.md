# AI Task Agent

An AI-enhanced to-do list that turns free-text input into structured tasks and schedules them onto Google Calendar. Single user, based in Whangaparāoa, NZ (Pacific/Auckland).

## Stack

- Firebase project `taskhub-next`. Hosting serves `public/`. Functions are v2 on Node 24, region us-central1. Firestore is in australia-southeast1.
- Calendar access uses service account `task-calendar-agent@gen-lang-client-0299359787.iam.gserviceaccount.com` (it lives in Google Cloud project `gen-lang-client-0299359787`, not `taskhub-next`). It has edit access to the agent calendar (`USER_CALENDAR_ID`) and "Make changes and see all event details" on the owner's personal calendar. The engine must only ever read the personal calendar, never write to it.
- Firestore rules: deny-all. Every read and write goes through the functions via the Admin SDK, which bypasses rules.
- A separate app, a kids' chore tracker, lives in its own Firebase project (`screen-time-chore-tracker`). Never deploy to it from this repo; always target `taskhub-next` explicitly (`--project taskhub-next`).
- Frontend: one file, `public/index.html`, vanilla HTML/CSS/JS, no build step. Calls the functions over HTTPS via hardcoded URLs. All task-derived text goes through `esc()` before `innerHTML`; list and filter clicks use event delegation on `data-` attributes.
- Backend: `functions/index.js` (endpoints and engine), `functions/calendar.js` (event cleanup helpers) and `functions/time.js` (NZ date/offset helpers). Gemini (`@google/genai`, model constant `MODEL_NAME`) for parsing, scheduling and coaching. Google Calendar via the `googleapis` service-account JWT. Weather from Open-Meteo.
- Secrets: `GEMINI_API_KEY`, `GOOGLE_CALENDAR_CREDENTIALS` (service-account JSON; bound to every function that touches Calendar, including `completeTask` and `updateTaskDirect`).
- Config (Firebase params read from `functions/.env` at deploy): `USER_CALENDAR_ID` (the agent calendar that tasks are scheduled onto) and `USER_PERSONAL_CALENDAR_ID` (the owner's personal calendar, read-only, used for free/busy).

## Data model

- `app_state/todo_doc`: `{tasks: Task[], updatedAt}`. The whole active list is one array in one document.
- `completed_tasks/{auto-id}`: a copy of the Task plus `completedAt`. Write-only archive for future analytics.
- Task: `id`, `title`, `priority` (HIGH/MEDIUM/LOW), `dueDate` (YYYY-MM-DD or empty), `estimatedMinutes`, `tags[]`, `status` (PENDING/COMPLETED), `googleCalendarEventId`, `order` (rank from 1).

## Endpoints

| Function | Purpose | AI |
|---|---|---|
| `getTasks` | Read the active list | No |
| `addOrUpdateTask` | Free text in; Gemini returns the full updated list, which replaces the stored one | Yes |
| `updateTaskDirect` | UPDATE or DELETE one task by id; DELETE also removes its calendar events | No |
| `completeTask` | Archive to `completed_tasks`, remove from the list, remove its calendar events | No |
| `getWhatToDoNow` | Recommend one task from time, energy, weather and the list | Yes |
| `generateWeeklySchedule` | Manual "Plan My Week" | Yes |
| `autoScheduleDaily` | Cron at 20:00 NZ; runs the same engine | Yes |

All HTTP endpoints are unauthenticated with `cors: true`.

Deleting or completing a task removes its calendar events by stored `googleCalendarEventId` and by the `taskId` private extended property on the event, so a task whose stored id was lost still gets cleaned up.

## Scheduling engine (`runScheduleEngine`)

1. Load tasks. Read the personal calendar's free/busy for the next 7 days first; if that fails, abort before touching any events.
2. Delete the Calendar event of every task that has `googleCalendarEventId` (already-missing events are ignored), then sweep every remaining event whose description contains the marker "Generated by AI Task Agent" from the start of today (NZ) onward, which clears orphans from deleted tasks.
3. Read free/busy for the agent calendar, merge it with the personal calendar's busy windows (overlaps combined) and pass Gemini only those time windows, never event titles.
4. Prompt Gemini with the current NZ time and its real UTC offset (+12:00 or +13:00 depending on daylight saving), weather, the merged busy windows (requested in NZ time) and tasks. Rules: 8:00–19:00 NZ local time, opaque for focus tasks and transparent for quick chores, no outdoor tasks in rain.
5. Insert one event per returned item on the agent calendar, store the new event id on the task, save the list.

The cron and the manual trigger both use `USER_CALENDAR_ID`; neither the frontend nor the request chooses the calendar. All writes go to that calendar only. Busy time marked "free" (transparent) on either calendar does not appear in free/busy.

## Roadmap

Each step fits in one turn. Do them in order unless told otherwise.

1. **Safe scheduling.** Ask Gemini first, validate its slots (parse, within hours, no overlap with busy windows or each other), then delete the old events and insert the new ones. Fix all-day events to use an exclusive end date. Keep the old events if generation or validation fails. Store `scheduledStart` and `scheduledEnd` on each task.
2. **Calendar lock.** A task is locked when its agent-created event has been moved to the personal calendar. Detect these by listing events from now on in the personal calendar that carry the "Generated by AI Task Agent" description (match to tasks by stored event id, then `taskId` tag, then title). Skip locked tasks in cleanup, the sweep and scheduling, and give Gemini their windows as unavailable. Release a lock once its event has passed, and never write to the personal calendar. If the lookup fails, abort the run. Mark locked tasks (`locked: true`) so the UI can show them.
3. **Schedule visibility in the app.** Show each task's scheduled date and time and a locked indicator in the task list (read-only; moving the event between calendars is the lock control).
4. **Safe task ingestion.** Make `addOrUpdateTask` ask the model for only the new or changed tasks, then merge server-side so existing ids, order and `googleCalendarEventId` are preserved. Wrap the read-modify-write in a Firestore transaction. Apply the same transaction to the other write endpoints.
5. **Endpoint auth.** Restrict access to the owner (Firebase Auth with an allowlisted account, or a shared-secret header as a minimum). Tighten CORS to the Hosting origin.
6. **Repo hygiene.** Add ESLint config so the predeploy lint passes, plus `.firebaserc`, `.gitignore`, and a short README with deploy and secret-setup commands. Move the function URLs in the frontend to a single config block.
